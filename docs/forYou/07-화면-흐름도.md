# 07. 화면 흐름도

> 기준: screen-flow.md v1.2 / atstudio-front-list.md v4 / ProtectedRoute.tsx
> 작성일: 2026-03-10

---

## 개요

이 문서는 ATStudio 서비스의 주요 사용자 여정을 화면 전환 흐름과 분기 조건 중심으로 설명합니다.
분기 조건은 대괄호 `[ ]`로 표시하며, 각 흐름마다 관련 파일명과 API 엔드포인트를 함께 기재합니다.

**표기 규칙:**
- `[ ]` — 분기 조건
- `→` — 화면 이동
- `↓` — 동일 화면 내 후속 동작
- `M-##` — 모달 (modal-list.md 참조)

---

## 1. 신규 사용자 가입 여정

**목적**: 처음 방문한 사용자가 계정을 생성하고 서비스를 이용하기까지의 전체 흐름.

```
[1 메인] (/)
  └── "로그인" GNB 클릭 → [A-1 로그인] (/login)
                          └── "회원가입" 클릭 → [A-2 회원가입] (/signup)
                                                 └── 폼 제출
                                                     → POST /api/users
                                                     → [이메일 인증 안내 화면] (/email-verify)
                                                         └── 인증 코드 입력 및 확인
                                                             → [A-1 로그인] (/login)
                                                                 └── 이메일+비밀번호 입력 및 로그인 성공
                                                                     → POST /api/auth/login → JWT 발급
                                                                     → [1 메인] (/) — 구독자 메뉴 GNB 노출
```

**관련 파일:**
- `LoginPage.tsx`, `SignupPage.tsx`, `EmailVerifyPage.tsx`

**관련 API:**
- `POST /api/users` (회원가입)
- `POST /api/auth/login` (로그인)

**분기 조건:**
- `[returnUrl 파라미터 있음]` → 로그인 성공 후 해당 경로로 복귀
- `[returnUrl 없음]` → 홈(`/`)으로 이동
- `[이메일 이미 사용 중]` → 인라인 오류 메시지 표시, 화면 유지

## 2. 소셜 로그인 여정

**목적**: 소셜 계정(Google/Kakao/Naver)으로 빠르게 가입·로그인하는 흐름.
소셜 최초 가입자는 추가 정보 입력 단계가 필요합니다.

```
[A-1 로그인] (/login)
  └── "소셜 로그인" 버튼 클릭 (Google/Kakao/Naver 중 선택)
      → OAuth 인증 서버로 이동
      → 인증 완료 후 콜백 → [A-3 소셜 로그인 콜백] (/social-login/:provider)
          → POST /api/auth/social/{provider}
          │
          ├── [기존 사용자 — 프로필 완성 상태]
          │     → JWT 발급 → [1 메인] (/) (직행)
          │
          └── [신규 사용자 — 프로필 미완성 (phone_personal 또는 job이 NULL)]
                → [A-4 추가정보 입력] (/complete-profile) — ProtectedRoute(minRole: USER)
                    └── phone_personal · job 입력 후 제출
                        → PUT /api/users/me/complete-profile
                        → [1 메인] (/) — 전체 기능 접근 가능
```

**관련 파일:**
- `LoginPage.tsx`, `SocialLoginPage.tsx`, `SocialCompleteProfilePage.tsx`

**관련 API:**
- `POST /api/auth/social/{provider}`
- `PUT /api/users/me/complete-profile`

**분기 조건:**
- `[phone_personal IS NOT NULL AND job IS NOT NULL]` → 프로필 완성 상태 → 메인으로 직행
- `[phone_personal IS NULL OR job IS NULL]` → 미완성 → 추가정보 입력 페이지로 이동

## 3. 구독 후 음원 다운로드 여정

**목적**: 비구독 사용자가 음원을 다운로드하기 위해 구독을 구매하고 실제 다운로드까지 완료하는 흐름.

```
[3 음원 목록] (/tracks) 또는 [1 메인] (/)
  └── "장바구니 담기" 클릭 → POST /api/download-queue/{trackId}
      → [11 다운로드 큐] (/download-queue)
          │
          ├── [구독 없음 상태]
          │     → "구독이 필요합니다" 안내 표시
          │     → "구독 플랜 보기" → [16-1 구독 플랜] (/subscriptions)
          │         └── "구독하기" 클릭
          │             ├── [비로그인] → "로그인이 필요합니다" + [A-1 로그인] 이동 제안
          │             └── [로그인+BUSINESS+기업인증 없음] → "기업인증이 필요합니다" + [I-1] 이동 제안
          │             → [16-2 구독 결제] (/subscriptions/payment)
          │                 └── "결제하기" → PG 처리 → POST /api/user-subscriptions
          │                     └── 성공 → [16-3 내 구독 현황] (/subscriptions/manage)
          │
          └── [구독 활성 상태 (ACTIVE)]
                → "항목별 다운로드" 클릭
                    → GET /api/tracks/{trackId}/download
                    ├── [한도 내] → 파일 다운로드 시작, 화면 유지
                    │              → licenses 테이블에 UUID 라이선스 자동 발급
                    │              → [F-1 내 라이선스 목록] (/licenses)에서 확인 가능
                    └── [한도 초과] → 토스트: "오늘 다운로드 한도 초과. {nextResetAt} 초기화"
```

**관련 파일:**
- `TrackListPage.tsx`, `DownloadQueuePage.tsx`, `SubscriptionPlanPage.tsx`
- `SubscriptionPaymentPage.tsx`, `LicenseListPage.tsx`

**관련 API:**
- `POST /api/download-queue/{trackId}`, `GET /api/download-queue`
- `GET /api/subscriptions`, `POST /api/user-subscriptions`
- `GET /api/tracks/{trackId}/download`, `GET /api/licenses/me`

**분기 조건:**
- `[구독 없음]` → 구독 안내 표시
- `[BUSINESS + company_certifications 없음 또는 PENDING]` → 기업인증 안내
- `[today COUNT(track_downloads) >= download_per_day]` → 다운로드 한도 초과

## 4. 크리에이터 음원 업로드 여정

**목적**: 관리자(ADMIN)가 음원을 업로드하고 앨범에 배치하여 공개 목록에 노출시키는 흐름.

```
[관리자 로그인] → POST /api/auth/login (role: ADMIN)
→ [K-7 트랙 관리] (/admin/track-manage) 또는 GNB "음원관리"
    │
    ├── [앨범에 먼저 추가하려면] → [L-4 앨범 생성] (/admin/albums/new)
    │     → POST /api/albums
    │     → 성공 → [L-5 앨범 수정 + 트랙 관리] (/admin/albums/:albumId/edit)
    │
    └── [음원 업로드] → [6 음원 업로드] (/admin/tracks/upload)
          └── 음원 파일 · 썸네일 · 제목 · BPM · 조성 · 설명 입력
              → "태그 선택" → [M-03 SelectModal] (태그 다중 선택, GET /api/tags)
              → "업로드" 제출
                  → POST /api/tracks (is_active 기본값 0 — 비활성 상태로 저장)
                  → 성공 → [B-1 음원 상세] (/tracks/:trackId)
                      │
                      └── [관리자가 활성화] → PUT /api/tracks/{id} (is_active = 1)
                          → [3 음원 목록] (/tracks) 공개 노출
```

**관련 파일:**
- `TrackUploadPage.tsx`, `AlbumCreatePage.tsx`, `AlbumEditPage.tsx`
- `TrackDetailPage.tsx`, `TrackManagePage.tsx`

**관련 API:**
- `POST /api/tracks`, `GET /api/tags`
- `POST /api/albums`, `PUT /api/albums/{id}`
- `PUT /api/tracks/{id}` (활성화)

**분기 조건:**
- `[is_active = 0]` → 공개 목록 미노출, 관리자만 조회 가능
- `[is_active = 1]` → 공개 목록 노출

## 5. 재생목록 관리 여정

**목적**: 구독자가 재생목록을 생성하고 음원을 담아 관리하는 흐름.
재생목록은 활성 상태 기준 최대 3개로 제한됩니다.

```
[GNB 또는 메인] → "재생목록" 클릭
  → [4 재생목록 목록 (이미지)] (/playlists) — GET /api/playlists
      │
      ├── [활성 재생목록 < 3개]
      │     → "새 재생목록 만들기" 버튼 노출 → [8 재생목록 생성] (/playlists/new)
      │         └── 제목 · 설명 입력 → POST /api/playlists
      │             → 생성 성공 → 목록 화면 복귀
      │
      ├── [활성 재생목록 >= 3개]
      │     → "새 재생목록 만들기" 버튼 비노출 (빈 상태 메시지로 한도 안내)
      │
      └── 재생목록 카드 클릭 → [C-1 재생목록 상세] (/playlists/:playlistId)
              → GET /api/playlists/{playlistId}
              └── "편집" 클릭 → [9 재생목록 수정] (/playlists/:playlistId/edit)
                      ├── "트랙 추가" → [M-05 SelectModal] → POST (트랙 추가) → 화면 갱신
                      ├── 트랙 순서 → 드래그앤드롭 → PUT (트랙 순서) → 자동 저장
                      ├── "트랙 삭제" → 인라인 X버튼 → confirm() → DELETE (트랙) → 목록 갱신
                      └── "재생목록 삭제" → [M-07 ConfirmModal]
                            → 확인 → DELETE /api/playlists/{playlistId}
                            → [4 재생목록 목록]으로 이동
```

**관련 파일:**
- `PlaylistImageListPage.tsx`, `PlaylistListPage.tsx`, `PlaylistDetailPage.tsx`
- `PlaylistCreatePage.tsx`, `PlaylistEditPage.tsx`

**관련 API:**
- `GET /api/playlists`, `POST /api/playlists`
- `GET /api/playlists/{playlistId}`, `PUT /api/playlists/{playlistId}`
- `POST (트랙 추가)`, `PUT (트랙 순서)`, `DELETE (트랙)`, `DELETE /api/playlists/{playlistId}`

**분기 조건:**
- `[활성 재생목록 수 >= 3]` → 생성 버튼 비노출, 생성 페이지 접근 차단
- `[구독 미활성 상태]` → 재생목록 기능 자체를 앱 레벨에서 제한 (DB 변경 없음)

## 6. 관리자 기업인증 심사 여정

**목적**: 기업 사용자의 인증 신청을 관리자가 검토하고 처리하는 흐름.
완전 자동화 목표이나, 가이드를 잘 따르는 "좋은 케이스"는 1:1 문의 없이 처리됩니다.

```
[기업 사용자]
  → [16-1 구독 플랜] (/subscriptions) — BUSINESS 플랜 선택
  → "구독하기" 클릭 → [기업인증 없음] 안내 → [I-1 기업인증 신청] (/company-certification/apply)
      └── 사업자 서류 첨부 (파일 업로드)
          → POST /api/company-certifications (status: PENDING)
          → [I-2 기업인증 현황] (/company-certification/status) — "심사 중" 표시

[관리자]
  → 로그인 → [K-5 기업인증 목록] (/admin/company-certifications)
      → GET /api/company-certifications (PENDING 건 상단 노출)
      └── 신청 클릭 → 상세 보기 (서류 확인)
              → "심사 처리" 클릭 → [M-17 ReviewModal]
                  │
                  ├── [승인 (APPROVED)]
                  │     → PUT /api/company-certifications/{id} (status: APPROVED)
                  │     → certification_code 자동 발급
                  │     → [I-2]에서 신청자: "승인됨" 표시, 구독 결제 가능
                  │
                  ├── [보완요청 (REVISION_REQUESTED)]
                  │     → PUT → admin_note 저장
                  │     → [I-2]에서 신청자: "이메일·1:1문의 확인" 안내 표시
                  │     → 관리자가 이메일 또는 1:1 문의로 직접 컨택
                  │
                  └── [반려 (REJECTED)]
                        → PUT → admin_note 저장
                        → [I-2]에서 신청자: "이메일·1:1문의 확인" 안내 표시
```

**관련 파일:**
- `CompanyCertApplyPage.tsx`, `CompanyCertStatusPage.tsx`
- `CompanyCertManagePage.tsx`

**관련 API:**
- `POST /api/company-certifications`
- `GET /api/company-certifications/me`
- `GET /api/company-certifications`, `GET (상세)`, `PUT (심사 처리)`

**분기 조건:**
- `[status = PENDING]` → "심사 중" 표시
- `[status = APPROVED]` → "승인됨" 표시, 구독 결제 버튼 활성화
- `[status = REVISION_REQUESTED / REJECTED]` → UI 재신청 흐름 없음, 이메일·1:1문의 안내

## 7. 인증 분기 흐름 (ProtectedRoute)

**목적**: 로그인 상태와 권한 레벨에 따라 접근 허용/거부를 처리하는 클라이언트 사이드 가드 흐름.

`ProtectedRoute.tsx`는 모든 보호된 페이지의 진입점에서 아래 로직을 실행합니다.

```
보호된 페이지 접근 시도
│
├── [isAuthenticated() = false — 토큰 없음 또는 만료]
│     → <Navigate to="/login" replace />
│     → [A-1 로그인] (/login) — returnUrl이 현재 경로로 자동 보존
│         → 로그인 성공 → JWT 발급 → returnUrl 경로로 복귀
│
├── [isAuthenticated() = true AND ROLE_LEVEL[role] >= ROLE_LEVEL[minRole]]
│     → 페이지 정상 렌더링
│
└── [isAuthenticated() = true AND ROLE_LEVEL[role] < ROLE_LEVEL[minRole]]
      → <Navigate to="/" replace />
      → [1 메인] (/) — 권한 부족으로 홈 리다이렉트
```

**권한 레벨 수치 (ProtectedRoute.tsx 정의):**

| 역할 | 레벨 |
|------|------|
| GUEST | 0 |
| USER | 1 |
| CREATOR | 2 |
| ADMIN | 3 |

**라우터 내 적용 패턴 (index.tsx):**

| 가드 함수 | minRole | 대상 |
|----------|---------|------|
| `authRequired()` | USER (1) | 구독자 전용 19개 라우트 |
| `adminOnly()` | ADMIN (3) | 크리에이터·관리자 15개 라우트 |

**관련 파일:**
- `frontend/src/router/ProtectedRoute.tsx`
- `frontend/src/router/index.tsx`
- `frontend/src/store/authStore.ts` (isAuthenticated, role 상태 관리)

## 8. 구독 변경 여정

**목적**: 이미 구독 중인 사용자가 플랜을 업그레이드 또는 다운그레이드하는 흐름.
업그레이드와 다운그레이드는 적용 시점이 다릅니다.

```
[16-3 내 구독 현황] (/subscriptions/manage)
  → GET /api/user-subscriptions/me
  │
  ├── "플랜 변경" 클릭 → [M-09 PlanCompareModal]
  │       │
  │       ├── [업그레이드 선택 (더 높은 플랜)]
  │       │     → GET /api/utils/subscription-change-preview → proratedAmount(차액) 표시
  │       │     → "결제하기" → [M-27 PG 결제 모달] (현재 보류)
  │       │     → 결제 성공 → PUT /api/user-subscriptions/{id} (즉시 적용)
  │       │     → 화면 갱신 — 새 플랜 즉시 반영
  │       │
  │       └── [다운그레이드 선택 (더 낮은 플랜)]
  │             → "다음 결제일({expiresAt})부터 적용 · 추가 결제 없음" 안내 표시
  │             → "변경 예약" 클릭 → PUT /api/user-subscriptions/{id}
  │             → pending_subscription_id · pending_billing_cycle 저장
  │             → 화면 갱신 — "예약된 변경: {플랜명} ({expiresAt}부터)" 표시
  │
  └── "구독 취소" 클릭 → [M-10 StatusModal]
          → "취소 후 {expiresAt}까지 이용 가능" 안내
          → 확인 → DELETE /api/user-subscriptions/{id} (status: CANCELLED)
          → 화면 갱신 — 취소 상태, expires_at까지 서비스 유지
```

**관련 파일:**
- `SubscriptionManagePage.tsx` (구독자), `SubscriptionPlanPage.tsx`

**관련 API:**
- `GET /api/user-subscriptions/me`
- `GET /api/utils/subscription-change-preview`
- `PUT /api/user-subscriptions/{id}` (업그레이드/다운그레이드/예약)
- `DELETE /api/user-subscriptions/{id}` (취소)

**분기 조건:**
- `[새 플랜 가격 > 현재 플랜 가격]` → 업그레이드: 즉시 적용, 차액 결제
- `[새 플랜 가격 < 현재 플랜 가격]` → 다운그레이드: 다음 결제일 적용, 추가 결제 없음
- `[status = CANCELLED]` → expires_at까지 서비스 유지 후 만료
