## 1. 백엔드 레이어 구조 원칙

ATStudio 백엔드는 4개의 레이어로 구분됩니다. 각 레이어는 자신의 역할만 수행하며 역할을 넘어서는 로직을 작성하지 않습니다.

| 레이어 | 어노테이션 | 역할 | 금지 사항 |
|--------|-----------|------|----------|
| Controller | `@RestController` | HTTP 요청 수신, 응답 변환 | 비즈니스 로직 작성 금지 |
| Service | `@Service`, `@Transactional` | 비즈니스 로직 전체 | — |
| Repository | `@Repository` (JPA 자동 적용) | DB 쿼리 인터페이스 | — |
| Entity | `@Entity` | JPA DB 매핑 | Controller에서 직접 반환 금지 |

**핵심 원칙:**
- Controller는 "얇게(Thin)" 유지합니다. Service 메서드를 호출하고, 결과를 ResponseDTO에 담아 반환하는 것이 전부입니다.
- 비즈니스 판단(검증, 계산, 상태 변경 등)은 모두 Service에 있어야 합니다.
- Entity는 절대 Controller에서 직접 반환하지 않습니다. 반드시 DTO로 변환합니다.

```java
// Controller — 올바른 예
@RestController
@RequestMapping("/api/tracks")
@RequiredArgsConstructor
public class TrackController {
    private final TrackService trackService;

    @GetMapping("/{id}")
    public ResponseEntity<ResponseDTO<TrackResponse>> getTrack(@PathVariable Long id) {
        return ResponseEntity.ok(ResponseDTO.<TrackResponse>withSingleData()
            .message("Track fetched")
            .data(trackService.getTrack(id))
            .build());
    }
}
```

## 2. 필수 어노테이션 가이드

각 어노테이션이 어떤 역할을 하는지 이해하고 사용하세요.

### Controller 레이어

| 어노테이션 | 역할 |
|-----------|------|
| `@RestController` | `@Controller` + `@ResponseBody` 합성. 모든 메서드 반환값이 JSON으로 직렬화됨 |
| `@RequestMapping("/api/...")` | 클래스 레벨 URL 접두사 지정 |
| `@RequiredArgsConstructor` | `final` 필드에 대한 생성자 자동 생성 (의존성 주입용) |
| `@GetMapping`, `@PostMapping`, etc. | HTTP 메서드별 엔드포인트 매핑 |
| `@PathVariable` | URL 경로의 `{id}` 부분을 파라미터로 바인딩 |
| `@RequestBody` | 요청 본문(JSON)을 DTO 객체로 역직렬화 |

### Service 레이어

| 어노테이션 | 역할 |
|-----------|------|
| `@Service` | Spring 빈으로 등록. 비즈니스 레이어임을 명시 |
| `@Transactional(readOnly = true)` | 클래스 레벨에 적용. 기본적으로 읽기 전용 트랜잭션. 불필요한 dirty checking을 방지해 성능 향상 |
| `@Transactional` | 데이터 변경 메서드에 별도 적용. 클래스 레벨 `readOnly=true`를 오버라이드 |

### Entity 레이어

| 어노테이션 | 역할 |
|-----------|------|
| `@Entity` | JPA 관리 엔티티임을 선언. 영속성 컨텍스트가 이 클래스를 추적 |
| `@Table(name = "tracks")` | 매핑할 실제 DB 테이블명 지정 (snake_case) |
| `@Id` | 기본키(PK) 필드 지정 |
| `@GeneratedValue(strategy = GenerationType.IDENTITY)` | DB의 AUTO_INCREMENT를 사용하는 PK 생성 전략 |
| `@Getter` | 모든 필드의 getter 메서드 자동 생성 (Lombok) |
| `@NoArgsConstructor(access = AccessLevel.PROTECTED)` | JPA가 내부적으로 사용하는 기본 생성자를 protected로 제한. 외부에서 `new Track()` 직접 생성 방지 |
| `@Column(nullable = false, length = 200)` | 컬럼 제약사항 지정. `nullable`, `length`, `unique` 등 설정 가능 |
| `@ManyToOne(fetch = FetchType.LAZY)` | N:1 관계. `LAZY`로 지정해 실제 사용 시점에 쿼리 실행 (N+1 방지 기반) |

## 3. Entity 작성 규칙

### 3.1 기본 구조 템플릿

```java
@Entity
@Table(name = "tracks")           // snake_case 테이블명
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)  // 직접 new 금지
public class Track extends BaseEntity {             // created_at, updated_at 자동 관리

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)  // BIGINT AUTO_INCREMENT
    private Long id;

    @Column(nullable = false, length = 100)
    private String title;

    @Column(nullable = false)
    private Integer bpm;

    @Column(name = "is_active", nullable = false)
    private Boolean isActive = false;   // 기본값 설정

    // 관계 매핑 — LAZY 기본
    @OneToMany(mappedBy = "track", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<TrackTag> trackTags = new ArrayList<>();

    // Builder 패턴으로만 생성
    @Builder
    public Track(String title, Integer bpm, Boolean isActive) {
        this.title = title;
        this.bpm = bpm;
        this.isActive = isActive != null ? isActive : false;
    }

    // 상태 변경은 도메인 메서드로 (Setter 금지)
    public void activate() {
        this.isActive = true;
    }

    public void deactivate() {
        this.isActive = false;
    }
}
```

### 3.2 Entity 규칙 요약

- **Setter 금지**: 외부에서 필드를 임의로 변경하면 비즈니스 의도가 드러나지 않습니다. 반드시 `activate()`, `updateTitle()` 등 이름을 가진 도메인 메서드를 사용하세요.
- **Builder 패턴 사용**: 객체 생성 시 어떤 값이 어떤 필드인지 명확합니다.
- **BaseEntity 상속**: `created_at`, `updated_at`을 직접 관리하지 마세요. `BaseEntity`를 상속하면 JPA Auditing이 자동으로 관리합니다.
- **기본값은 선언부에서**: `private Boolean isActive = false;` 처럼 선언 시점에 기본값을 지정하세요.

### 3.3 BaseEntity

모든 엔티티는 BaseEntity를 상속합니다. 직접 작성하지 않아도 `createdAt`, `updatedAt`이 자동으로 채워집니다.

```java
@MappedSuperclass
@Getter
@EntityListeners(AuditingEntityListener.class)
public abstract class BaseEntity {
    @CreatedDate
    @Column(updatable = false)
    private LocalDateTime createdAt;

    @LastModifiedDate
    private LocalDateTime updatedAt;
}
```

## 4. DTO 설계 규칙

### 4.1 Entity vs DTO — 절대 혼용 금지

| 구분 | Entity | DTO |
|------|--------|-----|
| 용도 | DB 영속성 관리 | 레이어 간 데이터 전달 |
| Setter | 없음 | Request DTO만 허용 |
| Controller 반환 | 금지 | 사용 |
| 변환 책임 | Service 레이어 | — |

### 4.2 Request DTO — 가변 객체

```java
// 요청 데이터를 받을 때: Getter + Setter + 기본 생성자
@Getter @Setter
@NoArgsConstructor
public class TrackCreateRequest {
    private String title;
    private Integer bpm;
    private String tonality;
    private String description;
    private List<Long> tagIds;
}
```

Spring MVC가 `@RequestBody`로 JSON을 바인딩할 때 Setter가 필요합니다.

### 4.3 Response DTO — Java record 권장

```java
// Java 17 record: 간결하고 불변
public record TrackResponse(
    Long id,
    String title,
    Integer bpm,
    String tonality,
    Boolean isActive,
    Long playCount,
    List<TagResponse> tags,
    LocalDateTime createdAt
) {
    // Entity → DTO 변환 정적 팩토리 메서드
    public static TrackResponse from(Track track) {
        return new TrackResponse(
            track.getId(),
            track.getTitle(),
            track.getBpm(),
            track.getTonality(),
            track.getIsActive(),
            track.getPlayCount(),
            track.getTrackTags().stream()
                .map(tt -> TagResponse.from(tt.getTag()))
                .toList(),
            track.getCreatedAt()
        );
    }
}
```

### 4.4 매핑 위치 — Service만

Entity → DTO 변환은 Service에서만 수행합니다. DTO가 `toEntity()` 메서드를 가지면 안 됩니다.

```java
// 올바른 위치: Service
@Service
public class TrackService {
    public TrackResponse getTrack(Long id) {
        Track track = trackRepository.findById(id)
            .orElseThrow(() -> new BusinessException(BUSINESS_ERROR.RESOURCE_NOT_FOUND));
        return TrackResponse.from(track); // Service에서 변환
    }
}

// 잘못된 예: DTO가 Entity를 알면 안 됨
public class TrackCreateRequest {
    public Track toEntity() { ... } // 금지
}
```

## 5. ResponseDTO 래퍼 구조

모든 API 응답은 `ResponseDTO<E>` 제네릭 래퍼로 감쌉니다. 단, 조회 데이터가 없는 경우(204 No Content)나 룩업 데이터 예외에 해당하는 경우 제외합니다.

### 5.1 사용 패턴

```java
// 단일 데이터 반환
return ResponseEntity.ok(ResponseDTO.<TrackResponse>withSingleData()
    .message("Track fetched")
    .data(trackResponse)
    .build());

// 목록 + 페이지네이션
return ResponseEntity.ok(ResponseDTO.<TrackResponse>withAll()
    .dataList(trackList)
    .pageInfo(PageInfo.of(requestDTO, totalCount))
    .build());

// 메시지만 (생성/삭제 확인용)
return ResponseEntity.ok(ResponseDTO.withMessage()
    .message("Track created successfully")
    .build());
```

### 5.2 응답 JSON 구조

```json
// 단일 데이터
{
  "message": "Track fetched",
  "data": { "id": 1, "title": "Summer Vibes", ... }
}

// 목록 + 페이지네이션
{
  "dataList": [ ... ],
  "pageInfo": {
    "page": 1,
    "size": 20,
    "total": 150,
    "start": 1,
    "end": 8,
    "prev": false,
    "next": true
  }
}
```

### 5.3 룩업 데이터 예외

`GET /api/tags`는 `ResponseDTO` 없이 `List<TagResponse>`를 직접 반환합니다. 이 예외는 `api-spec.md`에 명시된 경우에만 적용됩니다. 새로운 API에 임의로 적용하지 마세요.

## 6. 예외처리 패턴

### 6.1 두 가지 예외 분류

ATStudio는 예외를 원인에 따라 두 가지로 분류합니다.

| 분류 | 원인 | HTTP 범위 | 로그 레벨 |
|------|------|----------|----------|
| `BusinessException` | 클라이언트 행동 (잘못된 입력, 없는 리소스, 권한 없음) | 4xx | WARN |
| `TechnicException` | 시스템 내부 (DB, 네트워크, IO 오류) | 5xx | ERROR |

### 6.2 BusinessException 사용 예

```java
// 리소스를 찾을 수 없는 경우
Track track = trackRepository.findById(id)
    .orElseThrow(() -> new BusinessException(BUSINESS_ERROR.RESOURCE_NOT_FOUND));

// 구독이 없는 경우
if (subscription == null) {
    throw new BusinessException(BUSINESS_ERROR.NO_ACTIVE_SUBSCRIPTION);
}

// 다운로드 한도 초과
if (todayDownloads >= plan.getDownloadPerDay()) {
    throw new BusinessException(BUSINESS_ERROR.DOWNLOAD_LIMIT_EXCEEDED);
}
```

### 6.3 오류 응답 구조

```json
{
  "status": 403,
  "error": "Forbidden",
  "errorCode": "NO_ACTIVE_SUBSCRIPTION",
  "message": "구독이 필요한 서비스입니다."
}
```

- `error`: HTTP 상태 문구 (예: "Bad Request", "Forbidden")
- `errorCode`: 도메인 오류 코드 (도메인 특정 오류에만 포함, 일반 오류는 생략)
- `message`: 사용자에게 보여줄 안전한 메시지

### 6.4 GlobalExceptionHandler 주의 사항

`AccessDeniedException`은 Spring Security에서 발생하며 일반 `Exception` catch-all에 잡힐 수 있습니다. 이 경우 반드시 별도 분기 처리가 필요합니다.

```java
// Fallback 핸들러 내부에서 분기 처리 필요
if (ex instanceof AccessDeniedException) {
    businessEx = new BusinessException(BUSINESS_ERROR.RESOURCE_NOT_ACCESS);
    // ...
}
```

## 7. 보안 관련 규칙

### 7.1 시크릿 관리

환경변수로 처리해야 할 항목:

```yaml
# application.yml — 절대 하드코딩 금지
spring:
  datasource:
    password: ${DB_PASSWORD}   # 환경변수에서 주입
jwt:
  secret: ${JWT_SECRET}        # 환경변수에서 주입
```

현재 개발 편의상 기본값(예: `1234`)이 설정되어 있으나, 운영 환경에서는 반드시 환경변수로 오버라이드해야 합니다.

### 7.2 Spring Security 필터 순서

구체적인 규칙을 와일드카드 앞에 선언해야 합니다.

```java
// 올바른 순서
http.authorizeHttpRequests(auth -> auth
    .requestMatchers("/api/users/me").authenticated()    // 구체적 규칙 먼저
    .requestMatchers("/api/users/**").hasRole("ADMIN")   // 와일드카드는 뒤에
    .requestMatchers("/api/tracks/**").permitAll()
    // ...
);
```

이 순서가 뒤바뀌면 `/api/users/me`가 ADMIN 전용으로 처리될 수 있습니다.

### 7.3 CSRF 정책

- REST API 엔드포인트: CSRF 비활성화 (JWT 기반 인증 사용)
- Thymeleaf 폼 페이지: CSRF 활성화 (세션 기반)

## 8. MySQL 네이밍 규칙

### 8.1 테이블 및 컬럼

| 요소 | 규칙 | 예시 |
|------|------|------|
| 테이블명 | snake_case, 복수형 | `tracks`, `user_subscriptions`, `playlist_tracks` |
| 컬럼명 | snake_case | `created_at`, `is_active`, `download_per_day` |
| PK | `id` (BIGINT AUTO_INCREMENT) | `id` |
| FK | `참조테이블_id` | `user_id`, `track_id` |
| 날짜/시간 | `_at` 접미사 | `created_at`, `updated_at`, `expires_at` |
| 불리언 | `is_` 접두사 | `is_active`, `is_deleted`, `is_verified` |

### 8.2 JPA와의 매핑

```java
@Entity
@Table(name = "user_subscriptions")  // snake_case 테이블명
public class UserSubscription extends BaseEntity {
    @Column(name = "is_active")       // snake_case 컬럼명
    private Boolean isActive;

    @Column(name = "expires_at")
    private LocalDate expiresAt;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "user_id")     // FK 컬럼명
    private User user;
}
```

## 9. 프론트엔드 — CSS Modules & 디자인 토큰

### 9.1 CSS Modules 사용 규칙

Tailwind CSS, styled-components, inline style은 사용하지 않습니다. CSS Modules만 사용합니다.

```
// 파일 구조
src/
├── components/
│   ├── TrackRow.tsx
│   └── TrackRow.module.css    ← 컴포넌트와 같은 폴더
├── pages/
│   ├── TrackList.tsx
│   └── TrackList.module.css
```

```css
/* TrackRow.module.css */
.container {
  display: flex;
  align-items: center;
  padding: var(--spacing-md);    /* 디자인 토큰 사용 */
  border-bottom: 1px solid var(--color-border);
}

.title {
  color: var(--color-text-primary);
  font-size: var(--font-size-md);
}
```

```tsx
// TrackRow.tsx
import styles from './TrackRow.module.css';

const TrackRow = ({ track }: Props) => (
  <div className={styles.container}>
    <span className={styles.title}>{track.title}</span>
  </div>
);
```

### 9.2 CSS 디자인 토큰 (tokens.css)

모든 색상, 간격, 폰트 크기는 `tokens.css`의 CSS 변수를 참조합니다. 하드코딩된 색상값 사용 금지.

```css

:root {
  --color-primary: #6366f1;
```

## 10. 프론트엔드 — 상태 관리 (Zustand vs useState)

### 10.1 상태 종류별 사용 지침

| 상태 종류 | 해결책 | 이유 |
|----------|--------|------|
| 인증 정보 (user, token) | `useAuthStore` (Zustand) | 전역 공유, 변경 빈도 낮음 |
| UI 피드백 (toast, modal) | `useUIStore` (Zustand) | 크로스-커팅 관심사 |
| 서버 데이터 (목록, 검색 결과) | Axios + 로컬 state | 서버 연동 |
| 폼 입력값 | `useState` | 단일 컴포넌트 범위 |

```typescript
// stores/authStore.ts
import { create } from 'zustand';

interface AuthState {
  user: UserInfo | null;
  isAuthenticated: boolean;
  setUser: (user: UserInfo | null) => void;
  clearAuth: () => void;
}

export const useAuthStore = create<AuthState>((set) => ({
  user: null,
  isAuthenticated: false,
  setUser: (user) => set({ user, isAuthenticated: user !== null }),
  clearAuth: () => set({ user: null, isAuthenticated: false }),
}));
```

### 10.2 주의: AccessToken은 메모리에만 저장

```typescript
// 메모리 변수 (파일 모듈 스코프)
let accessToken: string | null = null;

export const setAccessToken = (token: string | null) => {
  accessToken = token;
};

export const getAccessToken = () => accessToken;
```

AccessToken을 localStorage에 저장하면 XSS 공격에 노출됩니다. 메모리 변수에만 보관합니다.

```typescript
// api/client.ts
axiosInstance.interceptors.request.use((config) => {
  const token = getAccessToken();
  if (token) {
    config.headers.Authorization = `Bearer ${token}`;
  }
  return config;
});

// 401 응답 시 토큰 갱신 후 재시도
axiosInstance.interceptors.response.use(
  (response) => response,
  async (error) => {
    if (error.response?.status === 401) {
      const newToken = await refreshAccessToken();
      error.config.headers.Authorization = `Bearer ${newToken}`;
      return axiosInstance(error.config);
    }
    return Promise.reject(error);
  }
);
```

### 13.2 ProtectedRoute 구현

```tsx
interface ProtectedRouteProps {
  children: React.ReactNode;
  roles?: string[];
}

const ProtectedRoute = ({ children, roles }: ProtectedRouteProps) => {
  const { user, isAuthenticated, initializing } = useAuthStore();

  if (initializing) return <LoadingSpinner />;

  if (!isAuthenticated) {
    return <Navigate to="/login" replace />;
  }

  if (roles && !roles.some(role => user?.role === role)) {
    return <Navigate to="/" replace />;
  }

  return <>{children}</>;
};
```
