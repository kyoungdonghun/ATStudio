# SR-94 관리자 태그 중복 저장 실패 처리 개선

> **우선 가치**: 태그 이름 중복은 예상 가능한 사용자 입력 오류로 처리한다. 프론트엔드의 사전 안내로 불필요한 요청을 줄이되, 백엔드의 `409 TAG_NAME_DUPLICATED` 계약을 서버 측 검증으로 유지하고 동시 요청은 DB 유일성 제약으로 방어한다.

## 환경

- 관리자 태그 관리 화면
- 태그 생성 및 수정
- PC, 모바일 공통

## 인수 테스트에서 확인된 현상

- 기존 태그와 같은 이름으로 태그를 생성하면 요청이 백엔드까지 전송됨.
- 백엔드는 중복 이름을 감지하여 HTTP `409 Conflict`, 오류 코드 `TAG_NAME_DUPLICATED`, 사용자 메시지 `이미 존재하는 태그 이름입니다.`를 반환하고 있음.
- 서비스의 중복 조회를 동시에 통과한 요청이 DB의 `uq_tags_name` 유일성 제약에서 충돌하면, 현재 공용 예외 처리는 `409 DATA_INTEGRITY_VIOLATION`으로 응답할 수 있음.
- 프론트엔드는 저장 요청의 모든 실패를 구분하지 않고 `Failed to save tag`로 처리함.
- 이 오류가 페이지 공용 오류 상태에 저장되면서 태그 관리 목록과 입력 모달 전체가 오류 문구만 있는 화면으로 대체됨.
- 태그 수정에서도 다른 태그와 같은 이름으로 변경하면 동일한 문제가 발생할 수 있음.

## 현재 계약과 문제 구분

| 구분 | 현재 동작 | 판단 |
| --- | --- | --- |
| 프론트엔드 사전 검사 | 빈 값은 제출 시 `trim()` 결과로만 막고, 중복 이름은 사전에 검사하지 않음 | 개선 필요 |
| API 호출 | 태그 생성·수정 요청이 백엔드로 전송됨 | 사전 중복 검사로 불필요한 호출 감소 필요 |
| 백엔드 응답 | 중복 이름에 `409 TAG_NAME_DUPLICATED` 반환 | 유지 필요 |
| DB 경합 응답 | `uq_tags_name` 위반을 공용 `409 DATA_INTEGRITY_VIOLATION`으로 처리할 수 있음 | 태그 이름 중복 도메인 오류로 안정적으로 변환 필요 |
| 화면 상태 | 모든 저장 실패를 페이지 공용 오류로 처리하여 모달·목록이 사라짐 | 수정 필요 |

## 수정 내용

### 1. 프론트엔드 사전 중복 안내

- 태그 생성과 수정 모두에서 제출 전에 현재 목록의 태그 이름과 비교함.
- 비교에는 SR-95에서 결정할 동일한 정규화 규칙을 적용함.
- 수정 시에는 편집 중인 태그 자신의 ID를 비교 대상에서 제외함.
- 중복이면 백엔드 요청을 보내지 않고 이름 입력 필드 가까이에 `이미 존재하는 태그 이름입니다.`를 표시함.
- 사용자가 이름을 변경하면 중복 상태를 다시 계산하여 안내를 해제하거나 갱신함.

### 2. 백엔드 409 응답 처리

- 프론트엔드 목록 기반 검사는 오래된 목록과 직접 API 호출을 막을 수 없으므로 백엔드 중복 검사를 제거하지 않음.
- 서비스의 사전 중복 조회를 동시에 통과하는 경합은 DB의 `uq_tags_name` 유일성 제약으로 차단함.
- `uq_tags_name` 위반은 다른 무결성 오류와 구분하여 `409 TAG_NAME_DUPLICATED`로 변환함.
- 서버가 `409`와 `TAG_NAME_DUPLICATED`를 반환하면 사전 검사와 같은 사용자 메시지를 이름 필드에 표시함.
- 상태 코드만 보지 말고 서버의 도메인 오류 코드로 중복 오류를 식별함.

### 3. 저장 실패 시 화면과 입력 상태 보존

- 중복 오류가 발생해도 생성·수정 모달을 닫지 않음.
- 사용자가 입력한 이름과 선택한 태그 유형을 유지함.
- 기존 태그 목록, 필터 탭, 관리 화면을 그대로 유지함.
- 중복 이외의 저장 실패도 페이지 전체를 교체하지 않고 모달 내부 또는 비차단 알림으로 안내하되, 서버에서 제공한 안전한 사용자 메시지가 있으면 우선 사용함.
