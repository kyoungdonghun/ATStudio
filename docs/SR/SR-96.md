# SR-96 관리자 역할 변경 시 마지막 관리자 상실 방지
> **우선 가치**: 관리자 역할 변경은 화면 선택지보다 서버의 권한 불변조건이 우선한다. 자기 강등, 마지막 관리자 강등, 동시 강등을 모두 막아 운영 제어권이 사라지지 않도록 하고, 실제 서버 권한과 화면에 남은 권한 표시를 일치시킨다.

## 환경

- 관리자 페이지 > 사용자 관리
- 사용자 역할 `USER` / `ADMIN` 변경
- PC, 모바일 공통

## 인수 테스트에서 제기된 위험

- 관리자 화면에서 사용자의 역할을 `ADMIN`에서 `USER`로 변경할 수 있음.
- 현재 로그인한 관리자가 자기 역할을 내리거나, 남아 있는 마지막 관리자를 내릴 수 있다면 관리자 기능을 수행할 계정이 0명이 될 수 있음.
- 관리자 두 명이 서로를 거의 동시에 강등하는 경우에는 단순한 관리자 수 조회만으로 마지막 관리자 조건을 보호하지 못할 수 있음.

## 현재 확인된 동작

| 구분 | 현재 동작 | 판단 |
| --- | --- | --- |
| 프론트엔드 | 모든 사용자 행에 동일한 `USER` / `ADMIN` 선택지를 표시하고, 현재 로그인 사용자나 마지막 관리자 여부를 구분하지 않음 | 자기 강등 요청 가능 |
| API 권한 | `PUT /api/users/{userId}` 호출 시작 시 요청자가 `ADMIN`인지 검사함 | 요청자와 대상의 관계는 검사하지 않음 |
| 백엔드 저장 | 대상 사용자를 일반 조회한 뒤 전달된 역할을 그대로 반영함 | 자기 강등과 마지막 관리자 강등을 모두 허용함 |
| 동시성 보호 | 현재 역할 변경 경로는 관리자 수 조회나 공통 잠금을 사용하지 않음 | 서로 다른 관리자를 동시에 강등하면 0명 상태에 도달할 위험이 있음 |
| 감사·복구 | 역할 변경 전용 감사 기록과 운영 관리자 복구 절차를 확인하지 못함 | 사고 추적과 복구 기준 필요 |

따라서 현재 구현에서는 **관리자가 자기 자신을 포함한 관리자를 `USER`로 강등할 수 있고, 마지막 관리자 보호도 없다.**

## 인증 상태에서 구분해야 할 점

- 액세스 토큰에는 발급 시점 역할이 들어가지만, 현재 서버 인증 필터는 토큰에서 사용자 ID를 얻은 뒤 DB의 사용자를 다시 조회하여 **현재 DB 역할**로 권한을 구성함.
- 따라서 DB에서 `USER`로 강등된 사용자가 기존 액세스 토큰만으로 다음 관리자 API 권한을 계속 유지하는 구조는 아님. 다음 관리자 요청은 서버에서 거절됨.
- 반면 React의 보호 라우트는 로컬에 저장된 사용자 역할을 사용하고, 토큰 갱신 과정도 저장된 사용자 역할을 자동 갱신하지 않음.
- 그 결과 강등된 사용자가 관리자 화면에 계속 머물거나 메뉴를 볼 수 있지만, 실제 API에서는 `403`을 만나는 **화면 역할과 서버 역할의 불일치**가 발생할 수 있음.

## 수정 내용

### 1. 서버의 역할 변경 불변조건

- `ADMIN -> USER` 변경에서 요청자와 대상이 같으면 서버가 `SELF_ADMIN_DEMOTION_FORBIDDEN`과 같은 명시적인 도메인 오류로 거절함.
- 다른 관리자를 강등할 때도 변경 완료 후 삭제되지 않은 `ADMIN`이 최소 1명 남는지 서버가 검사함.
- 요청이 잠금 대기 중일 수 있으므로, 역할 변경을 실제 적용하기 직전에 요청자가 여전히 삭제되지 않은 `ADMIN`인지 다시 확인함.
- 프론트엔드의 선택지 비활성화는 빠른 안내용으로만 사용하고, 직접 API 호출을 포함한 최종 방어는 백엔드가 담당함.
- 정상 운영에서는 복구를 위해 사용 가능한 관리자 계정을 2명 이상 유지하도록 운영 기준을 별도로 권고하되, 데이터 불변조건의 최소값은 1명으로 둠.

### 2. 동시 강등 방지

- 관리자 수를 조회한 뒤 각 대상 행만 잠그는 방식은 서로 다른 대상의 동시 강등을 막지 못함.
- 모든 역할 변경이 공유하는 하나의 직렬화 지점을 두고, 같은 트랜잭션 안에서 요청자 재확인, 대상 조회, 변경 후 관리자 수 검증, 역할 변경, 성공 감사 기록을 처리함.
- 공유 잠금의 구체적인 구현은 별도 설계에서 결정하되, 전용 guard 행 잠금이나 검토된 관리자 집합 잠금처럼 모든 역할 변경이 같은 순서를 거치도록 함.
- 실제 MySQL 환경에서 관리자 두 명이 서로를 동시에 강등해도 최대 한 요청만 성공하고 최종 관리자 수가 1명 이상인지 검증함.

### 3. 화면·오류·세션 동기화

- 현재 로그인한 관리자 자신의 `ADMIN -> USER` 선택지는 비활성화하고 그 이유를 가까이 표시함.
- 마지막 관리자 조건은 서버가 `LAST_ADMIN_REQUIRED`와 같은 안정적인 오류 코드로 거절하고, 목록 전체를 오류 페이지로 바꾸지 말고 해당 행 또는 확인 모달에 안내함.
- 타 관리자 강등 전에는 대상 식별 정보, 변경 전·후 역할, 영향, 재인증 여부를 확인 창에 표시함.
- 서버가 현재 세션 사용자의 역할 변경을 감지하거나 관리자 API가 역할 상실로 `403`을 반환하면 `/users/me`를 다시 조회하고 관리자 라우트와 메뉴를 재평가함.
- 강등된 사용자의 Refresh Token 제거와 재인증 요구를 우선 권고함. 기존 액세스 토큰을 USER 권한으로 만료 시점까지 허용할지, 세션 버전으로 완전히 종료할지는 후속 보안 정책에서 확정함.

### 4. 감사와 운영 복구

- 성공한 역할 변경에는 요청자 ID, 대상 ID, 변경 전·후 역할, 결과, 운영 사유, 서버 시각을 기록함.
- 거절된 자기 강등·마지막 관리자 강등 시도도 트랜잭션 롤백과 함께 사라지지 않는 보안 이벤트 경로에 최소 정보로 기록함.
- 이메일, 전화번호, 비밀번호, 액세스·Refresh Token, 전체 사용자 프로필은 역할 변경 감사 로그에 저장하지 않음.
- 운영 환경에서 관리자 0명 사고를 복구하는 제한된 절차를 별도로 마련함. 공개 복구 API나 QA용 관리자 부트스트랩을 운영 복구 수단으로 사용하지 않음.
- 복구 절차에는 승인된 사고·변경 번호, 2인 확인, 변경 전 백업, 기존 검증된 운영자 한 명의 제한적 승격, 전후 관리자 수와 로그인/API 확인, 세션·자격 증명 점검, 감사 증거를 포함함.

## 완료 조건

- [ ] 자기 자신을 `ADMIN`에서 `USER`로 변경하는 요청이 프론트엔드에서 안내되고 백엔드에서도 명시적인 오류로 거절됨.
- [ ] 다른 관리자가 마지막 남은 관리자를 강등하려는 요청이 서버에서 거절됨.
- [ ] 관리자 2명 이상일 때 다른 관리자 1명을 강등할 수 있고, 완료 후 관리자가 최소 1명 남음.
- [ ] 관리자 두 명의 동시 교차 강등 테스트에서 최대 한 건만 성공하고 최종 관리자 수가 1명 이상임.
- [ ] 잠금 대기 중 요청자의 역할이 먼저 강등되면 해당 요청의 관리자 작업도 적용 직전 재검사에서 거절됨.
- [ ] 삭제된 관리자 계정은 마지막 관리자 수에 포함되지 않음.
- [ ] 강등 직후 기존 액세스 토큰의 다음 관리자 API 요청은 `403`이며, 화면도 최신 사용자 역할을 다시 읽어 관리자 라우트에서 이탈함.
- [ ] 성공·거절 감사 기록에 필요한 최소 항목이 있고 토큰·비밀번호·불필요한 개인정보가 없음.
- [ ] 운영 관리자 복구 절차가 문서화되고 비운영 복제 환경에서 복구 훈련이 검증됨.

## 후속 설계에서 결정할 사항

- [ ] 모든 역할 변경을 직렬화할 전용 guard 행과 관리자 집합 잠금 중 어떤 방식을 사용할지
- [ ] 강등 시 Refresh Token만 제거할지, 액세스 토큰까지 세션 버전으로 즉시 무효화할지
- [ ] 운영 복구 수단을 봉인된 복구 관리자 계정과 오프라인 승격 명령 중 어떤 방식으로 둘지
