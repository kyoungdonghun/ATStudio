## Purpose

This SR tracks the remaining production-readiness work for the Toss billing-key recurring subscription system.

The P0 withdrawal renewal-stop behavior is implemented and focused-test verified in implementation commit `d11c62d`. This SR remains OPEN for production server setup, broader payment-integrity gates, operational safety, and follow-up payment operations.

## Current Implementation Snapshot

### Implemented

| Area | Current state |
|---|---|
| New subscription checkout | User-facing subscription purchase enters `/subscriptions/checkout` and uses Toss billing auth. |
| Billing auth callback | `/subscriptions/checkout/success` and `/subscriptions/checkout/fail` are the active callback routes. |
| First charge | Billing key confirmation immediately performs the first subscription charge before activating the subscription. |
| Direct subscription mutation | `POST /api/user-subscriptions` is blocked with `SUBSCRIPTION_CHECKOUT_REQUIRED`. |
| One-time subscription payment | `POST /api/payments/subscriptions/prepare` does not create `SUBSCRIBE` or `UPGRADE` one-time subscription orders. |
| One-time subscription confirm | `POST /api/payments/confirm` rejects legacy `SUBSCRIBE` and `UPGRADE` one-time orders before provider confirmation. |
| Legacy payment redirect | `/subscriptions/payment/*` is treated as a stale legacy subscription route and does not mutate subscriptions. |
| Upgrade | Plan upgrade is confirmed from the subscription management preview and charged through the active billing agreement. |
| Upgrade plus next-cycle change | The higher plan applies immediately after the upgrade charge. If the user selected a different next renewal cycle, only the billing-cycle change remains pending and must be labeled separately from a pending plan change. |
| Removed billing-key recovery | If Toss reports a stored billing key as removed/invalid during upgrade, the local billing agreement is marked `EXPIRED`, issued-key metadata is cleared, and the subscription remains unchanged. |
| Payment method re-registration | Active or CANCELLED grace-period subscribers can register a new payment method through a zero-amount `BILLING_AGREEMENT` order without changing the current subscription. Interrupted `READY` registrations are treated as incomplete and can be restarted. Upgrade-origin registrations preserve return context so the user can continue the selected plan change after card registration. |
| Upgrade billing cycle rule | Upgrade preserves the current paid period and current billing cycle. If the user selected a different next cycle, that cycle is stored as pending for the next renewal. |
| Scheduled change | Lower-tier and billing-cycle-only changes are payment-free and stored as a pending plan/cycle change. A later selection can overwrite the pending change. |
| Pending change clear | Selecting the current plan/current cycle clears a pending plan/cycle change. |
| Automatic renewal | `RecurringRenewalService` charges due active billing agreements and extends subscriptions on success. |
| Renewal failure policy | Renewal failure uses a 3-day grace period and up to 3 retry attempts. Failure emails are sent through the existing email service. |
| Subscription cancel | User-facing cancellation stops the next renewal by marking the subscription and local billing agreement as cancelled while preserving already-paid access until `expiresAt`. |
| Account withdrawal billing stop | Password-authenticated withdrawal marks a non-terminal agreement and ACTIVE subscription `CANCELLED` before soft-deleting the user. Deleted users are excluded by both renewal query and service guard. |
| Withdrawal Provider cleanup | An ID-only event runs after commit; agreement-specific `REQUIRES_NEW` cleanup clears issued-key fields on Provider success. |
| Withdrawal cleanup failure/retry | Failure keeps local cancellation and encrypted key material, creates/increments an agreement-scoped `WARNING` `LOCAL_DONE_PROVIDER_NOT_DONE` Incident, and is retried daily at 01:15. |
| Already-removed convergence | `ALREADY_REMOVED_BILLING_KEY` is treated as successful cleanup, clears local key material, and resolves the matching Incident. |
| Withdrawal refund boundary | Account withdrawal creates no automatic refund. Refund remains a separate admin request/approval/execution workflow. |
| Cancellation reactivation | A cancelled grace-period subscription can be reactivated before `expiresAt` by reusing the stored billing key when the billing agreement is still valid. |
| Provider-level billing agreement cancel | The legacy/operations billing-agreement cancel API deletes the provider billing key and clears local issued-key fields; it is not the current user-facing cancel UX. |
| Stale order cleanup | Scheduler expires old `READY` and `IN_PROGRESS` payment orders. |
| Local ledger reconciliation | `PaymentReconciliationService` logs local mismatches such as `DONE` order without payment row and active billing agreement without active subscription. |
| Provider API reconciliation | `PaymentReconciliationService` compares recent subscription payment orders with Toss provider state by `orderId` when Toss lookup configuration is available. |
| Admin visibility | `/admin/payments` provides payment order, billing agreement, subscription payment, reconciliation incident, receipt, audit, settlement, refund, and entitlement correction operation tabs. |
| Admin reconciliation | `GET /api/admin/payments/reconciliation` runs read-only local/provider reconciliation and returns support-safe issue records. |
| Reconciliation incident storage | Scheduled reconciliation creates or updates `payment_reconciliation_incidents` with `OPEN`, `ACKNOWLEDGED`, `RESOLVED`, and `IGNORED` workflow states. |
| Reconciliation incident admin APIs/UI | Admins can list incidents and update incident workflow state from APIs and `/admin/payments` without mutating payments, subscriptions, or billing agreements. |
| Reconciliation operator notification | Optional operator email notification is available when `PAYMENT_RECONCILIATION_NOTIFICATION_ENABLED=true` and `PAYMENT_OPERATIONS_OPERATOR_EMAIL` is set. |
| Receipt evidence storage | Successful initial subscription, upgrade, and renewal charges publish safe receipt evidence after commit. `payment_receipts` stores provider receipt URL/key metadata when Toss returns it. |
| Payment operation audit logs | `payment_operation_audit_logs` stores reconciliation incident status changes, system receipt evidence creation events, admin refund workflow transitions, and admin entitlement correction workflow transitions. |
| Refund ledger and Toss cancel API | Admin refund preview/request/approve/execute/read APIs are implemented through `payment_refunds`. Provider cancel execution uses the persisted idempotency key and does not automatically mutate subscription entitlement. |
| Refund entitlement correction | Admin entitlement correction preview/request/approve/execute/read APIs are implemented through `payment_entitlement_corrections`. Execution applies only explicit target subscription state and optionally local billing agreement cancellation; it does not call provider billing-key delete APIs or infer previous-plan rollback. |
| Settlement import/reconciliation | Admin settlement CSV import, settlement row list, missing-provider evidence scan, and ignore workflow are implemented through `payment_settlements`. Settlement rows are accounting review evidence and do not mutate subscriptions, payments, refunds, billing agreements, or provider state. |
| Refund/settlement/tax invoice policy | Policy is documented in [Payment Refund, Receipt, Settlement, and Tax Invoice Policy](../design/payment-refund-receipt-settlement-policy.md). First-class admin receipt/audit/settlement/refund/entitlement UI is implemented. Tax invoice workflow and cash receipt issue/cancel automation are on hold for card-only recurring billing. |
| Sensitive data boundary | User/admin responses do not expose raw billing keys, auth keys, Toss secret keys, raw card data, or raw provider payloads. |

## Production Transition Checklist

### Configuration

- Provision Toss test and live keys separately.
- Set `PAYMENT_BILLING_KEY_ENCRYPTION_SECRET` only through environment variables or a secret manager.
- Configure billing auth success/fail URLs to the production frontend origin.
- Confirm `TOSS_PAYMENT_LOOKUP_BY_ORDER_ID_URL` uses the production Toss payment lookup endpoint.
- Confirm production CORS allows only intended frontend origins.
- Keep `application-local.yml` out of production deployment assumptions.
- Confirm recurring checkout fails safely with `PAYMENT_PROVIDER_NOT_CONFIGURED` when Toss billing keys are missing.

### Security and data handling

- Never store raw card numbers, CVC, or expiry data.
- Never return raw billing keys to frontend or admin APIs.
- Keep Toss secret keys server-side only.
- Keep `authKey` and `customerKey` limited to the billing auth confirmation boundary.
- Sanitize provider failure payloads before storing or displaying them.
- Check logs for accidental raw provider payload, billing key, or card data exposure.

### Operations

- Run only one renewal scheduler instance in the current single-server deployment.
- Keep renewal charge idempotency based on `PaymentOrder` and provider idempotency key.
- Monitor failed renewal email delivery.
- Monitor scheduler logs for stale order expiration and renewal failures.
- Monitor local and provider reconciliation warnings.
- Monitor the 01:15 withdrawal cleanup retry aggregate and agreement-scoped cleanup Incidents.
- Confirm WARN-level reconciliation logs are collected by the production log monitoring system.
- Use `GET /api/admin/payments/reconciliation` for on-demand mismatch checks.
- Use `/admin/payments` or `GET /api/admin/payments/reconciliation-incidents?status=OPEN` for persisted incident triage.
- Enable `PAYMENT_RECONCILIATION_NOTIFICATION_ENABLED` and `PAYMENT_OPERATIONS_OPERATOR_EMAIL` if operator email alerts are required.
- Use `GET /api/admin/payments/receipts` to confirm safe receipt evidence after successful staging charges when provider receipt fields are present.
- Use `GET /api/admin/payments/operation-audit-logs` to confirm incident status changes and receipt evidence creation were recorded.
- Use `GET /api/admin/payments/refund-preview/{subscriptionPaymentId}` and the refund request/approve/execute APIs only for support-approved refund cases in a safe test/staging environment.
- Use `POST /api/admin/payments/entitlement-correction-preview` and the entitlement correction request/approve/execute APIs only after a refund has succeeded and support has approved the exact target access state.
- Use `GET /api/admin/payments/settlements`, `POST /api/admin/payments/settlements/import`, `POST /api/admin/payments/settlements/reconcile`, and `PUT /api/admin/payments/settlements/{settlementId}/ignore` only for PG-to-ATStudio settlement review. These APIs must not be used as payment/refund/subscription mutation tools.
- Use [Payment Operations Runbook](../design/payment-operations-runbook.md) for provider success plus local persistence failure.
- For withdrawal cleanup failure, keep the user deleted and agreement `CANCELLED`; do not restore renewal eligibility or manually clear encrypted key material. Allow targeted retry and verify automatic Incident resolution after convergence.
- Do not create a refund solely because account withdrawal occurred.
> Current deployment assumes a single application server. Multi-server scheduler lock is intentionally out of active scope and should be reconsidered only before running more than one application instance.

### Database and migration

- Confirm `billing_agreements`, `payment_orders`, `subscription_payments`, `payment_refunds`, `payment_entitlement_corrections`, `payment_settlements`, `payment_reconciliation_incidents`, `payment_receipts`, and `payment_operation_audit_logs` schema exists in production.
- Confirm indexes for billing agreement status/next billing date and payment order lookup exist.
- Confirm the deployment DB has been patched before startup because the base backend config uses `spring.jpa.hibernate.ddl-auto=validate`.
- Treat `src/main/resources/schema.sql` as a fresh-DB/reference schema, not as an automatic migration for an existing database.
- For the latest payment settlement plus whitelist workflow delta, review and apply `src/main/resources/db/manual/20260615_align_payment_whitelist_schema.sql` on a copied local/staging DB before any shared DB.
- Back up subscription and payment tables before production activation.
- Decide whether existing local/test subscriptions should be expired, cancelled, or left as test data before production-like staging.

Use this list for staging or production rehearsal.

| Scenario | Expected result |
|---|---|
| New subscription success | Billing auth succeeds, first charge succeeds, subscription becomes `ACTIVE`. |
| Billing auth failure | No subscription is created or changed. User can retry with a fresh checkout. |
| First charge failure after billing key issue | Subscription is not activated, order is failed, issued key is cancelled where possible. |
| Direct `POST /api/user-subscriptions` call | Returns `410 Gone` with `SUBSCRIPTION_CHECKOUT_REQUIRED`. |
| Legacy one-time subscription prepare | Returns a business error and creates no subscription mutation. |
| Legacy `/subscriptions/payment/*` redirect | Shows safe stale-route guidance and does not call one-time confirm. |
| Upgrade with active billing agreement | Remaining-period difference is charged immediately, plan changes immediately, current expiration date remains. |
| Upgrade with provider-removed billing key | Charge fails with `BILLING_AGREEMENT_REAUTH_REQUIRED`, billing agreement becomes `EXPIRED`, issued-key metadata is cleared, subscription stays unchanged. |
| Interrupted payment method registration | Billing agreement status `READY` is shown as incomplete, payment method is not displayed as registered, and the user can restart registration. |
| Upgrade-origin payment method registration | Checkout shows that registration itself has no immediate charge, separately shows the selected upgrade's expected prorated amount, and returns to the selected plan/cycle preview after registration succeeds. |
| Payment method re-registration | Active subscriber completes Toss billing auth with `purpose=BILLING_AGREEMENT`; no immediate charge occurs, billing agreement becomes `ACTIVE`, next billing date remains the subscription `expiresAt`. |
| Upgrade with selected next cycle different from current cycle | Upgrade charge applies the higher plan immediately. Current paid cycle remains until renewal, selected next cycle is stored as pending, and the UI labels only the billing-cycle reservation rather than implying the upgraded plan is still pending. |
| Upgrade without active billing agreement | No one-time checkout fallback. User sees safe guidance. |
| Scheduled lower-tier/cycle change | No immediate charge. Pending change applies after the next successful renewal. |
| Pending change overwrite | User can choose another plan/cycle before renewal; pending values are replaced. |
| Pending change clear | User selects the current plan/current cycle; pending values are cleared. |
| Automatic renewal success | Renewal charge succeeds, subscription extends, failure count resets. |
| Automatic renewal failure during grace | Failure count increases, email is sent, access remains during grace. |
| Automatic renewal final failure | Billing agreement becomes suspended and subscription expires after grace. |
| Subscription cancel | Future charges stop, current paid access remains until `expiresAt`. |
| Cancellation reactivation | Before `expiresAt`, user can keep the subscription and future renewal resumes from the original expiresAt without card re-registration when the stored billing key is valid. |
| Account withdrawal | User, ACTIVE subscription, and non-terminal agreement become locally non-renewable before cleanup dispatch; no refund row is created. |
| Renewal after withdrawal | Due renewal produces zero key-decrypt, order-save, subscription-lookup, and Provider-charge calls for the deleted user. |
| Withdrawal cleanup failure | Local cancellation remains; encrypted key is retained; one agreement-scoped `WARNING` Incident is created or incremented. |
| Withdrawal cleanup retry success | Issued-key fields are cleared and the matching Incident is resolved. |
| Provider key already removed | `ALREADY_REMOVED_BILLING_KEY` converges to the same cleared/resolved result. |
| Admin read-only payment page | Shows operational records without raw sensitive data. |
| Admin reconciliation endpoint | Shows local/provider mismatch counts and issue records without raw sensitive data. |
| Scheduled reconciliation incident storage | Detected mismatches create or update `payment_reconciliation_incidents`; repeated detections increment occurrence metadata. |
| Admin incident workflow | Admin can list incidents and change status to `ACKNOWLEDGED`, `RESOLVED`, or `IGNORED` from `/admin/payments` without mutating subscription/payment state. |
| Payment receipt evidence | After a successful staging charge, `GET /api/admin/payments/receipts` returns provider receipt evidence if Toss returned receipt fields, without raw card/provider payload data. |
| Payment operation audit log | After an admin incident status change, `GET /api/admin/payments/operation-audit-logs` returns the before/after status audit row. |
| Refund preview | For a refundable Toss billing subscription payment, `GET /api/admin/payments/refund-preview/{subscriptionPaymentId}` returns original, reserved, and remaining refundable amounts. |
| Refund request/approval | Admin creates and approves a refund request; `payment_refunds` and `payment_operation_audit_logs` record the workflow without calling Toss before execution. |
| Refund execution | Admin executes an approved refund after typed confirmation; Toss cancel is called with the stored idempotency key, the refund becomes `SUCCEEDED`, `FAILED`, or `PENDING_PROVIDER_CONFIRMATION`, and subscription entitlement is not automatically changed. |
| Entitlement correction preview/request | After a succeeded refund, admin previews and creates an explicit target subscription state; `payment_entitlement_corrections` stores before/target snapshots without mutating access yet. |
| Entitlement correction approval/execution | Admin approves and executes the correction after typed confirmation; `user_subscriptions` is updated to the explicit target state, optional local billing agreement cancellation is applied, and `payment_operation_audit_logs` records the workflow. |
| Settlement CSV import | Admin imports a valid settlement CSV; `payment_settlements` rows are created with `MATCHED`, `MISMATCHED`, or `LOCAL_PAYMENT_NOT_FOUND` status and no subscription/payment/refund/provider state changes. |
| Settlement missing-provider scan | Admin runs settlement reconcile for a selected period; local finalized payments without imported provider evidence create `PROVIDER_SETTLEMENT_NOT_FOUND` review rows unless provider evidence already exists. |
| Settlement ignore workflow | Admin ignores a verified settlement row with a note; the row becomes `IGNORED`, an audit row is recorded, and the original row remains queryable. |

## Remaining Development Points

These are not blockers for closing the current local/test payment feature. They are production operation items and should be split into future REQ/SR work.

| Priority | Item | Why it remains |
|---|---|---|
| P2 | Slack/SMS/in-app operator notifications | Email notification is optional; additional notification channels are future operations integrations. |
| P2 | Toss Settlement API adapter automation | CSV/manual settlement import is implemented first; direct provider settlement API import remains future if operations volume requires it. |
| P2 | Legacy endpoint removal | Remove blocked legacy routes only after stale clients and bookmarked callbacks are no longer a concern. |
| P3 | Multi-PG adapters | KakaoPay, Naver Pay, or additional PGs remain future provider-extension work. |
| Conditional | Tax invoice request workflow | On hold while ATStudio remains card-only recurring billing. Reopen only for approved B2B invoice, bank-transfer, postpaid, contract purchase, or institution purchase scope. |

Conditional infrastructure item: multi-server scheduler lock remains excluded while ATStudio runs as a single application server. Reopen it only before more than one application instance can execute renewal/reconciliation schedulers.
Cash receipt issue/cancel automation is excluded from the current next-step list while recurring billing remains card-only. Reopen it only if a cash-like payment method or a separate cash receipt request flow is approved.

## Close Criteria for Payment Feature Slice

The payment feature slice can be considered closed when the following remain true:

- User-facing subscription purchase uses recurring billing only.
- First subscription activation happens only after billing key issue and first charge success.
- Upgrade uses the active billing agreement instead of one-time checkout.
- Upgrade plus next-cycle selection shows the upgraded plan as active immediately and only the next billing cycle as pending.
- Scheduled lower-tier/cycle changes are pending-only and payment-free until renewal.
- Pending changes can be overwritten or cleared before renewal.
- User-facing cancellation can be reversed before expiresAt when the stored billing key remains valid.
- Account withdrawal stops local renewal before soft deletion, retries Provider cleanup without restoring charge eligibility, and never auto-refunds.
- Deleted, expired, or interrupted billing-key registrations can be recovered through zero-amount payment-method re-registration.
- Direct/mock-style subscription creation is blocked.
- Local/test validation passes across backend tests, frontend tests, typecheck, lint, build, and docs validation.
- Production-specific items above are tracked as SR-93 or future REQ/SR follow-up work.
