# SR-93 Toss 정기결제 운영 서버 체크포인트 및 개발 포인트

> Status: OPEN
> Created date: 2026-05-19
> Source REQ: REQ-20260519-ATS-001

## 목적

Toss 빌링키 기반 정기결제를 실제 운영 서버에 올리기 전에 필요한 설정, 검증, 운영 관측, 후속 개발 포인트를 정리한다.

## 운영 전환 체크포인트

- Toss test key와 live key를 환경별로 분리한다.
- `PAYMENT_BILLING_KEY_ENCRYPTION_SECRET`는 운영 환경변수 또는 안전한 secret manager로만 주입한다.
- 운영 서버에는 `app.payment.provider=TOSS_BILLING` 기준의 정기결제 구독 흐름을 사용한다.
- `application-local.yml` 같은 gitignored 로컬 설정은 운영 기준 문서로 사용하지 않는다.
- 프론트엔드 success/fail URL은 운영 도메인과 CORS 허용 origin에 맞춘다.
- 빌링키, authKey, customerKey, Toss secret key, raw provider payload는 사용자 화면, 운영 화면, 로그, 문서에 원문 노출하지 않는다.
- renewal scheduler가 운영에서 중복 실행되지 않도록 실행 주기와 idempotency 기준을 점검한다.
- 결제 실패 유예 정책은 기본 `3일 / 3회 재시도`로 시작하고, 실제 운영 데이터에 따라 조정한다.

## 개발 포인트

- 업그레이드 실패 시 payment order 실패 기록과 사용자 재시도 안내를 정리한다.
- 결제 성공 후 로컬 구독 변경 저장 실패에 대한 보상 취소/환불 runbook을 만든다.
- Toss webhook 또는 정기 reconciliation job을 추가해 provider 상태와 로컬 원장 상태를 대사한다.
- 운영자 read-only 결제 조회 화면을 추가한다.
- 환불, 영수증, 정산, 세금계산서, 관리자 결제 조작은 별도 REQ/SR로 분리한다.
- billing agreement 변경, 결제수단 재등록, 만료된 billing key 복구 흐름을 설계한다.
- 구독 취소와 자동 갱신 해지를 UI/문구/API 상태에서 명확히 구분한다.

## 수동 인수 테스트 후보

- 신규 구독: billing auth 성공 → 첫 결제 성공 → 구독 ACTIVE.
- 신규 구독 실패: billing auth 실패 또는 첫 결제 실패 → 구독 미생성.
- 업그레이드 성공: preview 확인 → 차액 결제 성공 → 플랜 즉시 변경, next billing date 유지.
- 업그레이드 실패: billing charge 실패 → 기존 플랜/기간 유지.
- 다운그레이드: preview 확인 → pending 저장 → 다음 renewal에서 하위 플랜 적용.
- 자동 갱신 해지: billing agreement CANCELLED → 현재 이용 기간 유지 → 다음 결제 미실행.
- renewal 실패: 실패 기록, failure count, grace period, 최종 SUSPENDED/EXPIRED 전환 확인.
