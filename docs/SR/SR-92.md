# SR-92 Toss 결제위젯 인라인 렌더링 UX 분리

> **우선 가치**: 현재 Toss 결제위젯이 구독 결제 페이지 본문에 인라인으로 렌더링되는 것은 Phase 2 결제 통합 검증을 위한 의도된 중간 형태다. 기능 버그로 즉시 제거하지 말고, 결제 안정화와 디버깅이 끝난 뒤 프로덕션 UX에 맞게 모달 또는 전용 checkout 단계로 분리한다.

## 환경

- 기기: PC
- OS: Windows 로컬 개발 환경
- 브라우저: Chrome 계열 테스트
- 페이지/경로: 구독 결제 화면 (`/subscriptions/payment`)
- 계정 상태: 일반 사용자 로그인 후 구독 결제 진행
- 결제 설정: Toss Payments test key, `app.payment.provider=TOSS`

## 배경

- 현재 구독 결제 화면은 Toss Payments 결제위젯을 페이지 본문에 직접 렌더링한다.
- 이 구조는 결제 준비 응답, 주문 번호, provider 상태, Toss widget 로딩 여부를 한 화면에서 확인하기 쉬워 로컬 통합 테스트와 디버깅에 유리하다.
- 실제 테스트에서도 결제 준비, 위젯 렌더링, Toss 테스트 결제창 진입까지 확인하는 데 도움이 되었다.
- 다만 일반 사용자는 보통 "결제하기" 버튼을 누른 뒤 별도 결제 팝업, 모달, 또는 checkout 단계에서 결제를 진행하는 UX를 기대한다.

## 현상

- Toss 결제수단/약관 UI가 구독 결제 페이지의 본문 영역에 크게 고정되어 보인다.
- 결제 페이지가 플랜 요약과 결제 진행 화면을 동시에 품고 있어, 사용자가 보기에는 Toss 화면이 페이지에 "박혀 있는" 느낌을 줄 수 있다.
- 하단 플레이어바 등 고정 UI가 있는 화면에서는 결제위젯 영역과 페이지 레이아웃이 시각적으로 복잡해질 수 있다.

## 현재 의도

- 현재 인라인 렌더링은 의도된 임시 구현이다.
- 목적은 다음과 같다.
  - Toss widget script 로딩 여부를 쉽게 확인한다.
  - `PaymentOrder` 상태, `orderId`, provider, amount를 화면에서 바로 확인한다.
  - success/fail redirect와 confirm API 문제를 한 화면에서 추적한다.
  - 결제 통합 초기 단계에서 브라우저 자동화 및 수동 테스트 비용을 낮춘다.
- 따라서 이 SR은 "즉시 버그 수정"이 아니라 "결제 안정화 후 UX 개선"으로 관리한다.

## 기대 동작

- 구독 결제 화면은 기본적으로 플랜 요약, 결제 금액, 결제 방식 선택, 결제 실행 버튼 중심으로 단순하게 보여준다.
- 사용자가 `토스 결제하기`를 누른 뒤 Toss 결제위젯을 모달, drawer, 또는 전용 checkout 단계에서 렌더링한다.
- 결제 진행 중에는 이탈 방지, 로딩, 실패, 취소, 재시도 상태가 명확해야 한다.
- Toss success/fail redirect 후에는 기존처럼 서버 confirm/cancel 처리를 수행하고, 성공 시 구독 관리 화면으로 이동한다.
- 개발/디버깅 모드에서는 필요하면 주문 번호와 provider 상태를 볼 수 있는 debug panel을 별도 토글로 제공한다.

## 수정 방향

### 1. 결제 페이지 구조 정리

- 기본 페이지에서는 Toss widget iframe을 바로 노출하지 않는다.
- `prepare` 응답은 내부 상태로 보관하되, 사용자가 결제 버튼을 누르기 전까지 widget 영역을 숨긴다.
- 결제 금액, 플랜, 결제 주기, 테스트 결제 안내는 유지한다.

### 2. Toss widget 표시 위치 분리

- 후보 A: 모달 안에서 Toss widget 렌더링
  - 장점: 사용자가 기대하는 결제창 UX에 가깝다.
  - 주의: Toss iframe 높이, 모바일 스크롤, 하단 플레이어바와의 z-index를 검증해야 한다.
- 후보 B: `/subscriptions/payment/checkout` 같은 전용 checkout route로 분리
  - 장점: redirect success/fail 상태와 history 처리가 단순하다.
  - 주의: 화면 전환이 늘어나므로 진행 상태 안내가 필요하다.
- 후보 C: 현행 인라인 유지 + 접힘 패널 처리
  - 장점: 구현 비용이 낮고 디버깅 편의성이 높다.
  - 주의: 프로덕션 UX 개선 효과는 제한적이다.

### 3. 디버깅 편의 유지

- `orderId`, provider, checkout type, amount는 개발 모드에서 확인 가능해야 한다.
- 운영 화면에는 내부 주문 메타 정보를 과도하게 노출하지 않는다.
- 결제 실패 시 사용자 메시지와 개발자용 원인 정보를 분리한다.

## 지금 당장 수정하지 않는 이유

- 현재는 Toss one-time payment 통합 안정화와 정기결제 설계/구현 전환이 더 우선이다.
- 인라인 렌더링은 기능상 정상이며, 결제 준비와 위젯 로딩 문제를 추적하는 데 실질적으로 유용하다.
- 결제창 UX를 먼저 바꾸면, 아직 안정화 중인 Toss confirm, redirect, 재구독 처리 문제를 디버깅하기 어려워질 수 있다.
- 따라서 이 항목은 결제 핵심 플로우 안정화 후 독립 SR/커밋으로 분리해 처리한다.

## 확인 사항

- Toss widget을 모달 안에 렌더링해도 결제수단 선택, 약관 동의, requestPayment가 정상 동작하는지 확인한다.
- 모바일 viewport에서 모달 내부 스크롤과 하단 플레이어바 overlap 여부를 확인한다.
- success/fail redirect 후 기존 주문 상태가 idempotent하게 처리되는지 확인한다.
- `localhost`와 외부 테스트 URL(ngrok 등)에서 success/fail URL 설정이 일관되는지 확인한다.

## 비고

- 현재 구현은 기능 검증용으로 의도된 상태이며, 사용자 경험 관점에서는 개선 대상이다.
- 이 SR은 결제 로직 변경이 아니라 checkout presentation layer 개선으로 분리한다.
- 결제 도메인 안정화가 끝난 뒤 진행하는 것이 적절하다.
