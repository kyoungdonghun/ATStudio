# SR-95 태그 이름 공백·특수문자 입력 규칙 정립
> **우선 가치**: 음악 장르·분위기·악기·용도 이름의 실제 표기 가능성을 보존하면서 검색과 중복 판정에 일관된 입력 규칙을 적용한다. 이 SR은 권고안과 후속 결정 항목을 기록하며, 허용 문자 집합을 최종 확정하거나 즉시 구현하지 않는다.

## 환경

- 관리자 태그 관리 화면
- 태그 생성 및 수정
- PC, 모바일 공통

## 현재 확인된 동작

- 프론트엔드는 이름 입력 시 최대 50자만 제한하고, 제출 직전에 `trim()`을 적용함.
- 프론트엔드에는 태그 이름의 내부 공백, 연속 공백, 특수문자를 검사하는 규칙이 없음.
- 백엔드는 `@NotBlank`와 최대 50자 제한을 적용하지만, 공백 정규화나 허용 문자 패턴은 적용하지 않음.
- 백엔드 서비스는 전달받은 이름을 그대로 중복 조회하고 저장함.
- DB의 태그 이름은 태그 유형과 무관하게 전역 `unique`임.
- 따라서 앞뒤 공백은 현재 관리자 화면 제출에서는 제거되지만, 직접 API 호출과 다른 클라이언트까지 포함한 일관된 정규화 계약은 없음.

## 외부 음악 서비스 사례

- [Splice의 공식 장르 목록](https://splice.com/sounds/genres)에는 `Hip Hop / R&B`, `Lo-Fi Hip Hop`, `Synth-Pop`, `K-Pop`, `Afropop & Afrobeats`처럼 내부 공백, 슬래시(`/`), 앰퍼샌드(`&`), 하이픈(`-`)이 포함된 장르명이 있음.
- [Splice의 공식 사운드 검색 도움말](https://support.splice.com/en/articles/8652594-finding-sounds)은 키워드와 장르·악기 태그를 이용한 검색을 안내하며, 장르 예시로 `hip-hop`을 사용함.
- [Epidemic Sound의 공식 장르 목록](https://www.epidemicsound.com/music/genres/)에는 `R&B`, `Brass & Marching Band`, `Electro-Funk`, `Electronic Dance Music (EDM)`, `Euro-Trance`, `Children’s Music`, `2-Step`처럼 공백, 앰퍼샌드, 하이픈, 괄호, 아포스트로피, 숫자가 포함된 이름이 있음.
- 이 사례는 모든 특수문자를 허용해야 한다는 근거가 아니라, 음악 분류 이름에 필요한 문장부호를 일괄 금지하면 정상적인 표기를 훼손할 수 있다는 근거로 사용함.

## 권고안

### 1. 공백 정규화

- 앞뒤 공백은 프론트엔드와 백엔드 모두에서 제거함.
- 단어 사이의 공백은 장르명과 용도명의 자연스러운 표기를 위해 허용함.
- 연속된 내부 공백은 하나의 일반 공백으로 정규화하는 방안을 우선 권고함.
- 줄바꿈, 탭, 제어 문자는 태그 이름에서 허용하지 않는 방향을 권고함.
- 중복 비교와 저장에는 동일하게 정규화된 값을 사용하여 `Hip Hop`, ` Hip Hop `, `Hip  Hop`이 서로 다른 태그로 취급되지 않도록 함.
- 최대 50자 검사는 정규화된 최종 값 기준으로 프론트엔드와 백엔드가 동일하게 적용하는 방안을 권고함.

### 2. 허용 문자 정책

- 한글, 영문자, 숫자, 내부 공백을 기본 허용 문자로 권고함.
- 모든 특수문자를 포괄 허용하거나 일괄 금지하지 않고, 실제 음악 분류 표기에 필요한 문장부호 allowlist를 설계함.
- 초기 검토 후보는 하이픈(`-`), 앰퍼샌드(`&`), 슬래시(`/`), 아포스트로피(`'`, `’`), 괄호(`(`, `)`)임.
- allowlist 밖의 문자는 저장 전에 필드 단위 안내를 제공하고, 백엔드도 같은 규칙으로 검증함.
- `#`는 용도 태그의 화면 표시용 접두사인지 저장 이름의 일부인지 먼저 확인한 뒤 허용 여부를 결정함.

### 3. 적용 원칙

- 프론트엔드 규칙은 빠른 입력 안내를 제공하고, 백엔드 규칙은 모든 클라이언트에 적용되는 최종 계약으로 유지함.
- 생성과 수정에 같은 정규화·검증 함수를 적용함.
- 중복 확인은 정규화 이후 수행함.
- 기존 데이터에 정규화 후 충돌하는 이름이 있는지 조사한 뒤 저장 규칙을 적용함.
- 사용자에게는 허용 규칙과 수정 방법을 입력 필드 가까이에서 구체적으로 안내함.

## 후속 설계에서 결정할 사항

- [ ] 대소문자를 중복 판정에서 동일하게 볼지 여부
- [ ] Unicode 정규화 형식과 전각·호환 문자의 처리 방식
- [ ] 문장부호 allowlist의 최종 목록과 문자별 사용 목적
- [ ] `#`를 저장 값으로 허용할지, 화면에서만 붙일지 여부
- [ ] 현재의 전역 유일성을 유지할지, 태그 유형별 동일 이름을 허용할지 여부
- [ ] 정규화 적용 전 기존 태그 데이터의 충돌·마이그레이션 필요 여부

## 완료 조건

- [ ] 승인된 공백 정규화와 문자 allowlist가 프론트엔드·백엔드의 단일 규칙으로 문서화됨.
- [ ] 생성·수정·직접 API 호출에 같은 정규화와 검증 결과가 적용됨.
- [ ] 앞뒤 공백, 내부 단일 공백, 연속 공백, 허용 문장부호, 미허용 문자에 대한 테스트가 포함됨.
- [ ] 정규화된 값 기준의 중복 생성·수정 테스트가 포함됨.
- [ ] 기존 데이터 충돌 여부와 DB 유일성 범위가 구현 전에 확인됨.
