# SR-97 관리자 구독 편집의 플랜 선택과 상태·만료일 정합성 보강
> **우선 가치**: 관리자 구독 편집은 화면에 보이는 상태만 바꾸는 기능이 아니라 접근 권한, 예약 변경, 정기결제와 감사 근거에 영향을 주는 운영 작업이다. 플랜·주기·상태·만료일을 하나의 목표 상태로 검증하고, 로컬 권한 보정과 실제 결제·환불을 구분한다.

## 환경

- 관리자 페이지 > 사용자 구독 관리
- 구독 상태, 결제 주기, 만료일 편집
- PC, 모바일 공통

## 인수 테스트에서 확인된 현상

- 구독 상태를 `ACTIVE`, `CANCELLED`, `EXPIRED` 중에서 선택하고 결제 주기와 만료일을 수정할 수 있음.
- 플랜 목록 데이터는 불러오지만 현재 플랜을 변경할 선택지는 없음.
- `EXPIRED` 상태와 미래 만료일처럼 의미가 충돌하는 값을 화면에서 선택할 수 있음.

## 현재 계약과 저장 동작

| 구분 | 현재 동작 | 판단 |
| --- | --- | --- |
| 프론트엔드 | 플랜 목록을 조회하지만 대기 플랜 이름 표시에만 사용함. 수정 모달에는 현재 플랜 선택 필드가 없음 | 현재 플랜 변경 불가 |
| API | 관리자 수정 요청은 `status`, `billingCycle`, `expiresAt`만 받으며 `subscriptionId`가 없음 | 플랜 변경 계약 없음 |
| 백엔드 저장 | 전달된 상태·주기·만료일을 서로 독립적으로 대입하고 관계 검증을 하지 않음 | 모순 조합 저장 가능 |
| 예약 변경 | 현재 플랜과 별도의 대기 플랜·주기를 그대로 남김 | 관리자 수정이 다음 갱신에서 덮어써질 수 있음 |
| 결제 연계 | 빌링 약정, 다음 결제일, 진행 중 결제 주문, 외부 결제 상태를 확인하거나 바꾸지 않음 | 내부 표시와 결제 운영 상태가 어긋날 수 있음 |
| 감사 | 일반 수정 경로에 행위자·사유·전후 상태 감사 계약이 없음 | 운영 보정 근거 부족 |

현재 화면에서는 **플랜을 변경할 수 없으며**, 기존 [SR-14](SR-14.md)가 요구한 구독 상품 변경 부분은 이 경로에 구현되지 않은 상태임.

## 상태와 만료일 규칙 제안

`today`는 서버의 동일한 업무 시간대와 `Clock`을 기준으로 계산하고, 프론트엔드 검사는 안내용으로만 사용함.

| 목표 상태 | 허용 만료일 | 처리 원칙 |
| --- | --- | --- |
| `ACTIVE` | `expiresAt >= today` | 과거 날짜는 거절함. 자동 갱신 가능 여부는 빌링 약정과 별도로 표시·검증함 |
| `CANCELLED` | `expiresAt >= today` | 오늘 또는 미래는 결제한 기간까지 접근하는 정상 유예 기간으로 허용함 |
| `EXPIRED` | `expiresAt <= today` | 미래 날짜는 의미가 충돌하므로 거절함. 대기 변경과 빌링 약정 처리 방침을 함께 결정함 |

- 사용자가 지적한 `EXPIRED` + 미래 만료일은 백엔드에서 거절해야 함.
- `ACTIVE` 또는 `CANCELLED` + 과거 만료일도 거절하거나 명시적으로 `EXPIRED`로 전환하는 승인된 규칙이 필요함. 설명 없이 자동 보정하지 않음.
- **`CANCELLED` + 오늘 또는 미래 만료일은 오류가 아님.** 현재 서비스는 취소 후 만료일까지 접근 권한을 유지하는 유예 기간으로 사용함.
- `EXPIRED` 선택 시 만료일을 오늘로 제안할 수 있지만, 사용자가 입력한 미래 날짜를 조용히 덮어쓰지 말고 필드 단위로 이유를 안내함.
- 빈 변경 요청과 실제로 달라지는 값이 없는 요청은 안정적인 오류 또는 명시적인 `NO_CHANGE` 결과로 처리하여 운영자가 성공으로 오인하지 않도록 함.

## 플랜 변경 개선안

### 대안 A. 현재 빠른 수정 모달에 플랜 선택 추가

- 현재 플랜 선택지를 추가하고 요청 계약에 목표 플랜 ID를 포함함.
- 대상 플랜이 활성 상태인지, 사용자의 `userType`과 일치하는지 백엔드가 최종 검증함.
- 현재·대기 플랜과 주기, 목표 상태와 만료일, 빌링 약정, 다음 결제일을 한 화면에서 미리 보여 줌.
- 대기 변경을 유지할지 제거할지, 로컬 빌링 약정을 유지할지 취소할지 명시적으로 선택함.
- 구독과 빌링 약정을 잠그고, 결과가 확정되지 않은 구독·업그레이드·갱신 주문이 있으면 변경을 막으며, 행위자·사유·전후 상태를 감사함.

이 조건 없이 셀렉트와 DB 필드 변경만 추가하면 다음 정기결제 플랜·금액·주기가 결제 근거 없이 달라질 수 있음.

### 대안 B. 일반 관리자 권한 보정 흐름으로 분리 — 권고

- 현재 결제 운영 화면의 환불 연계 권한 보정이 사용하는 목표 플랜·주기·상태·만료일, 대기 변경 제거, 로컬 빌링 약정 취소, 미리보기, 잠금, 승인·실행, 감사 패턴을 재사용함.
- 환불이 없는 고객지원·운영 교정도 지원 티켓이나 사고 번호와 함께 처리할 수 있도록 별도의 일반 권한 보정 흐름으로 확장함.
- 사용자 구독 화면의 빠른 수정은 검증된 상태·날짜 보정만 남기거나, 새 보정 흐름으로 이동하는 진입점으로 바꿈.
- 이 작업은 **로컬 구독 권한 보정**이며 외부 결제, 환불, 결제수단 해지가 자동 실행되는 일반 유료 플랜 변경이 아님을 확인 화면과 결과에 명시함.

단순한 플랜 셀렉트보다 대안 B를 우선 권고함. 플랜을 고를 수 있게 하되, 결제와 분리된 관리자 보정이라는 경계와 감사 근거를 보존할 수 있기 때문임.

## 수정 내용

### 1. 상태·날짜 검증

- 위 상태·만료일 행렬을 백엔드의 최종 규칙으로 적용하고 프론트엔드에서 같은 메시지로 사전 안내함.
- 상태, 주기, 만료일을 독립 필드 패치로 보지 않고 현재·목표 구독 상태 전체를 검증함.
- 예약된 플랜·주기 변경이 있으면 현재 값과 함께 표시하고 유지·제거 결과를 확인받음.

### 2. 플랜과 결제 경계

- 플랜 변경을 제공하면 활성 플랜과 사용자 유형에 맞는 플랜만 선택 가능하게 하고 서버가 다시 검증함.
- 즉시 로컬 권한 보정, 다음 결제 시 예약 변경, 차액 결제 기반 업그레이드를 서로 다른 작업으로 구분함.
- 관리자 로컬 보정은 외부 결제사업자의 결제·환불·빌링 키 삭제를 암묵적으로 실행하지 않음.
- 외부 결제 동작이 필요하면 기존 결제 명령·환불 흐름을 별도로 사용하고, 화면의 확인 문구, API 호출, 결제사업자 결과, 저장 상태를 각각 기록함.

### 3. 동시성·확인·감사

- 구독과 빌링 약정을 정해진 순서로 잠그고 적용 전 상태를 다시 확인함.
- 결과가 확정되지 않은 결제 주문이 있으면 보정을 차단함.
- 저장 전에 현재 상태, 목표 상태, 대기 변경, 로컬 빌링 약정 처리, 외부 결제 비실행 범위를 미리 보여 줌.
- 운영 사유를 필수로 받고 행위자, 대상 사용자·구독 ID, 전후 상태, 결과, 서버 시각을 감사 로그에 남김.

## 완료 조건

- [ ] 현재 플랜 변경이 불가능한 화면과 API 계약이 명확히 정리됨.
- [ ] `EXPIRED` + 미래 만료일, `ACTIVE`/`CANCELLED` + 과거 만료일이 백엔드에서 거절되고 필드 단위 안내가 표시됨.
- [ ] `CANCELLED` + 오늘/미래 만료일이 정상 유예 기간으로 허용되고 접근 권한 회귀 테스트가 있음.
- [ ] 플랜 변경을 제공할 경우 활성 플랜과 사용자 유형이 맞는 선택지만 제시되고 서버에서도 검증됨.
- [ ] 플랜·주기·상태·만료일·대기 변경·빌링 약정의 현재값과 목표값을 저장 전에 함께 확인할 수 있음.
- [ ] 대기 변경의 유지·제거와 로컬 빌링 약정의 유지·취소가 명시적인 선택으로 처리됨.
- [ ] 진행 중 결제 주문과 동시 수정이 잠금·재검사로 차단됨.
- [ ] 로컬 권한 보정이 외부 결제·환불·빌링 키 삭제를 자동 수행하지 않는다는 경계가 표시되고 검증됨.
- [ ] 운영 사유, 행위자, 전후 상태와 결과가 감사 로그에 남음.

## 후속 설계에서 결정할 사항

- [ ] 빠른 수정 모달을 제한적으로 유지할지, 모든 비단순 변경을 일반 권한 보정 흐름으로 통합할지
- [ ] 일반 권한 보정에 단일 운영자 재확인과 요청자·승인자 분리 중 어떤 승인 수준을 적용할지
- [ ] 플랜 변경이 즉시 로컬 권한 보정인지, 다음 결제 예약인지, 차액 결제 작업인지 화면별로 어떤 범위를 허용할지
- [ ] 업무 기준 시간대와 경계일 `today` 처리 규칙
