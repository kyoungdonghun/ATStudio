## INFO-001: 회원가입

| 항목 | 내용 |
|------|------|
| **코드** | INFO-001 |
| **버전** | 26-02-20 |
| **설명** | 비회원이 회원가입을 한다. |
| **액터** | 사용자(비회원), 백엔드 시스템 |
| **사전 조건** | 미등록 이메일, 미등록 전화번호, 미사용 닉네임이어야 함. |
| **트리거** | 사용자가 '로그인' 화면에서 '회원가입' 버튼을 클릭한다. |
| **관련 UC** | UTIL-002(이메일 중복), UTIL-003(전화번호 중복), UTIL-012(닉네임 중복), INFO-008(로그인), INFO-013(소셜 로그인) |

**기본 흐름**
1. 사용자가 회원가입 화면으로 이동한다.
2. 사용자가 메타데이터(닉네임, 이메일, 비밀번호, 개인 전화번호, 직업, 회원 유형)를 입력한다.
3. 프론트엔드가 실시간으로 입력값 유효성 검증을 수행한다.
4. 사용자가 이메일, 전화번호, 닉네임 각각의 '중복 체크' 버튼을 클릭한다.
   - 이메일: UTIL-002, 전화번호: UTIL-003, 닉네임: UTIL-012 호출
5. 모든 중복 체크가 완료되면 '회원가입' 버튼이 활성화된다.
6. 사용자가 '회원가입' 버튼을 클릭한다.
7. 프론트엔드가 입력값을 백엔드에 전송한다.
8. 백엔드가 서버 유효성 검사를 수행한다.
9. 백엔드가 비밀번호를 BCrypt로 해시하여 users 테이블에 저장(is_verified=0)한다.
10. 백엔드가 성공 응답(201 Created)을 반환하고, 프론트엔드는 '로그인' 화면으로 이동한다.

**예외/대안 흐름**
- 소셜 로그인: INFO-013 참조.

**사후 조건**
- users 테이블에 레코드가 생성됨. 로그인 가능 상태.

## INFO-008: 로그인

| 항목 | 내용 |
|------|------|
| **코드** | INFO-008 |
| **버전** | 26-02-20 |
| **설명** | 회원이 이메일/비밀번호로 로그인하여 Access Token과 Refresh Token을 발급받는다. |
| **액터** | 사용자(회원), 백엔드 시스템 |
| **사전 조건** | users 테이블에 해당 이메일로 등록된 계정 존재. is_deleted=0. |
| **트리거** | 사용자가 '로그인' 버튼을 클릭한다. |
| **관련 UC** | UTIL-004(토큰 재발급), INFO-013(소셜 로그인) |

**기본 흐름**
1. 사용자가 이메일과 비밀번호를 입력하고 '로그인' 버튼을 클릭한다.
2. 프론트엔드가 이메일, 비밀번호를 백엔드에 전송한다.
3. 백엔드가 이메일로 사용자를 조회하고 BCrypt 비밀번호를 검증한다.
4. 백엔드가 Access Token(단기)과 Refresh Token(장기)을 발급한다.
5. 백엔드가 토큰 정보(accessToken, refreshToken, tokenType, expiresIn)를 반환한다.
6. 프론트엔드가 Access Token을 메모리에 저장하고, Refresh Token을 httpOnly 쿠키에 저장한다.

**예외/대안 흐름**
- 이메일 미존재 또는 비밀번호 불일치: 401 응답.
- 탈퇴 처리된 계정(is_deleted=1): 403 응답.

**사후 조건**
- Access Token, Refresh Token이 정상 발급됨. 이후 인증 필요 API에서 Bearer 토큰으로 사용 가능.

## INFO-013: 소셜 로그인 [신규]

| 항목 | 내용 |
|------|------|
| **코드** | INFO-013 |
| **버전** | 26-02-20 |
| **설명** | 사용자가 소셜 계정(Google/Kakao/Naver)으로 로그인한다. 최초 로그인 시 최소 레코드 생성 후 프로필 완성 단계(INFO-014)로 안내. |
| **액터** | 사용자, 소셜 OAuth 서버, 백엔드 시스템 |
| **사전 조건** | - |
| **트리거** | 사용자가 소셜 로그인 버튼(Google/Kakao/Naver)을 클릭한다. |
| **관련 UC** | INFO-008(로그인), INFO-014(소셜 프로필 완성) |

**기본 흐름**
1. 사용자가 소셜 로그인 버튼을 클릭한다.
2. 프론트엔드가 OAuth 인증 코드(authorizationCode)를 취득한다.
3. 프론트엔드가 provider, authorizationCode를 백엔드에 전송한다.
4. 백엔드가 소셜 서버에서 사용자 정보(이메일, 이름 등)를 조회한다.
5. social_accounts 테이블에서 (provider, provider_id) 기존 연결 여부를 확인한다.
6. 기존 연결 있음: 해당 사용자로 로그인 처리. isProfileComplete=true. Access/Refresh Token 발급 후 반환.
7. 기존 연결 없음 (신규 가입):
   a. 최소 정보(이메일, 소셜 이름)만으로 users 레코드 생성 (password=NULL, phonePersonal=NULL, job=NULL 허용).
   b. social_accounts 레코드 생성 및 연결.
   c. Access/Refresh Token 발급.
   d. 응답에 isProfileComplete=false 포함하여 반환.
8. 프론트엔드가 isProfileComplete=false 확인 시 INFO-014(소셜 프로필 완성) 화면으로 이동.

**사후 조건**
- 토큰 발급 완료.
- 신규 사용자인 경우 users(최소 정보), social_accounts 레코드 생성됨. isProfileComplete=false.
- 기존 사용자인 경우 isProfileComplete=true.

## INFO-014: 소셜 회원 프로필 완성 [신규]

| 항목 | 내용 |
|------|------|
| **코드** | INFO-014 |
| **버전** | 26-02-20 |
| **설명** | 소셜 로그인으로 최초 가입한 회원이 필수 프로필 정보(닉네임, 전화번호, 직업, 회원 유형)를 입력하여 프로필을 완성한다. |
| **액터** | 사용자(신규 소셜 가입자), 백엔드 시스템 |
| **사전 조건** | 로그인 상태. users 레코드가 존재하고 isProfileComplete=false 상태. |
| **트리거** | INFO-013에서 isProfileComplete=false 응답 수신 후 프론트엔드가 자동으로 프로필 완성 화면으로 이동한다. |
| **관련 UC** | INFO-013(소셜 로그인), UTIL-003(전화번호 중복 확인), UTIL-012(닉네임 중복 확인) |

**기본 흐름**
1. 프론트엔드가 프로필 완성 화면을 출력한다.
2. 사용자가 닉네임(필수), 개인 전화번호(필수), 직업(필수), 회원 유형(INDIVIDUAL/BUSINESS, 필수)을 입력한다.
3. 프론트엔드가 UTIL-003(전화번호 중복), UTIL-012(닉네임 중복) 확인을 수행한다.
4. 사용자가 '완료' 버튼을 클릭한다.
5. 프론트엔드가 인증 토큰과 프로필 정보를 `PUT /api/users/me/complete-profile`로 백엔드에 전송한다.
6. 백엔드가 isProfileComplete=false 여부를 확인한다.
7. 백엔드가 users 레코드(nickname, phonePersonal, job, userType)를 업데이트한다.
8. 백엔드가 수정된 사용자 정보를 반환한다 (5.4 내 정보 보기와 동일 형식).
9. 프론트엔드가 메인 화면으로 이동한다.

**예외/대안 흐름**
- 닉네임 중복: UTIL-012에서 available=false 반환. 재입력 요청.
- 전화번호 중복: UTIL-003에서 available=false 반환. 재입력 요청.

**사후 조건**
- users 레코드에 필수 프로필 정보가 저장됨. 이후 isProfileComplete=true 상태.

## INFO-005: 내 정보 수정

| 항목 | 내용 |
|------|------|
| **코드** | INFO-005 |
| **버전** | 26-02-20 |
| **설명** | 회원이 본인의 정보를 수정한다. 수정 가능 필드: nickname, phonePersonal, phoneCompany, job. |
| **액터** | 사용자(회원), 백엔드 시스템 |
| **사전 조건** | 로그인 상태. |
| **트리거** | 사용자가 '내 정보' 화면에서 '정보 수정' 버튼을 클릭한다. |
| **관련 UC** | UTIL-012(닉네임 중복 확인) |

**기본 흐름**
1. 사용자가 수정할 필드(nickname, phonePersonal, phoneCompany, job)를 변경 입력한다.
2. 프론트엔드가 실시간 유효성 검증을 수행한다.
3. nickname을 변경하는 경우, UTIL-012(닉네임 중복 확인)를 통해 중복 체크를 수행한다.
4. 사용자가 '수정 완료' 버튼을 클릭한다.
5. 프론트엔드가 변경 데이터를 백엔드에 전송한다.
6. 백엔드가 유효성 검사 수행 후 users 레코드를 업데이트한다.
7. 수정된 내 정보를 반환하고 화면에 출력한다.

**예외/대안 흐름**
- 닉네임 중복: UTIL-012에서 available=false 반환.

**사후 조건**
- 변경된 정보가 DB에 반영됨. 화면에 수정된 내 정보가 표시됨.

> **주의**: email, userType은 수정 불가.

## INFO-007: 회원탈퇴 (본인)

| 항목 | 내용 |
|------|------|
| **코드** | INFO-007 |
| **버전** | 26-02-20 |
| **설명** | 회원이 본인 계정을 탈퇴한다. 논리적 삭제(is_deleted=1). |
| **액터** | 사용자(회원), 백엔드 시스템 |
| **사전 조건** | 로그인 상태. |
| **트리거** | 사용자가 '내 정보' 화면에서 '회원 탈퇴' 버튼을 클릭한다. |
| **관련 UC** | - |

**기본 흐름**
1. 사용자가 '회원 탈퇴' 버튼을 클릭한다.
2. 프론트엔드가 탈퇴 고지사항 화면을 출력한다.
3. 사용자가 비밀번호를 입력하고 '확인' 버튼을 클릭한다.
4. 프론트엔드가 비밀번호를 포함한 탈퇴 요청을 백엔드에 전송한다.
5. 백엔드가 비밀번호를 검증한다.
6. 백엔드가 users.is_deleted=1로 업데이트한다. (논리적 삭제. 물리적 삭제 아님.)
7. 백엔드가 204 No Content를 반환한다. 프론트엔드가 로그아웃 처리 후 메인 화면으로 이동한다.

**예외/대안 흐름**
- 비밀번호 불일치: 401 응답.

**사후 조건**
- users.is_deleted=1로 갱신됨. 해당 계정으로 로그인 불가.
