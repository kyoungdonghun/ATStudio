## Verified Contract

### Schema And Consent Persistence

- Static DDL equality passed for `user_consents` between
  `src/main/resources/schema.sql:113-125` and
  `scripts/database/patches/WI-20260809-ATS-068-user-consents.sql:4-16`.
- The schema has 43 `CREATE TABLE` statements and the entity source has 43
  `@Entity` types. The bootstrap source expectation is 43
  (`scripts/database/DisposableMysqlBootstrap.java:49-51`).
- `UserConsent` maps the table, identity key, non-null user FK, enum, version,
  immutable agreement time, and the `(user_id, consent_type, policy_version)`
  uniqueness contract (`UserConsent.java:26-72`). The latter permits later
  policy versions while rejecting duplicate evidence for the same user/type/
  version.
- Required Terms and Privacy are separately checked; Marketing is recorded
  only for `Boolean.TRUE` (`UserService.java:444-464`). Policy version is taken
  from server configuration (`ConsentPolicyProperties.java:15-29`), and time
  is server-generated by `@CreationTimestamp` with an SQL default fallback.
  No client timestamp, policy body, IP, device, or negative-marketing record is
  added.
- The registration method is transactional and saves the user then its consent
  evidence in the same transaction (`UserService.java:75-107`).

### Authentication And Frontend Session Handling

- Password login obtains the authenticated user and checks verification before
  either access or refresh token generation; refresh checks verification before
  token rotation (`AuthService.java:39-56`, `78-112`).
- Focused backend tests assert no generator invocation for unverified password
  login or refresh (`AuthServiceTest.java:79-99`, `297-315`).
- The fixed `EMAIL_VERIFICATION_REQUIRED` login path makes no `fetchMe` call,
  makes no auth-store login call, and suppresses private diagnostics
  (`LoginPage.test.tsx:261-284`). Signup only calls registration and navigates
  to email verification; it does not stage or persist credentials
  (`SignupPage.tsx:163-177`).

### Logout

- Only a `204` response is `confirmed`; every non-204, bare `401`, and thrown
  request becomes `unconfirmed` (`frontend/src/api/auth.ts:164-171`,
  `auth.test.ts:16-48`).
- The store coalesces concurrent requests, awaits revocation, then clears every
  local credential and user-dependent store in `finally`
  (`authStore.ts:149-180`). Store tests cover confirmed, unconfirmed, and
  coalesced outcomes (`authStore.test.ts:340-397`).
- Header and ADMIN callers await the safe outcome, block a duplicate click, and
  show the fixed accessible warning when unconfirmed
  (`Header.tsx:194-207`, `AdminLayout.tsx:259-272`, corresponding layout
  tests). The selected frontend suite passed all 69 tests.
