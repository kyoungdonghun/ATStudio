## P1 Findings And Exact Corrections

### P1-1: Consent identity is ambiguous at unauthenticated signup

The decision record calls the consent subject an "authenticated user identity" but does not define how an unauthenticated signup can supply one. Current registration is an unauthenticated `POST /api/users` and creates the `User` inside `UserService.register`; requiring an existing authenticated-session principal would be impossible and could disconnect consent from the account.

**Correct Section 3.1 by adding:**

> During signup, the server must first create or obtain the newly created account's persistent user ID, then associate each required consent record with that user ID in the same transaction. "Authenticated user identity" in the approved policy means that persisted account identity, not a pre-login `SecurityContext`, access token, refresh token, or `/users/me` identity.

This clarification adds no field and no additional retention.

### P1-2: Policy-version and agreement-time semantics are incomplete

Section 3.1 names category, document version, and agreement timestamp but does not define their authoritative source. Without that boundary, a client-supplied or mutable version/time could be recorded as consent evidence even though the record says server-side persistence is authoritative.

**Correct Section 3.1 by adding:**

> The consent category and immutable policy/document version must identify the exact policy presented and accepted. The agreement timestamp must be generated by the server when that acceptance is persisted in the signup transaction; it is not a client-supplied value and is not rewritten by later reads or login. This selects no timestamp precision, time zone representation, schema layout, or retention period.

### P1-3: A bare `401` is incorrectly elevated to confirmed revocation

The approved policy makes `204` and a **confirmed invalid/revoked session** terminal success. Decision-register Section 3.4 instead states "`401` or a confirmed invalid/revoked session" and Section 6 repeats "confirmed `401`/revoked". That wording permits an unclassified `401` to produce no warning and claim confirmed server revocation. The current frontend helper does exactly that for every Axios `401`; it has no response classification.

**Replace the Section 3.4 second outcome row and align Section 6 with:**

> A `401` is terminal success only when the logout contract confirms that it means an already-invalid or revoked session. A bare or otherwise unclassified `401`, and every other settled network/server failure, is local-only logout completion: clear local state, navigate away, and show the server-revocation-could-not-be-confirmed notice. Do not claim confirmed server revocation for that outcome.

This preserves the approved hybrid server-first policy and makes notice truthfulness testable without selecting a new error code or API shape.

## Verified Preserved Boundaries

- Separate Terms and Privacy consent, with optional independent marketing, remains the only selected consent scope. An affirmative marketing agreement may be recorded; declining it requires no negative-consent record.
- The verified-only invariant already covers password, refresh, restored local state, and social token issuance. Social-provider authentication is not application verification or consent; current code demonstrates the gap, but the decision record correctly frames it as future work rather than current behavior.
- `returnTo` is bounded to same-application pathname and query, rejects the stated unsafe classes, and is re-authorized against the post-login role and user type. Current frontend normalization and fallback are accurately described as observed behavior, not proof of server authorization.
- The logout policy requires a single awaited, coalesced settlement; local clear follows every settled outcome; only confirmed outcomes may be reported as server revocation. The record accurately identifies that current Header and Admin callers do not await and that the auth store does not coalesce logout.
