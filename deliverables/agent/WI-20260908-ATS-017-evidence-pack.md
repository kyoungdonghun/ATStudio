## Findings
### F1 [P1] Track soft deletion permanently erases issued licenses and history
- Location: `src/main/java/com/atstudio/atstudio/service/TrackService.java:221-228`, specifically `trackDownloadRepository.deleteAllByTrack(track)` at 222 and `licenseRepository.deleteAllByTrack(track)` at 223.
- Trigger: an ADMIN deletes a Track with existing member downloads through `DELETE /api/tracks/{trackId}`. `frontend/src/pages/admin/TrackManagePage.tsx:195` sends this request; its confirmation at 377-378 explicitly describes deactivation.
- Impact: every member's persisted license code and download history for that Track is physically removed. Reactivating the retained Track cannot restore those records; a later download becomes a new quota/entitlement decision. Deleting same-day history also reduces the quota count in `src/main/java/com/atstudio/atstudio/service/DownloadService.java:63-68` via `repository/TrackDownloadRepository.java:18-20` under the same Java package: already-consumed daily slots become available for OTHER first downloads. Older-day history deletion does not change today's count. This is not merely hiding inactive Tracks from public lists.
- Defenses checked: ADMIN-only controller/security rules, confirmation and duplicate-submit fencing, retained media, and one transaction. None prevents these deletes on successful commit. `LicenseRepository.java:25` in `src/main/java/com/atstudio/atstudio/repository/` is an actual derived delete, not a status update.
- Requirement/test mismatch: `docs/design/usecase/sound-track.md:306-326` specifies soft deletion plus tag cleanup; `user-license.md:28-48` preserves access to previously issued licenses. `src/test/java/com/atstudio/atstudio/service/TrackServiceTest.java:674-694` checks deactivation/storage untouched/tag cleanup but never checks license/history retention.
- Minimal recommendation: preserve issued entitlement/history during soft deletion; hold this workflow pending separately approved correction. Code-confirmed path and quota consequence; no existing user record was inspected or deleted, and runtime impact was not reproduced.

### F2 [P1] Normal Playlist/Album deletion makes a later strict startup fail
- Location: `src/main/java/com/atstudio/atstudio/service/PlaylistService.java:268-272` retains the parent thumbnail key while deactivating and scheduling its physical deletion. Brief Album analog check confirms the same behavior at `src/main/java/com/atstudio/atstudio/service/AlbumService.java:139-145`; `entity/Album.java:53-55` under the same Java package changes only `isActive`. This is one shared defect, not a separate finding.
- Trigger: a subscriber deletes an owned Playlist, or an authorized Album deletion occurs, with an uploaded, unshared thumbnail; after-commit cleanup succeeds; the same DB/media tuple is subsequently started with the required strict audit.
- Causal chain: `src/main/java/com/atstudio/atstudio/service/storage/StorageReferenceChecker.java:25-32` excludes inactive Playlists/Albums, so `StorageCleanupService.java:28-37` removes the file. `StorageIntegrityService.java:50-53` nevertheless audits both repositories with `findAll()`, including inactive parents and their retained keys. `src/main/java/com/atstudio/atstudio/config/StorageIntegrityStartupGuard.java:32-49` then rejects startup for the missing reference.
- Impact: an ordinary authorized operation creates the condition that blocks the next production-profile startup. No hostile filesystem, incorrect roots, or historical bad data is required. A no-thumbnail deletion does not trigger it.
- Defenses checked: subscriber/owner checks and Playlist row lock; cleanup waits for commit and retains shared active references. These work but do not reconcile the conflicting reference definitions. Keeping strict startup checks enabled is correct.
- Test gap: `src/test/java/com/atstudio/atstudio/service/PlaylistServiceTest.java:614-640` checks only soft deletion/membership cleanup with a mocked coordinator; `src/test/java/com/atstudio/atstudio/service/storage/StorageIntegrityServiceTest.java:62` supplies no Playlists. Neither composes delete, cleanup, inspect and startup.
- Minimal recommendation: align soft-deleted thumbnail references across cleanup and auditing; retain strict integrity and historical parents. `docs/design/runtime-storage-operations.md:47-72` requires this tuple to remain restartable. Code-confirmed sequence, independently confirmed by MA; runtime restart failure was not reproduced and deployed occurrence is unverified.

### F3 [P2, Unexecuted Risk] Stale Track writers may restore a removed media key
- Location: `src/main/java/com/atstudio/atstudio/service/TrackService.java:170-198` reads via unlocked `findById` (`:265-267`) before replacing media. `src/main/java/com/atstudio/atstudio/entity/Track.java:10-38` and `common/entity/BaseEntity.java:13-24` under the same Java package have neither `@Version` nor dynamic-update protection.
- Candidate interleaving: metadata edit B loads old key K0; audio replacement A commits K1 and after-commit cleanup deletes K0; B then commits its stale managed Track. If Hibernate emits a full-row dirty update, B can write K0 back; generated SQL and this outcome were not verified. `src/main/java/com/atstudio/atstudio/service/LikeService.java:33-48` is another material writer of the same entity, so the candidate conflict is not limited to two admin edit forms.
- Impact: the DB again references deleted audio/thumbnail, while K1 is unreferenced; streaming/download and strict audit can fail. This is a concrete unprotected-write path, but the interleaving/SQL outcome was not executed in this review and needs persistence-level confirmation.
- Defenses checked: atomic promotion, transactional rollback cleanup and committed-reference checks only protect the file operation they observe; they do not fence a later stale Track write. Download user locks do not cover Track edits. Whitelist/Certification have `@Version`; that counterevidence does not apply to Track.
- Test candidate: `src/test/java/com/atstudio/atstudio/service/TrackServiceTest.java:466` and `TrackServiceAudioProcessingTest.java` mock persistence and cannot confirm this. A deterministic two-transaction stale-write test must establish SQL/outcome before fix selection or maintenance acceptance. No schema/locking implementation was selected or changed here.

### F4 [P2, Maintenance Candidate] A failed partial stage is omitted from cleanup and recovery
- Location: `src/main/java/com/atstudio/atstudio/service/storage/LocalStorageService.java:89-95` copies directly to the staged target and only rethrows an I/O failure. `StorageMutationCoordinator.java:69-78` increments `stagedCount` after success and cleans only `drafts.subList(0, stagedCount)`.
- Trigger: `Files.copy` creates/writes the staged file and then encounters a read/write failure. For a first-file failure the cleanup list is empty; for a later-file failure it excludes exactly the failed target.
- Impact/bounds: partial bytes remain under `.staging` without a journal row. `StorageMutationRecoveryService.java:43-48` processes journal claims only, and the persisted-reference audit cannot discover this orphan. This low-frequency failure-cleanup maintenance candidate requires partial-write I/O failure; production frequency and accumulated volume are unmeasured. Repeated failures can accumulate disk usage, including sensitive partial private documents; remote disclosure is not claimed and no failure was reproduced.
- Defenses checked: successfully staged earlier files are journaled/cleaned; DB rollback and normal prepared/promoted cleanup exist. None owns the partially written failing target. `LocalStorageService.java:92` also does not close the multipart input stream, which should be handled with the same staging lifecycle fix.
- Tests/minimal recommendation: `src/test/java/com/atstudio/atstudio/service/storage/LocalStorageServiceTest.java:185-189` fails before a stream opens; `StorageMutationCoordinatorTest.java:126-163` mocks second-stage failure and explicitly expects only one draft. Cover write-then-throw cleanup and keep ownership of the failing target until cleanup succeeds.
