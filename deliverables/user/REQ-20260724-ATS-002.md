[GOAL / WHY]
- 원격 `codex/p1-acceptance-hardening` 브랜치만으로 ATStudio V1을 깨끗한 환경에 재현할 수 있는지 증명한다.
- 기존 작업 폴더, 현재 `atstudio` DB, 빌드 캐시, 미추적 파일에 대한 숨은 의존성을 제거한 상태에서 전체 품질·빈 MySQL·실제 기동·주요 API/UI를 검증한다.
- 내부 재현이 통과한 뒤 Toss 테스트 환경과 통제된 메일 환경에서 결제·환불·대사·메일 전달을 검증하고, 인수테스트 전 기술적 준비 상태를 확정한다.

[SCOPE]
- In:
  - 원격 공식 브랜치의 별도 fresh clone과 커밋 동일성 검증
  - Java/Gradle/Node/npm/MySQL 도구 체인 및 잠금 파일 기반 의존성 재설치
  - 백엔드 전체 테스트·커버리지·빌드와 프론트 전체 테스트·커버리지·typecheck·ESLint·Prettier·build
  - 문서·PDF 재현 계약 검증
  - 보호된 기존 DB와 분리된 폐기형 MySQL DB 생성, `schema.sql`·`seed.sql`, Hibernate `ddl-auto=validate`, 환경조건 MySQL 테스트 8건
  - 격리된 백엔드·프론트 기동과 주요 공개/권한 API 및 UI 스모크 테스트
  - Toss 테스트 키에 한정한 카드 등록, 최초 결제, 업그레이드, 예약 변경, 취소/재활성화, 갱신, 환불, 대사, 빌링키 정리 검증
  - 로컬 SMTP 수신 검증과, 안전한 지정 테스트 SMTP/수신함이 이미 제공된 경우에 한한 실제 전달 검증
  - 독립 최종 검수, 비밀값 비노출 확인, 임시 프로세스·DB·clone 정리
- Out:
  - Toss live key 또는 실제 금액 결제·환불
  - 운영 DB, 현재 로컬 `atstudio` DB, 실제 회원 데이터 사용
  - 이전 원격 브랜치 삭제, 운영 배포, 최종 인수 승인
  - 재현되지 않은 추측성 리팩터링과 신규 제품 기능
  - 외부 SMTP 계정 또는 지정 수신함이 없는 상태에서의 임의 실메일 발송

[SUCCESS CRITERIA (DoD)]
- fresh clone HEAD와 원격 공식 브랜치 HEAD가 일치하고 로컬 미추적/ignored 자산 없이 전체 검증이 통과한다.
- 백엔드와 프론트의 현재 품질 임계값이 clean install/build에서 통과한다.
- 폐기형 MySQL 8 DB에서 `schema.sql`, `seed.sql`, Hibernate validation과 환경조건 테스트 8건이 통과하며 현재/보호 DB는 변경되지 않는다.
- 격리 런타임의 주요 API와 역할별 UI가 정상 동작하고 비밀값·raw 결제 식별자가 노출되지 않는다.
- Toss 테스트 환경에서 실행 가능한 승인 범위의 결제·환불·대사 흐름이 제공자와 로컬 ledger 양쪽에서 일치한다.
- 메일 생성·SMTP 전달·링크 base URL이 통제된 테스트 환경에서 확인되며 실제 회원에게 발송되지 않는다.
- 종료 후 임시 프로세스와 폐기형 DB가 남지 않고, 실패 시에는 재현을 위한 최소 증거만 안전하게 보존된다.
- 독립 검수가 PASS/FAIL과 인수테스트·운영 단계의 잔여 항목을 명시한다.

[CONSTRAINTS / POLICIES]
- Work tracking unit: WI
- 현재 공식 작업 폴더와 원격 공식 브랜치는 검증 대상으로만 사용하며 구현 수정은 별도 승인된 corrective WI 없이는 금지한다.
- 현재 `atstudio` DB와 보호 DB 이름은 생성·수정·삭제 대상으로 사용할 수 없다.
- Toss 키는 값 출력 없이 테스트/live 유형을 판별하고, test가 확실하지 않으면 외부 결제 단계는 중단한다.
- 비밀 파일과 환경변수 값은 로그·산출물·Git에 기록하지 않는다.
- 환불은 같은 리허설에서 만든 Toss 테스트 결제만 대상으로 한다.
- 실메일은 지정 테스트 수신함과 안전한 SMTP 구성이 확인된 경우에만 실행한다.
- 외부 연동 실패는 내부 재현 실패와 분리해 판정한다.
- 파괴적 정리는 작업 시작 시 생성한 정확한 임시 경로와 폐기형 DB 이름에만 수행한다.
