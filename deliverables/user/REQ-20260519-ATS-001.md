# REQ-20260519-ATS-001: 정기결제 기반 플랜 변경 및 결제 문서 현행화

[REQ]
REQ ID: REQ-20260519-ATS-001
Project: ATS
Owner: MA
Status: approved

[GOAL / WHY]
- ATStudio 구독 결제를 "Toss 빌링키 기반 정기결제" 중심으로 재정렬한다.
- 구독 플랜 변경에서 단건 결제 Toss Widget 경로를 제거하고, 업그레이드는 기존 빌링키로 즉시 차액을 청구한 뒤 적용하며, 다운그레이드는 다음 결제일부터 적용한다.
- 현재 문서, 설계, 코드가 "단건 결제 + 정기결제 병행" 전제를 일부 유지하고 있으므로, 실제 구현과 목표 정책이 같은 말을 하도록 설계 문서, UI 문서, API 문서, 테스트, 코드를 함께 현행화한다.

[SCOPE]
- In:
  - 현재 결제 문서, SR, REQ, API spec, DB schema, UI flow, use case 문서를 재점검한다.
  - `SR-92 Toss 결제위젯 인라인 렌더링 UX 분리`는 현재 정책과 맞지 않으므로 폐기 또는 archived/deprecated 상태로 정리한다.
  - 신규 구독은 기존처럼 Toss billing auth로 결제수단을 등록하고, 빌링키 발급 후 즉시 첫 결제 성공 시 구독을 활성화한다.
  - 업그레이드는 결제 페이지의 단건 결제 경로로 보내지 않고, 저장된 billing agreement의 빌링키를 사용해 즉시 차액을 청구한다.
  - 업그레이드 차액은 현재 결제 주기의 남은 기간을 기준으로 서버에서 계산한다.
  - 업그레이드 성공 시 새 플랜 혜택은 즉시 적용하고, 다음 결제일은 기존 주기의 다음 결제일을 유지한다.
  - 다운그레이드는 결제 없이 pending 변경으로 저장하고, 다음 결제일부터 새 플랜과 새 billingCycle을 적용한다.
  - 플랜 변경 UI는 기존 방향대로 preview를 먼저 보여주고, 사용자가 "플랜 변경 확인"을 눌러 확정하는 흐름을 유지한다.
  - 업그레이드 preview는 즉시 청구될 차액, 적용일, 다음 결제일, 다음 결제 금액을 사용자가 오해하지 않도록 표시한다.
  - 다운그레이드 preview는 다음 결제일부터 적용됨, 현재 혜택 유지, 즉시 결제 없음이 드러나도록 표시한다.
  - 문서 현행화 누락을 함께 처리한다. 특히 `payment-integration-design.md`, `api-spec.md`, `db-schema.md`, `user-subscription.md`, `screen-flow.md`, `modal-list.md`, `atstudio-front-list.md`, `docs/SR/index.md`를 점검한다.
  - 백엔드/프론트엔드 테스트를 정책 변경에 맞게 보강한다.
- Out:
  - KakaoPay, Naver Pay 등 Toss 외 PG 구현.
  - 운영 live key를 사용한 실제 과금 테스트.
  - webhook, 환불 자동화, 정산, 영수증, 세금계산서 자동화 구현.
  - 관리자 결제 운영 화면 전체 구현. 단, 운영 체크포인트 문서에는 후속 개발 포인트로 기록한다.
  - 단건 결제 상품, 기간권, 크레딧 판매 모델 설계.
  - 사용자 데이터 대량 삭제나 운영 DB 마이그레이션 실행.

[SUCCESS CRITERIA (DoD)]
- 신규 구독은 `mode=recurring` 기반 Toss billing auth 흐름으로 진입하고, 첫 결제 성공 후 구독이 활성화된다.
- 기존 구독자의 업그레이드는 `/subscriptions/payment?purpose=UPGRADE` 또는 Toss one-time widget으로 이동하지 않는다.
- 업그레이드는 활성 billing agreement가 있을 때만 진행되며, 빌링키 즉시 청구 성공 이후에만 새 플랜으로 변경된다.
- 업그레이드 실패 시 구독 플랜, billingCycle, expiresAt, pending 변경값이 변경되지 않는다.
- 업그레이드 성공 시 다음 결제일은 유지되고, 다음 정기 갱신에서 새 플랜/주기의 정가가 청구된다.
- 다운그레이드는 즉시 결제 없이 pending 변경으로 저장되고, 갱신 job이 다음 결제일에 새 플랜을 적용한다.
- 플랜 변경 UI는 preview 후 확인 흐름을 유지하고, 업그레이드/다운그레이드의 결제·적용 시점 차이를 명확히 보여준다.
- 구독 사용자-facing 흐름에서 Toss one-time widget 경로가 제거되거나 접근 불가 상태로 정리된다.
- `SR-92`는 폐기/보관 상태로 정리되고, SR index와 관련 문서가 같은 상태를 가리킨다.
- 결제 설계 문서는 "단건 + 정기결제 병행"이 아니라 "정기결제 중심, 단건 결제는 구독 user-facing 범위 밖"으로 현행화된다.
- API spec, DB schema, UI flow, use case 문서가 실제 코드와 목표 정책을 반영한다.
- 백엔드 결제/구독 테스트, 프론트엔드 타입체크/테스트/ESLint, 문서 검증이 통과한다.
- 변경사항은 명시 파일만 stage/commit하고, 기존 untracked 과거 산출물과 runtime pid/log 파일은 건드리지 않는다.

[CONSTRAINTS / POLICIES]
- Work tracking unit: WI
- REQ 승인 전에는 구현 코드와 기존 설계 문서를 수정하지 않는다. 단, 이 REQ draft 파일은 검토용 산출물이다.
- 결제 secret, billing key, customerKey, authKey 원문은 프론트엔드 응답, 사용자 화면, 운영 화면, 로그, 문서, 테스트 fixture에 노출하지 않는다.
- 빌링키 암호화 키는 `PAYMENT_BILLING_KEY_ENCRYPTION_SECRET` 정책을 유지한다.
- 로컬 테스트는 Toss test key 또는 Mock만 사용하며 실제 과금이 발생하면 안 된다.
- 서버 계산 금액이 결제 금액의 단일 기준이다. 프론트엔드 금액은 표시와 검증 보조 값으로만 사용한다.
- 결제 성공 후 구독 변경 실패가 생길 수 있으므로, 최소한 실패 기록과 후속 보상/운영 체크포인트를 문서화한다.
- DB 스키마 변경이 필요하면 별도 WI에서 변경 범위와 rollback 기준을 명시한다.

[CURRENT FINDINGS]
- `docs/design/payment-integration-design.md`는 아직 Toss one-time payment와 recurring billing을 함께 지원하는 구조를 중심으로 설명한다.
- `docs/SR/SR-92.md`는 Toss one-time widget 인라인 렌더링 UX 분리를 목표로 하지만, 구독 정책이 정기결제 중심으로 바뀌면 원래 목적이 소멸한다.
- `frontend/src/pages/subscriber/SubscriptionManagePage.tsx`는 업그레이드 시 `/subscriptions/payment?...&purpose=UPGRADE`로 이동한다.
- `frontend/src/pages/subscriber/SubscriptionPaymentPage.tsx`는 `purpose=UPGRADE`일 때 `prepareSubscriptionPayment`를 호출하고, provider가 Toss이면 `TOSS_WIDGET` 경로를 처리한다.
- `PaymentApplicationService.prepareSubscriptionPayment()`는 `SUBSCRIBE`와 `UPGRADE`를 one-time payment provider(`MOCK` 또는 `TOSS`)로 처리한다.
- `UserSubscriptionService.changeSubscription()`의 업그레이드 분기는 레거시 `paymentService.processPayment()`를 호출하고 즉시 플랜/만료일을 변경한다.
- 현재 업그레이드 로직은 새 `expiresAt`을 오늘 기준 새 주기로 재설정한다. 이번 정책은 다음 결제일 유지가 목표이므로 변경이 필요하다.
- `RecurringRenewalService`는 pending downgrade를 다음 renewal charge에 반영하는 구조를 이미 갖고 있어, 다운그레이드 정책은 기존 방향을 보강하면 된다.
- `api-spec.md`, `db-schema.md`, `screen-flow.md`, `modal-list.md`, `user-subscription.md`에는 업그레이드 결제 방식과 단건 결제 전제가 남아 있어 현행화 대상이다.

[RISKS / OPEN QUESTIONS]
- Risks:
  - 업그레이드 즉시 청구가 성공했는데 로컬 구독 변경 저장이 실패하면 보상 취소/환불 또는 운영자 개입 기준이 필요하다.
  - billing agreement가 없는 기존 구독 사용자는 업그레이드를 진행할 수 없으므로 결제수단 등록 유도 흐름이 필요할 수 있다.
  - billingCycle 변경을 업그레이드와 동시에 허용하면 "즉시 적용 범위"와 "다음 결제 금액"을 사용자가 오해할 수 있다.
  - 기존 `PaymentApplicationService`의 one-time `UPGRADE` 경로를 제거할 때 Mock/Toss 단건 결제 테스트가 깨질 수 있다.
  - 문서 수가 많아 일부 화면/API 문서가 낡은 흐름을 계속 참조할 수 있다.
- Questions:
  - 업그레이드에서 사용자가 billingCycle도 함께 바꾸는 경우, 추천 정책은 "플랜 혜택은 즉시 적용, 선택한 billingCycle은 다음 결제일부터 적용"이다. 이 방향으로 승인할지 확인이 필요하다.

[ALTERNATIVE SUGGESTION]
- 추천안:
  - 구독 user-facing 결제는 정기결제 하나로 단순화한다.
  - 업그레이드는 `RecurringPaymentProvider.charge()`를 사용하는 별도 서비스 경로를 만들고, one-time `PaymentApplicationService`의 `UPGRADE` 흐름은 구독 UI에서 제거한다.
  - 다운그레이드는 기존 pending 구조를 살리되, preview와 문서에서 "다음 결제일 적용"을 더 명확히 한다.
  - 단건 결제 provider 코드는 즉시 삭제하지 않고, 구독 화면에서 접근하지 않는 legacy/test-only 범위로 축소한 뒤 후속 정리 여부를 판단한다.
- 대안:
  - 단건 결제 provider 코드를 이번 REQ에서 완전히 제거할 수 있다. 다만 테스트/문서/과거 REQ 영향 범위가 커져서 이번 작업의 위험과 소요가 늘어난다.
