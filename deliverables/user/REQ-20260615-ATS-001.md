[GOAL / WHY]
- 결제 기능, 음원 검색 태그 보정, 화이트리스트 채널 확장 작업 이후 현재 코드, DB schema, 설계 문서, UI 문서, 작업 산출물 사이의 불일치를 최종 점검하고 현행화한다.
- 특히 `schema.sql`이 최신이어도 기존 로컬/운영 DB에는 자동 반영되지 않는 구조를 명확히 기록하고, 실제 적용 절차와 검증 포인트를 문서화한다.
- 신규 기능을 추가하기보다, 이미 구현된 기능이 클라이언트 설명/운영/후속 개발 기준으로 신뢰 가능한 상태인지 확인한다.

[SCOPE]
- In:
  - 결제/정기구독/운영 결제 기능 문서와 코드 정합성 점검.
  - 화이트리스트 채널 기능 문서와 코드 정합성 점검.
  - 음원 검색 태그/usage 보정 기능 문서와 코드 정합성 점검.
  - `schema.sql`, 엔티티, DB 설계 문서, 실제 DB 반영 절차의 차이 명확화.
  - API count, DB table count, screen count, usecase count 등 주요 인덱스 값 재검증.
  - 필요한 문서/산출물 보강 및 오기입 수정.
- Out:
  - 실제 로컬/운영 DB에 DDL을 직접 적용하는 작업.
  - 운영 데이터 삭제/수정.
  - 신규 결제 provider, webhook, tax invoice 자동 발급, YouTube API 자동 등록 같은 새 기능 구현.
  - 대규모 UI 리디자인.

[SUCCESS CRITERIA (DoD)]
- 코드, 설계 문서, UI 문서, 작업 산출물이 서로 같은 기능 범위와 상태 모델을 설명한다.
- `schema.sql`과 `docs/design/db-schema.md`의 테이블/핵심 컬럼 설명이 맞고, 기존 DB 수동 반영 필요성이 별도 절차로 남는다.
- 결제/화이트리스트/검색 태그 기능의 API, 화면, DB, 테스트 근거가 추적 가능하다.
- 문서 validation, backend test, frontend typecheck/lint/build, diff check를 재실행하고 결과를 보고한다.
- 파괴적 DB/데이터 작업이 필요하면 실행 전 사용자 승인을 받는다.

[CONSTRAINTS / POLICIES]
- Work tracking unit: WI.
- REQ 내용은 사용자 승인 범위를 기록하기 위한 한국어 문서로 유지한다.
- 일반 문서와 설계 문서는 기존 프로젝트 정책에 따라 영어로 작성한다.
- DB DDL 직접 적용, 데이터 삭제, 운영 시크릿 변경은 별도 승인 없이는 수행하지 않는다.
- 기존 사용자가 만든 변경사항은 되돌리지 않는다.
