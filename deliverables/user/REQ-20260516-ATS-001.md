## [GOAL / WHY]

- ATStudio 구독 결제 흐름을 현재의 직접 구독 생성 방식에서 결제 준비, 결제 확인, 구독 적용이 분리된 구조로 전환한다.
- 로컬/테스트 환경에서는 실제 외부 결제 없이 Mock 결제로 성공, 실패, 취소 흐름을 검증할 수 있어야 한다.
- 이후 Toss 일회성 결제와 Toss 정기결제를 같은 계약 위에 얹을 수 있도록 결제 주문, provider interface, 구독 적용 경계를 먼저 만든다.

## [SCOPE]

- In:
  - `payment_orders` 기반 결제 주문/시도 추적 모델 추가
  - Mock-first `prepare / confirm / cancel` 결제 API 추가
  - `PaymentProvider` 추상화와 Mock provider 구현
  - 구독 신규 가입과 업그레이드를 결제 확인 이후 적용되도록 리팩터링
  - React 구독 결제 화면에서 기존 직접 `subscribe()` 호출 제거
  - Mock 결제 UI에서 성공, 실패, 취소 시나리오 제공
  - 기존 `POST /api/user-subscriptions`는 임시 호환 엔드포인트로 유지하되 사용자 결제 화면에서는 사용하지 않음
  - 백엔드/프론트엔드 회귀 테스트와 문서 정합성 갱신
- Out:
  - Toss 실 API 연동
  - Toss billing key 저장 및 실제 정기결제 실행
  - KakaoPay 구현
  - 환불 자동화, webhook, 관리자 결제 감사 화면
  - 운영 결제키/시크릿 설정

## [SUCCESS CRITERIA (DoD)]

- 사용자는 구독 결제 화면에서 Mock 결제 준비 후 성공 confirm을 통해 구독을 활성화할 수 있다.
- Mock 결제 실패와 취소는 구독을 생성하거나 업그레이드하지 않고 결제 주문 상태만 기록한다.
- 신규 구독과 업그레이드는 결제 confirm 성공 이후에만 적용된다.
- 다운그레이드는 기존처럼 결제 없이 예약 변경으로 유지된다.
- 결제 confirm은 `orderId`, 사용자, 목적, 구독 상품, 결제주기, 금액을 서버 기준으로 검증한다.
- 동일 `orderId` confirm 재시도는 중복 구독/중복 결제 기록을 만들지 않는다.
- 기존 `POST /api/user-subscriptions`는 호환 목적으로 남아 있으나 React 사용자 결제 플로우에서는 호출되지 않는다.
- 백엔드 테스트, 프론트엔드 타입체크/테스트, 문서 검증이 통과한다.

## [RISKS / OPEN QUESTIONS]

- Risks:
  - 현재 구독 생성과 결제 기록이 한 서비스 흐름에 묶여 있어 리팩터링 중 회귀 위험이 있다.

  - 프론트엔드 결제 페이지 전환 중 기존 subscribe UX와 관리 화면 이동 경로가 어긋날 수 있다.
- Questions:
  - Mock 결제 실패/취소 UI는 버튼 3개 방식으로 충분한가?
  - `POST /api/user-subscriptions` 호환 엔드포인트를 local/test 전용 설정으로 즉시 제한할지, 이번 REQ에서는 deprecated 표기와 UI 제거까지만 할지 결정이 필요하다.
