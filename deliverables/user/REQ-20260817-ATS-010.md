[GOAL / WHY]
- Keep a client-facing acceptance environment available through Cloudflare Tunnel while preparing a separate operational-rehearsal environment for V1 release readiness.
- Prevent source, runtime, database, SMTP, payment-provider, callback, and test-data interference between the two activities.

[SCOPE]
- In:
  - Record a non-destructive disposition inventory for existing local and remote branches, including unique-commit and preservation evidence.
  - Freeze the current release-candidate commit as the client-acceptance baseline and prepare a separate client runtime/tunnel health check.
  - Create a separate operational-rehearsal branch and isolated runtime plan, including independent ports, disposable/rehearsal database target, test accounts, and callback-origin boundaries.
  - Inspect release configuration without exposing secrets.
  - Prepare and execute evidence-driven verification for HTTPS/proxy/CORS/callback origins, SMTP receipt, Toss test rehearsal, backup/restore, logs/monitoring/alerts, and single-scheduler operation.
  - Update current-state operational documentation only when a verified result changes it.
- Out:
  - Immediate deletion of any branch, worktree, file, database, or data.
  - Live-money payment, live refund, production email blast, production database mutation, or secret disclosure.
  - New product features and broad refactoring.
  - Promotion to `master`, production deployment, or deletion of legacy branches before a separately approved disposition list.

[SUCCESS CRITERIA (DoD)]
- The client acceptance runtime and its public frontend/API health are recorded from a fixed commit and remain isolated from rehearsal changes.
- A distinct operational-rehearsal branch and runtime boundary are documented and reproducible.
- Each mandatory readiness item has explicit evidence, an identified blocker, or an approved follow-up owner; provider/UI/API/persisted-state evidence is not conflated.
- Branch disposition inventory identifies preservation and deletion candidates without deleting anything.
- All changed code, configuration, and documentation pass applicable checks before integration.

[CONSTRAINTS / POLICIES]
- Work tracking unit: WI.
- Client acceptance and operational rehearsal must not share mutable database state, provider customer/billing state, SMTP recipient flow, scheduler execution, or callback origin.
- Do not print or commit secrets, credentials, JDBC URLs, raw provider payloads, or personal data.
- Any destructive action requires a new exact-scope confirmation.
- Any external side effect requires an explicit action plan and confirmation immediately before execution.
- Use Extra High reasoning effort unless Ultra is materially necessary and explicitly announced first.
