[SCOPE]

- 제외: 신규 제품 기능/정책, 실제 Toss 결제·환불·메일, 기존 DB/파일/로그 삭제·복구·DDL, 키/비밀값 열람·변경, 배포/서버 재시작/브랜치 정리, 자동 커밋/푸시.

[SUCCESS CRITERIA (DoD)]
- 각 결함별 수정 근거와 기존 방어를 유지한 회귀 테스트를 남긴다. 가능하면 수정 전 실패도 기록하고, 실행하지 못한 검증은 통과로 적지 않는다.
- 결제는 fake Provider/독립 로컬 트랜잭션, 저장소는 임시 파일과 H2, 인증은 합성 키/토큰으로 검증한다.
- 백엔드 test/build/기존 JaCoCo gate, 프론트 test/typecheck/lint/Prettier/build, docs validation/diff check를 수행한다. 임계값을 낮추거나 검사를 삭제해 통과시키지 않는다.
- 구현과 별도 검토자가 변경 경계를 재검수하고 반례가 나오면 수정 후 관련 검증을 반복한다.
- 기존 데이터/프로세스는 직접 조작하지 않으며, 미커밋 문서와 미추적 자료를 보존한다.
- 완료 판정은 코드 전달/검증 기준이다. 실제 운영 대상·계정과 함께 할 잔여 항목 및 재로그인 같은 적용 영향은 별도로 보고한다.

[CONSTRAINTS / POLICIES]
- 전체곡 무료 재생, 유료 구독 다운로드/횟수, Toss 카드 정기결제, 단일 서버, 연간 잔여 기간 유지와 다음 주기 예약 정책을 변경하지 않는다.
- 기존 스키마/잠금/상태 필드를 우선 사용한다. DDL·기존 자료 파괴·정책 변경이 꼭 필요하면 그 부분만 중단하고 정확한 결정을 남긴다.
- 동시에 최대 3명, fork_context=false, 각자 분리된 파일 범위; 완료 시 close_agent. Gradle/npm 무거운 검증은 MA가 직렬 실행/허가하여 앱 부하와 산출물 충돌을 줄인다.
- 서버는 기존 pinned JAR를 유지한다. main을 참조하는 Vite는 프론트 변경을 HMR로 볼 수 있으나 실제 계정/결제 동작으로 검증하지 않는다.
