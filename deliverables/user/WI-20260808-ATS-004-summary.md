# WI-20260808-ATS-004 Work Summary

## 결론

- 현재 관리자 사용자 구독 화면에서는 **플랜을 변경할 수 없다**. 관리자 플랜 목록을 조회하지만, 이 목록은 표의 `대기 플랜` 이름을 표시하는 데만 사용된다.
- 현재 수정 API는 `status`, `billingCycle`, `expiresAt`만 받으며, 세 값을 관계 검증 없이 서로 독립적으로 저장한다.
- 따라서 사용자가 지적한 `EXPIRED` + 미래 만료일 조합이 현재 허용된다. 반대로 `ACTIVE` 또는 `CANCELLED` + 과거 만료일도 허용된다.
- `CANCELLED` + 오늘 또는 미래 만료일은 오류가 아니다. 취소 후 만료일까지 유료 접근을 유지하는 정상 유예 기간이다.
- 플랜 변경이 필요한 경우 단순히 현재 모달과 DTO에 플랜 셀렉트를 추가하는 방식은 권고하지 않는다. 이미 결제 운영 화면에 구현된 환불 연계 권한 보정 패턴을 일반 운영 교정으로 확장하는 방식이 안전하다.

## 현재 동작의 레이어별 판정

| 레이어 | 현재 동작 | 판정 |
| --- | --- | --- |
| UI | 플랜 전체 목록을 조회하지만 현재 플랜 선택 필드는 없음. 상태·결제 주기·만료일만 수정 가능하며 조합 검증 없음 | 플랜 변경 불가, 논리적으로 잘못된 조합 제출 가능 |
| API | 관리자 수정 요청은 `status`, `billingCycle`, `expiresAt`만 포함 | `subscriptionId`가 없어 플랜 변경 계약 자체가 없음 |
| 저장 | 엔티티가 전달된 세 필드를 각각 바로 대입하고 현재 플랜·예약 변경은 그대로 둠 | 상태 전이, 날짜, 예약 변경 정합성 미보장 |
| 결제/예약 | 빌링 약정, 다음 결제일, 진행 중 결제 주문, 결제 감사 로그를 확인하거나 변경하지 않음 | 내부 표시 변경과 자동 결제 상태가 어긋날 수 있음 |

## 제안 상태·만료일 행렬

`today`는 서버가 사용하는 하나의 업무 기준일로 계산해야 한다.

| 목표 상태 | 허용 만료일 | 처리 원칙 |
| --- | --- | --- |
| `ACTIVE` | `expiresAt >= today` | 과거는 거부. 자동 갱신 여부는 빌링 약정 상태와 별도로 표시하고 검증 |
| `CANCELLED` | `expiresAt >= today` | 오늘/미래는 유예 기간으로 허용. 자동 갱신 중단 및 빌링 약정 처리 여부를 명시 |
| `EXPIRED` | `expiresAt <= today` | 미래는 거부. 예약 변경 제거를 기본값으로 하고 빌링 약정 종료/보존 정책을 명시 |

- UI는 잘못된 조합을 즉시 안내하고 저장 버튼을 비활성화할 수 있지만, 최종 검증은 반드시 백엔드가 수행해야 한다.
- `EXPIRED` 선택 시 만료일을 오늘로 제안할 수 있으나, 사용자가 입력한 미래 날짜를 설명 없이 자동 변환하지 말고 명확히 안내한다.
- 빈 변경 요청과 동일 상태 요청도 명시적으로 거부하거나 “변경 없음”으로 응답하여 운영자가 성공으로 오인하지 않도록 한다.

## 플랜 변경 대안

### 대안 A: 현재 빠른 수정 모달에 플랜 선택 추가

- 장점: 구현과 운영 동선이 단순하다.
- 필수 조건: 대상 플랜 활성 여부와 사용자 유형 검증, 구독·빌링 약정 잠금, 예약 변경 처리, 진행 중 결제 차단, 전후 상태 감사, 운영 사유와 확인 화면이 모두 필요하다.
- 위험: 단순 DB 플랜 변경으로 구현하면 업그레이드 차액 결제, 다음 정기결제 금액·주기, 대기 플랜과의 관계를 설명할 수 없다.

### 대안 B: 일반 관리자 권한 보정 흐름으로 분리 — 권고

- 기존 결제 운영의 환불 연계 권한 보정은 목표 플랜·주기·상태·만료일, 예약 변경 제거, 로컬 빌링 약정 취소, 미리보기, 승인·실행, 잠금, 감사 로그를 이미 다룬다.
- 이 안전 패턴을 재사용하여 환불이 없는 고객지원/운영 교정도 별도 근거와 함께 처리하도록 확장한다.
- 사용자 구독 화면의 빠른 수정은 상태·날짜의 제한된 교정만 남기거나, 새 보정 흐름으로 이동시키는 진입점으로 바꾼다.
- 플랜 변경은 “정상 결제 플랜 변경”이 아니라 “관리자 로컬 권한 교정”임을 표시하며, 외부 결제나 환불이 자동 실행된다고 오해하지 않게 한다.

## SR-97에 반드시 들어갈 요구

- 현재 플랜 변경은 불가능하다는 사실과 기존 `SR-14`의 플랜 변경 요구가 미완료라는 점.
- `EXPIRED` + 미래 만료일과 `ACTIVE`/`CANCELLED` + 과거 만료일을 서버에서 거부하는 상태·날짜 규칙.
- `CANCELLED` + 미래 만료일은 정상 유예 기간이라는 예외.
- 플랜·주기·상태·만료일·대기 변경·빌링 약정·결제 진행 상태를 하나의 미리보기에서 함께 보여주는 요구.
- 대상 플랜은 활성 상태이고 사용자의 `userType`과 일치해야 한다는 요구.
- 플랜/주기 변경의 적용 시점과 금액 처리 원칙을 명시하고, 관리자 로컬 교정이 외부 결제·환불을 자동 수행하지 않는다는 경계.
- 구독과 빌링 약정의 잠금, 진행 중 결제 주문 차단, 운영 사유, 행위자·전후 상태 감사 로그, 확인 절차.

## 검증 및 변경 범위

- UI, API, 엔티티, 서비스, 저장소, 정기결제 스케줄러, 환불 연계 권한 보정 구현과 설계 문서를 읽기 전용으로 대조했다.
- 애플리케이션 테스트는 실행하지 않았다. 이번 WI는 조사 전용이며 필요한 회귀 테스트 목록을 Evidence Pack에 기록했다.
- 코드, SR, 인덱스, DB, 빌링 약정 및 외부 결제사업자 상태는 변경하지 않았다.
