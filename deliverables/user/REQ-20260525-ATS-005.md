[GOAL / WHY]
- REQ-20260525-ATS-004로 관리자 환불 원장과 Toss cancel 실행 backend가 구현되었다.
- 하지만 환불 성공은 아직 `user_subscriptions`, `billing_agreements`, `subscription_payments` 같은 로컬 구독 권한 상태를 자동으로 바꾸지 않는다.
- 다음 단계는 환불 이후 운영자가 별도 승인 절차로 구독 권한을 보정할 수 있게 하여, "돈은 환불되었지만 권한은 그대로 남는 상황" 또는 "권한 보정을 임의 DB 수정으로 처리하는 상황"을 막는 것이다.

[SCOPE]
- In:
  - 환불 후 권한 보정 정책을 명시한다.
  - `payment_entitlement_corrections` 또는 동등한 로컬 권한 보정 원장 추가.
  - 환불 건과 연결된 권한 보정 preview API 추가.
  - 관리자 권한 보정 요청 생성 API 추가.
  - 관리자 권한 보정 승인 API 추가.
  - 관리자 권한 보정 실행 API 추가.
  - 관리자 권한 보정 목록/상세 조회 API 추가.
  - 보정 실행 시 `user_subscriptions`의 플랜, 결제 주기, 상태, 만료일, pending 변경을 명시된 목표값으로만 바꾼다.
  - 필요 시 local `billing_agreements`를 cancel 처리할 수 있게 하되, provider billing key 삭제/취소 API 호출은 하지 않는다.
  - 모든 보정 전/후 상태와 actor를 audit log에 남긴다.
  - 환불 자체와 권한 보정은 계속 분리한다. 환불 성공 후 권한 보정은 자동 실행하지 않는다.
  - API spec, DB schema, SR-93, payment runbook, payment policy, final acceptance checklist 현행화.
  - 백엔드 테스트와 문서 검증.
- Out:
  - 사용자 환불 요청 UI/API.
  - 관리자 환불/권한 보정 UI 탭.
  - 자동 정책 추론으로 즉시 권한 보정 실행.
  - provider billing key 삭제 API 호출.
  - 정산, 세금계산서, cash receipt 발급/취소.
  - settlement import/reconciliation.
  - webhook/multi-PG.

[SUCCESS CRITERIA (DoD)]
- 관리자는 환불 성공 또는 확인 가능한 환불 건에 대해 권한 보정 preview를 볼 수 있다.
- 권한 보정 요청은 실행 전 로컬 원장에 저장되고, 보정 전/후 목표 상태가 명확히 기록된다.
- 승인되지 않은 권한 보정 요청은 실행할 수 없다.
- 실행은 명시된 목표 상태만 적용하며, 추정으로 이전 플랜을 복원하지 않는다.
- 실행 후 `user_subscriptions`와 선택된 local `billing_agreements` 상태가 preview와 일치한다.
- 실행 결과는 `SUCCEEDED`, `FAILED` 또는 이에 준하는 상태로 기록된다.
- audit log에는 요청/승인/실행 전이가 actor와 함께 남는다.
- 환불 provider 호출과 권한 보정 실행은 서로 자동 연결되지 않는다.
- backend tests, docs validation, diff check가 통과한다.

[CONSTRAINTS / POLICIES]
- Work tracking unit: WI
- 문서는 English, REQ는 한국어로 작성한다.
- 로컬 구독 권한 변경은 실제 서비스 접근에 영향을 주므로 provider refund보다 더 보수적으로 다룬다.
- 업그레이드 이전 플랜이 현재 결제 원장에 명시적으로 저장되어 있지 않으므로, 시스템이 자동으로 "이전 플랜"을 추정해서 롤백하면 안 된다.
- 운영자는 목표 플랜, 결제 주기, 상태, 만료일, pending clear 여부, local billing agreement cancel 여부를 명시한다.
- provider billing key 원문, Toss secret, authKey, customerKey, raw card data, raw provider payload는 저장/노출하지 않는다.
- local billing agreement cancel은 future charge를 막는 로컬 운영 상태 변경이며, provider billing key 삭제와는 별도다.
