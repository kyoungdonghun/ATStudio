# WI-20260714-ATS-001 P1 통합 추적 기준선 결과

## 확정 범위

- `ATS020-P1-01`부터 `ATS020-P1-13`까지 현재 브랜치의 코드, 스키마/수동 패치, 테스트, 설계, 운영 문서, 클라이언트 문서를 다시 대조했습니다.
- 조건부 인수환경 항목 `ATS020-X-01`, `X-02`, `X-04`는 P1 구현 범위와 분리했습니다.
- 이번 WI는 결함 종료가 아니라 수정 전 기준선 확정입니다. 13개 P1은 모두 열린 상태입니다.
- 코드, 스키마, 테스트, 기존 문서, 런타임 로그는 수정하지 않았습니다.

## 핵심 교정

1. `P1-07`: 갱신 경로에는 P0 작업으로 약정 행 잠금이 추가됐습니다. 따라서 "갱신 직렬화가 전혀 없다"는 과거 표현은 좁혀야 합니다. 다만 confirm/upgrade 잠금, 안정적인 명령 식별자, 결제 최종화 유일성은 여전히 없습니다.
2. `P1-09`: 갱신 행 잠금이 생겼어도 전체 due 목록과 Provider 호출이 한 트랜잭션에서 실행되는 문제는 남아 있습니다. `P1-07`의 명령 중복 방지와 별도 결함입니다.
3. `P1-13`: P0 작업으로 회원 탈퇴 후 결제키 정리 절차는 문서화됐습니다. 이 부분의 과거 지적은 현행화해야 하지만, 결제 문서의 완료 표현과 P1 출시 게이트 부재, CSV/기업문서 임시 안전 안내 부재는 남아 있습니다.
4. `P1-01`: 위험한 플레이리스트 파일 업로드는 P1로 확정됩니다. 동일 출처에서 실제 실행돼 토큰 탈취로 이어지는 P0급 영향은 저장소만으로 확인되지 않은 환경 조건입니다.

## 위험과 승인 포인트

- `X-01`의 기존 DB 이력은 저장소에서 알 수 없습니다. 수동 패치 두 개만 존재하며 이전 결제 마이그레이션 체인과 기업 인증 레거시 문서 backfill/처분 절차가 없습니다.
- 특히 레거시 기업 인증 문서 backfill/처분을 명시적으로 소유한 승인 WI가 없습니다. MA가 별도 WI를 지정하거나 기존 WI 범위를 승인 변경해야 합니다.
- disposable MySQL 생성/삭제, DDL·데이터 변경, 레거시 backfill, 새 라이브러리, live Toss/SMTP/운영 DB, 공개 URL 전달은 별도 승인이 필요합니다.
- `X-02`는 Cloudflare 경유 실제 client IP가 어떻게 보이는지 저장소만으로 확정할 수 없습니다.
- `X-04`는 bootstrap이 기본 비활성이지만 profile 차단이 없습니다. 실제 배포에서 활성화됐는지는 확인되지 않았습니다.
- 이 WI에서는 테스트를 실행하지 않았습니다. 현재 테스트를 읽어 공백을 확인했고, 각 행에 필요한 신규 테스트와 재현 명령을 지정했습니다.

## WI 체인

- WI-001 완료로 `WI-004`~`WI-034`에 대한 WI-001 의존성은 해제됩니다.
- 다만 Phase 1 구현은 병렬 설계 WI인 `WI-002`, `WI-003`도 완료된 뒤 시작해야 합니다.
- 결제 검토는 `WI-023`, 보안 검토는 `WI-024`, 교차 레이어 검토는 `WI-025`, 문서 현행화는 `WI-026`/`WI-027`, 최종 종료 판정은 `WI-034`가 담당합니다.
