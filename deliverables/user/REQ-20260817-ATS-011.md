[GOAL / WHY]

- 기존 개발 MySQL DB와 기존 클라이언트 acceptance disposable DB, 정확히 두 로컬 환경만 동일한 검증용 ADMIN 계정과 명확히 식별 가능한 dummy 음악 카탈로그로 동기화한다.
- 두 환경에서 acceptance 검증이 같은 계정, 태그, 재생 가능한 미디어, waveform, 앨범 관계를 사용하도록 하며, UI/API/저장 상태가 서로 어긋나는 수동 DB 조작을 피한다.

[SCOPE]

- In:
  - 사전점검으로 기존 개발 MySQL DB 하나와 기존 클라이언트 acceptance disposable DB 하나만 대상임을 확인하고, 다른 로컬ㆍ원격ㆍproductionㆍstage DB 연결을 차단한다.
  - 두 대상에 동일한 식별자의 verified `ADMIN` 계정 하나를 준비한다. 하나의 공유되고 추측 불가능한 비밀번호만 사용하며, 평문 자격 증명은 완료 시 사용자에게만 직접 보고할 수 있고 문서, 소스, Git, 로그, Evidence Pack에는 기록하지 않는다.
  - `USAGE`, `GENRE`, `MOOD`, `INSTRUMENT` 각각에 acceptance dummy 데이터임이 명확한 전용 태그를 추가하고, 생성한 ten dummy tracks에 필요한 태그 관계를 일관되게 연결한다.
  - 전용 식별 접두사를 사용한 재생 가능한 dummy track 정확히 10개와, 그 10개만 포함하는 active dummy album 정확히 1개를 각 환경에 준비한다.
  - 애플리케이션 service/API/storage workflow를 사용하여 오디오 미디어, waveform 데이터, 태그 관계, 앨범-트랙 관계 및 활성 상태를 생성ㆍ검증한다. 직접 SQL 삽입이나 관계 우회는 허용하지 않는다.
  - 두 DB 각각에서 UI 관찰, API 응답, 저장된 관계를 구분한 strict post-seed proof를 수집하고, 계정ㆍ태그ㆍ트랙ㆍ미디어ㆍwaveformㆍ앨범 구성이 서로 동등함을 비교ㆍ증명한다.
- Out:
  - 위 두 대상 이외의 DB, production DB, stage DB, 원격 DB 또는 공개 URL에 대한 접속ㆍ변경.
  - 범위 밖 기존 데이터의 삭제ㆍ정리ㆍ변경 및 기존 사용자, 플랜, 구독, 결제, 환불, 이메일 발송 데이터의 변경.
  - 소스 기능 동작, 애플리케이션 설정, public URL, 이메일 전달 설정의 변경.
  - 자격 증명, JDBC URL, 비밀값, 원시 connection 정보, 평문 비밀번호의 출력ㆍ커밋ㆍ로그ㆍ문서화.

[SUCCESS CRITERIA (DoD)]

- 사전점검 증거는 정확히 두 로컬 대상만 허용됐음을 확인하며, 대상 식별자와 자격 증명 같은 민감값은 보존하지 않는다.
- 두 환경 모두 동일한 verified `ADMIN` 계정 하나를 가지며, 동일한 공유 비밀번호로 인증 가능함이 자격 증명 비노출 방식으로 검증된다.
- 두 환경 모두 `USAGE`, `GENRE`, `MOOD`, `INSTRUMENT` 각 분류에 dedicated dummy tag가 존재하고, 각 tag 및 track relation은 API와 persisted state에서 일치한다.
- 각 환경에는 전용 prefix로 식별되는 playable dummy track이 정확히 10개 있고, 모든 track의 실제 미디어 접근과 waveform 데이터가 정상이며, 누락되거나 추가된 범위 내 dummy track이 없다.
- 각 환경에는 active dummy album이 정확히 1개 있고, 그 album은 해당 10개 track을 각각 한 번씩 포함하며, 다른 track을 포함하지 않는다.
- strict post-seed proof는 각 환경에서 UI behavior, API invocation/response, storage/media result, persisted DB state를 분리해 기록한다. parity proof는 식별자, role/verification state, tag category/value set, track set, playability, waveform presence, album state 및 ordered album membership이 동일함을 확인한다.
- proof 또는 parity가 하나라도 실패ㆍ불명확하면 성공으로 판정하지 않으며, 범위 확대, 재시도, cleanup은 새 승인 없이는 수행하지 않는다.

[CONSTRAINTS / POLICIES]

- Work tracking unit: WI. 본 REQ는 승인된 두 로컬 DB seed 작업만 허용한다.
- 데이터 변경 전, 실행 담당자는 대상 두 DB의 현재 연결 범위와 예상 변경 집합을 자격 증명 비노출 방식으로 다시 보고하고, 대상이 모호하면 fail-closed로 중단한다.
- 기존 데이터는 보존한다. 본 REQ가 소유하는 전용 dummy 식별자만 생성 또는 필요한 경우 같은 전용 식별자 범위 안에서 동기화할 수 있으며, unrelated data는 삭제하거나 수정하지 않는다.
- account, tags, tracks, media, waveform, album relations는 애플리케이션의 지원된 service/API/storage 경로를 통해서만 작성한다. 허용 경로가 모든 관계를 일관되게 만들 수 없으면 우회하지 말고 blocker로 보고한다.
- 하나의 공유 비밀번호는 실행 중 안전하게 생성ㆍ전달하며, 평문은 사용자에게 직접 보고하는 경우에만 일회성으로 제공한다. 어떤 산출물ㆍcommand historyㆍ테스트 fixtureㆍ환경 파일ㆍGit 기록에도 남기지 않는다.
- 외부 이메일 전달, 공개 URL, source/configuration change는 필요하지 않으며, 이를 유발하는 작업은 범위 밖이다.
