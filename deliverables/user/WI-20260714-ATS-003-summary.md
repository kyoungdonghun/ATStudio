# WI-20260714-ATS-003 보안·인수환경 설계 요약

## 결과

코드 변경 없이 P1 보안 결함과 Cloudflare 인수환경의 구현 계약을 확정했습니다. 설계 원문은 `docs/design/p1-security-acceptance-hardening-design.md`입니다.

- 플레이리스트 이미지는 JPEG/PNG만 디코드한 뒤 메타데이터와 부가 페이로드를 버리고 새 JPEG로 재인코딩합니다.
- 기업 인증 문서는 공용 `/uploads` 밖에 격리하고 ADMIN API에서 항상 첨부파일로만 내려받습니다. 1차 허용 형식은 PDF/JPEG/PNG입니다.
- 로그아웃, 비밀번호 변경, 비밀번호 재설정은 사용자 행 잠금 아래 refresh token 해시를 제거합니다. 기존 access token은 만료 시점까지 유효합니다.
- 파일 생성·교체·삭제는 새 파일 롤백 정리, 커밋 후 이전 파일 삭제, 영속 재시도 증거를 갖는 공통 조정기로 통일합니다.
- CSV는 사용자 입력이 수식 문자로 시작하면 원문 앞에 작은따옴표를 붙인 뒤 기존 CSV 따옴표 이스케이프를 적용합니다.
- 소셜 callback은 토큰 상태를 먼저 확정한 뒤 `/users/me`를 호출하고, 실패하면 부분 로그인 상태를 전부 제거합니다.
- 인수환경은 loopback Vite 한 곳만 공개하고, 정확한 Host·신뢰 프록시·단일 client IP 규칙을 적용합니다. 임의 `Forwarded` 헤더와 wildcard Host/CORS는 허용하지 않습니다.
- Cloudflare URL 하나에서 메일·소셜·Toss callback을 파생하며, 시작 실패나 종료 시 터널을 먼저 닫고 소유 프로세스만 정리합니다.

## 제한과 승인 포인트

현재 코드와 문서만 읽어 설계했으며 업로드 문서 본문, 런타임 로그, live Toss/SMTP/DB, 서버 또는 터널은 확인하지 않았습니다. 따라서 Cloudflare의 실제 헤더 전달, 다중 클라이언트 IP 분리, Toss test callback 등록은 후속 공개 smoke에서 입증해야 합니다.

별도 승인이 필요한 항목은 두 가지입니다. HWP/HWPX/DOC/DOCX를 계속 허용하려면 파서 또는 격리 열람 방식 승인이 필요하며, 기본안은 이를 거부합니다. 파일 재시도용 `storage_mutations` 테이블과 disposable MySQL 적용도 스키마·환경 승인이 선행되어야 합니다. 실제 공개 URL을 클라이언트에게 전달하는 시점 역시 별도 운영 승인 대상입니다.

## 후속 WI

본 WI 완료는 구현 `WI-009`~`WI-017`, 검증 `WI-019`~`WI-022`, 보안·통합 리뷰 `WI-024`~`WI-025`의 체인 트리거입니다. MA는 승인 포인트를 해소한 뒤 각 핸드오프를 즉시 생성·위임해야 합니다.
