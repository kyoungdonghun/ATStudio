# REQ-20260902-ATS-001

[REQ]
REQ ID: REQ-20260902-ATS-001
Project: ATS
Owner: MA
Status: implemented; legacy asset repair remains a separate approved-data operation

[GOAL / WHY]
- 개발·클라이언트 인수테스트·운영 리허설 서버가 DB, public storage, private storage, 공개 URL을 하나의 명시적 Runtime Environment Contract로 사용하도록 정리한다.
- 환경 전환 또는 서버 재기동 후 DB는 남았지만 미디어 파일을 다른 저장소에서 찾는 문제를 사전에 발견하고, acceptance/운영 리허설 환경에서는 잘못된 저장소 설정으로 기동하지 못하게 한다.
- 현재 발견된 기존 음원 3건의 파일 경로 불일치는 무단 데이터 이동 없이 inventory와 복구 후보로 기록한다.

[SCOPE]
- In:
  - 기존 acceptance lifecycle의 외부 환경 묶음, runtime manifest, 시작·상태 점검 방식을 재사용 가능한 기준으로 정리한다.
  - acceptance와 production 성격의 환경에서 public/private storage 경로를 명시적으로 요구하고, 루트 안전성·분리 조건을 시작 전에 검증한다.
  - DB가 참조하는 public/private 파일의 누락을 확인하는 저장소 정합성 검사와 운영자용 확인 경로를 추가한다.
  - 개발·acceptance·운영 리허설의 Runtime Environment Contract, 기동·백업·복구·검증 절차를 현재 문서로 현행화한다.
  - 현재 development DB 기준 파일 누락 inventory와 이관/비활성화 후보를 evidence로 남긴다.
- Out:
  - Toss 실제 결제·환불, 실제 SMTP/OAuth 외부 호출, production DB 변경.
  - 기존 media/attachment 파일의 삭제·이동·덮어쓰기 또는 DB 행 삭제·비활성화.
  - S3 등 외부 object storage 도입.
  - 클라이언트 전용 worktree 또는 이미 실행 중인 클라이언트 서버 변경.

[SUCCESS CRITERIA (DoD)]
- acceptance 성격 환경은 명시적이고 절대 경로인 public/private storage 설정 없이는 기동을 거부한다.
- public/private storage가 동일하거나 포함 관계이면 기동을 거부한다.
- 운영자는 관리자 권한으로 현재 DB 참조 파일의 누락 현황을 확인할 수 있고, private storage key는 API 응답에 노출하지 않는다.
- acceptance 환경의 readiness는 저장소 정합성 누락이 있으면 ready 상태가 되지 않는다.
- development 환경은 누락을 구조화된 경고로 남기고, 전체 서비스가 임의로 중단되지 않는다.
- 현재 development DB의 누락 파일 inventory와 과거 acceptance 저장소의 복구 후보 존재 여부를 secret-safe evidence로 남긴다.
- 새/기존 Track의 업로드·재생·재시작 검증 절차, DB+storage 백업·복구 절차, 환경별 기동 책임이 문서에 명시된다.

- Extra High reasoning effort로 수행한다.
