[GOAL / WHY]
- Toss 정기결제 구독 기능은 구매, 변경, 갱신, 대사, incident 운영까지 P1 흐름이 구현되었다.
- 다음 운영 단계인 환불, 영수증/현금영수증, 정산, 세금계산서 기능은 금전·세무·증빙 경계가 섞이기 쉬우므로, 바로 mutation API를 구현하기 전에 운영 정책과 시스템 경계를 먼저 설계한다.
- 목표는 다음 구현 REQ에서 환불/증빙/정산 기능을 안전하게 나눌 수 있도록, 무엇을 자동화하고 무엇을 수동 운영/외부 시스템으로 남길지 확정하는 것이다.

[SCOPE]
- In:
  - 구독 결제 환불 정책: 전액/부분 환불, 중복 방지, 권한 회수 여부, incident 연계 기준.
  - 영수증/현금영수증 정책: Toss 결제 영수증 링크, 현금영수증 발급/취소 경계, 사용자/관리자 노출 기준.
  - 정산 정책: Toss 정산 조회, 내부 매출 대사, 수수료/지급일/정산 상태 추적 기준.
  - 세금계산서 정책: 전자세금계산서 발급 책임, B2B 증빙 요청, 홈택스/ASP/수동 운영 경계.
  - 다음 구현을 위한 데이터 모델/API/UI 후보와 금지선 정리.
  - SR-93, runbook, payment design, docs index 현행화.
- Out:
  - 실제 Toss refund/cancel API 구현.
  - 현금영수증 발급/취소 API 구현.
  - 정산 조회 API 구현.
  - 전자세금계산서 API 또는 외부 ASP 연동 구현.
  - 관리자 환불/권한 보정 mutation UI 구현.
  - 회계/세무 자문 확정. 운영 전 세무 담당자 또는 세무 대행사의 검토가 필요하다.
