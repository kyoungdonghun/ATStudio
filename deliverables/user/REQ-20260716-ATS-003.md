[GOAL / WHY]
- 현재 공개 데모는 음원, 태그, 플레이리스트 데이터가 적어 화면 밀도와 실제 사용 흐름을 충분히 보여주기 어렵다.
- 클라이언트 캡처와 기능 시연에 사용할 수 있도록 재생 가능한 데모 음원과 자연스러운 분류·묶음 데이터를 충분히 제공한다.
- 일회성 수동 SQL이 아니라 반복 실행과 정리가 가능한 시드 도구로 남겨 이후 데모 환경을 재구성할 수 있게 한다.

[SCOPE]
- In:
  - 현재 `codex/client-demo-stable` 기반 공개 데모 환경에만 가산 적용
  - `QA Demo` 식별자를 가진 활성 트랙 30개 이상 및 실제 재생 가능한 사인파 WAV 생성
  - 장르·무드·사용처를 포함한 태그 30개 이상 생성 및 트랙 연결
  - 데모 구독 계정으로 플레이리스트 8~12개 생성, 각 플레이리스트에 트랙 5~12개 연결
  - 제목, BPM, 조성, 길이, 설명, 파형, 사용처 태그가 화면에서 다양하게 보이도록 구성
  - 재실행 시 중복을 만들지 않는 idempotent 처리와 `QA Demo` 데이터만 정리하는 cleanup 경로 제공
  - 공개 API, 인증 API, 스트리밍, 검색, 플레이리스트 조회 및 브라우저 화면 검증
- Out:
  - 기존 관리자·결제·기업인증·화이트리스트 데이터 변경 또는 삭제
  - 개발 브랜치 기능을 클라이언트 안정 브랜치에 병합
  - 운영 DB 적용, 실제 사용자 계정 변경, 실제 음원 저작물 사용
  - 앨범 더미데이터 생성과 UI 기능 변경

[SUCCESS CRITERIA (DoD)]
- 공개 데모에서 활성 트랙과 태그가 각각 30개 이상 조회된다.
- 생성된 모든 데모 트랙은 상세 및 플레이어에서 재생되고 duration과 waveform이 유효하다.
- 제목 및 Usage Guide Tag 검색으로 데모 트랙을 찾을 수 있다.
- 플레이리스트가 8~12개 존재하고 각 항목에 5~12개 데모 트랙이 연결된다.
- 동일한 시드 명령을 다시 실행해도 데모 데이터 수가 중복 증가하지 않는다.
- cleanup은 `QA Demo` 식별 데이터만 대상으로 하며 기존 데이터는 유지한다.
- 적용 결과와 검증 명령, 생성 수량, 롤백 방법이 Evidence Pack에 기록된다.

[CONSTRAINTS / POLICIES]
- Work tracking unit: WI
- 기존 데이터 삭제는 금지하고 승인된 데모 식별 데이터만 cleanup 대상으로 한다.
- 비밀번호, JWT, DB 접속정보 등 비밀값을 저장소·로그·산출물에 기록하지 않는다.
- 가능한 한 공개된 애플리케이션 API를 사용해 서비스 검증과 동일한 경로로 데이터를 만든다.
- 공개 데모 프로세스와 Cloudflare URL은 유지하고 필요한 경우에만 무중단 범위에서 확인한다.
- 개발 브랜치의 대규모 미커밋 변경과 이번 시드 변경을 섞어 커밋하지 않는다.

[RISKS / OPEN QUESTIONS]
- Risks:
  - 플레이리스트 API는 활성 구독 계정을 요구할 수 있어 현재 테스트 구독 계정의 상태를 먼저 확인해야 한다.
  - WAV 파일 수가 많아 저장공간과 초기 생성 시간이 늘어날 수 있으므로 짧고 서로 다른 길이의 저용량 PCM을 사용한다.
  - 공개 데모가 별도 런타임 DB와 스토리지를 사용하므로 실행 중 프로세스의 실제 runtime root를 확인해야 한다.
