## [GOAL / WHY]

- 현재 구독 결제 기능은 로컬/테스트 기능 단위로 닫을 수 있으나, 실제 운영 서버에서 Toss billing-key 정기결제를 안정적으로 운영하려면 provider 상태 대사와 장애 대응 기준이 필요하다.
- 현행 `PaymentReconciliationService`는 로컬 원장 불일치만 탐지하므로, Toss provider 결제 상태와 로컬 `payment_orders`, `subscription_payments`, `billing_agreements`, `user_subscriptions` 상태를 비교할 수 있어야 한다.
- provider 결제 성공 후 로컬 DB 반영 실패가 발생했을 때 운영자가 주문, 결제, 구독 상태를 추적하고 취소/환불 판단을 할 수 있는 보상 runbook을 준비한다.

## [SCOPE]

### In

- Toss billing-key 결제 주문을 provider API 조회 기반으로 대사한다.
- `paymentKey` 또는 `orderId`, 결제 금액, provider status, 로컬 order/subscription payment 상태를 비교한다.
- webhook은 Toss에서 지원하는 이벤트만 보조 채널로 설계하고, 자동결제 성공 판단의 단독 근거로 삼지 않는다.
- provider 결제 성공 + 로컬 저장 실패 상황에 대한 운영 보상 runbook을 작성한다.
- 운영 서버 Toss live key, secret, CORS, callback URL, log redaction, secret handling 체크리스트를 현행화한다.
- SR-93, payment design, API spec, 관련 운영 문서를 현재 구현에 맞게 갱신한다.
- backend provider reconciliation 테스트와 문서 검증을 수행한다.

### Out

- 실제 환불 자동화.
- admin 결제 mutation API/UI.
- 정산, 영수증, 세금계산서 자동화.
- 멀티서버 scheduler distributed lock.
- blocked legacy endpoint 완전 제거.
- KakaoPay, NaverPay 등 멀티 PG 구현.
- 구독 UX 전면 개편.

## [SUCCESS CRITERIA / DoD]

- Toss provider API 조회 기반 reconciliation이 현행 로컬 reconciliation과 함께 동작한다.
- provider status가 `DONE`인데 로컬 주문이 최종 처리되지 않았거나, 로컬 `DONE` 주문에 결제 row가 없는 경우 운영자가 확인 가능한 결과가 남는다.
- provider success + local persistence failure 대응 절차가 문서화된다.
- 운영 서버 설정 체크리스트가 Toss live/test key, billing auth callback, CORS, secret, log redaction 기준을 포함한다.
- raw billing key, authKey, Toss secret key, raw card data, raw provider payload는 API 응답과 로그에 노출하지 않는다.
- backend 테스트와 문서 검증을 통과하거나, 실행 불가 시 사유가 명확히 기록된다.
- DB 스키마 추가가 필요하다고 판단되면 구현 전에 별도 승인을 받는다.

## [CONSTRAINTS / POLICIES]

- REQ 승인 후 WI 단위로 추적한다.
- 보안 민감 결제 데이터는 서버 내부에서만 다루고, 저장/응답/로그는 sanitize된 값만 사용한다.
- Toss 공식 문서 기준과 현행 코드 기준이 충돌하면 현행 구현을 먼저 보호하고, 문서/설계를 보정한다.
- DB schema migration, 자동 환불, admin mutation은 본 REQ 승인 범위 밖이다.
- P2/P3 운영 항목은 별도 REQ/SR로 분리한다.

## [RISKS / OPEN QUESTIONS]

- Toss webhook은 모든 recurring billing 성공 이벤트의 단독 근거로 쓰기 어렵다. provider API lookup을 중심으로 reconciliation을 설계한다.
- provider 결제 성공 직후 서버가 비정상 종료되면, 어떤 로컬 기록이 남는지 흐름별로 다를 수 있다. 본 REQ에서는 기존 `payment_orders`를 최대한 durable 기준점으로 보강하되, 새 테이블이 필요하면 별도 승인 지점으로 분리한다.
- 실제 환불/취소 자동화는 운영 정책, 회계, Toss 계약 범위가 필요하므로 본 REQ에서는 runbook과 탐지까지만 다룬다.

## [APPROVAL POINTS]

- 본 REQ는 P1 운영 안정화만 수행한다.

- DB 스키마 추가가 필요하면 구현 전에 사용자에게 별도 확인한다.
