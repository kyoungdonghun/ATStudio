# WI-20260714-ATS-036 완료 요약

## 결과

- WI-023에서 발견된 결제 무결성 문제 F-01부터 F-05까지를 구현 가능한 수준으로 설계했습니다.
- 이번 WI는 **설계 완료**이며, 실제 코드 문제가 해결됐다는 뜻은 아닙니다. 구현 패키지 A-G와 독립 검증이 끝날 때까지 결제 후속 승인은 계속 차단됩니다.

## 설계 차단 사항 보정

1. 기존 DB 수동 패치는 `사전검사/중단 → 컬럼 추가 → 데이터 보정·백필 → 인덱스 추가 → 사후검증` 순서로 고쳤습니다. 새 컬럼이 생기기 전에 해당 컬럼을 사용하는 문제가 없습니다.
2. 패키지 B가 `BillingAgreementRepository`의 갱신 및 cleanup/stale 조회 계약을 소유하고 제공합니다. 패키지 C는 A와 B에 의존하며 해당 계약을 소비할 뿐 저장소 파일을 수정하지 않습니다.

## F-01~F-05 설계 결론

| 항목 | 설계된 해결 방향 |
|---|---|
| F-01 갱신 재시도 | 결제 주기와 재시도 날짜를 분리하여 같은 주기는 같은 주문·명령을 유지합니다. |
| F-02 외부 호출 트랜잭션 | 취소, 탈퇴 정리, 유료 업그레이드, 대사를 짧은 로컬 단계와 트랜잭션 없는 Provider 호출로 분리합니다. |
| F-03 환불 중단 복구 | 15분 lease, 동일 키 재조회/재시도, 오래된 처리 결과 차단 규칙을 적용합니다. |
| F-04 Provider 성공 복구 | 정확한 금액·주문·통화·거래 증거가 맞을 때만 `PROVIDER_SUCCEEDED`로 기록하고 목적별 로컬 마무리만 수행합니다. |
| F-05 잠금·동시성 | 하나의 잠금 순서를 강제하고 MySQL 8/InnoDB에서 실제 경쟁 상황을 검증합니다. |

- B: 결제 명령 및 갱신 핵심, 공용 저장소 계약
- C: 구독 취소와 탈퇴 시 결제수단 정리
- D: 차액 결제가 있는 업그레이드

의존 관계는 `A → B → C/D/F`, `A → E`, `B~F → G`입니다.
