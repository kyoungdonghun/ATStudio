[GOAL / WHY]
- ATStudio Toss 정기결제는 구독 결제, 플랜 변경, 갱신, 대사 incident, receipt/audit 기반까지 구현되었다.
- 다음 단계는 실제 환불이 필요한 운영 상황에서 운영자가 수동 Toss 대시보드에만 의존하지 않고, 로컬 환불 원장과 감사 로그를 남긴 뒤 Toss 결제 취소 API를 멱등하게 호출할 수 있게 하는 것이다.
- 환불은 일반 사용자 구독 취소와 다르며, 실제 돈을 되돌리는 provider money movement이므로 admin-only, audited, idempotent 원칙으로 구현한다.

[SCOPE]
- In:
  - `payment_refunds` 환불 원장 테이블/엔티티/Repository/Service 추가.
  - 환불 가능 금액 preview API 추가.
  - 관리자 환불 요청 생성 API 추가.
  - 관리자 환불 요청 승인 API 추가.
  - 관리자 환불 실행 API 추가.
  - Toss `POST /v1/payments/{paymentKey}/cancel` 연동.
  - Toss cancel 요청에 `Idempotency-Key`를 사용하고, 같은 환불 요청 재시도는 같은 멱등키를 사용한다.
  - 전액 환불과 부분 환불을 모두 지원하되, 누적 환불액이 원 결제 금액을 넘지 않도록 로컬에서 차단한다.
  - provider 응답은 sanitized metadata만 저장한다.
  - `payment_operation_audit_logs`에 환불 요청/승인/실행/실패/상태 전이를 기록한다.
  - 관리자 read-only API로 환불 원장 목록/상세를 조회할 수 있게 한다.
  - API spec, DB schema, SR-93, payment runbook, payment policy, final acceptance checklist 현행화.
  - 백엔드 단위/통합 테스트와 문서 검증.
- Out:
  - 사용자 화면에서 환불 요청을 받는 기능.
  - 관리자 환불 UI 탭 구현.
  - 환불 후 구독 권한 자동 보정.
  - 세금계산서/정산/현금영수증 발급·취소 자동화.
  - live key로 실제 운영 환불 테스트.
  - Toss webhook 기반 환불 상태 자동 확정.
  - 다중 PG 환불 어댑터 구현.

[SUCCESS CRITERIA (DoD)]
- 관리자는 특정 `subscription_payment` 또는 그에 연결된 `payment_order`에 대해 환불 가능 금액을 조회할 수 있다.
- 환불 요청은 로컬 `payment_refunds`에 먼저 저장되고, provider 호출 전 고유 idempotency key를 가진다.
- 승인되지 않은 환불 요청은 Toss cancel API를 호출할 수 없다.
- 환불 실행은 Toss cancel API를 호출하고 성공 시 `SUCCEEDED`, 실패 시 `FAILED`, 결과 불명확 시 `PENDING_PROVIDER_CONFIRMATION`으로 기록한다.
- 같은 환불 요청 재실행은 같은 idempotency key를 사용해 중복 환불 위험을 낮춘다.
- 전액/부분 환불 합계가 원 결제 금액을 초과하면 서버가 차단한다.
- 환불 성공이 곧바로 구독 권한 변경을 발생시키지 않는다. 권한 보정은 별도 후속 작업으로 남긴다.
- API/DB/운영 문서가 현행 구현과 맞는다.
- backend tests, docs validation, diff check가 통과한다.

[RISKS / OPEN QUESTIONS]
- Risks:
  - 환불 성공 후 로컬 저장 실패가 발생하면 provider와 로컬 원장이 어긋날 수 있다. 따라서 provider 호출 전 원장을 만들고, 결과 불명확 상태를 보존해야 한다.
  - 부분 환불은 여러 번 가능하므로 누적 환불액 계산과 동시성 제어가 필요하다.
  - 환불 후 권한 보정을 자동으로 섞으면 돈/권한 두 mutation이 한 흐름에 묶여 감사가 어려워진다.
  - Toss cancel API 응답 구조 변경 가능성이 있으므로 provider payload는 allowlist sanitizer로만 저장해야 한다.
- Questions:
  - 환불 승인/실행을 같은 ADMIN이 수행해도 되는가? 기본안은 현재 소규모 운영 전제에서 허용하되, audit log에 actor를 모두 남긴다.
  - 부분 환불을 이번 1차에서 허용할까? 기본안은 허용하되, 금액 초과 차단과 reason 필수로 제한한다.
  - 환불 성공 후 구독 권한 보정은 자동이 아니라 별도 후속 작업으로 남기는 데 동의하는가?
