# REQ-20260518-ATS-001: 결제 UX 및 운영 안정화 설계

[REQ]
REQ ID: REQ-20260518-ATS-001
Project: ATS
Owner: MA
Status: approved

[GOAL / WHY]
- Toss 일회성 결제와 Toss 빌링키 기반 정기결제가 구현된 상태에서, 실제 사용자 흐름과 운영자가 다룰 결제 상태를 더 안정적으로 설계한다.
- 현재 결제 진행 화면은 디버깅과 진행 상태 확인을 위해 구독 결제 페이지 안에 고정된 형태가 남아 있으므로, 실제 서비스 UX에 맞는 결제 창 분리, 실패/복귀 처리, 상태 안내, 운영 추적 기준을 정리한다.
- 클라이언트 피드백이나 SR 작업으로 넘기기 전에, 결제 흐름의 사용자 경험과 운영 기준을 문서 수준에서 먼저 확정한다.

[SCOPE]
- In:
  - Toss 결제/빌링 인증 화면을 구독 페이지 안에 고정할지, 팝업/새 창/전용 콜백 화면으로 분리할지 UX 정책을 정한다.
  - 결제 진행 중 서버 재시작, 브라우저 새로고침, 모바일 인증 후 PC 복귀, 중복 시도, 만료 주문 재시도 상황의 사용자 안내와 복구 흐름을 정의한다.
  - 구독 관리 화면에서 자동 갱신 상태, 다음 결제일, 실패 유예, 자동 갱신 해지 상태를 어떻게 보여줄지 정한다.
  - 운영자가 결제 주문, 구독 결제 이력, 빌링 계약 상태를 확인하기 위한 최소 관리 화면/API 요구사항을 사용자 결제 UX와 같은 범위에서 정한다.
  - Toss webhook, 환불, 영수증, 정산은 지금 바로 구현하지 않더라도 후속 SR/REQ로 분리할 기준을 정한다.
  - 기존 결제 설계 문서, UI 문서, API/DB 문서와 충돌하지 않도록 현행 구현과 문서 갭을 정리한다.
- Out:
  - 실제 코드 구현.
  - PG를 Toss 외 KakaoPay, Naver Pay 등으로 확장하는 구현.
  - 실결제 운영 키 적용 및 운영 배포.
  - 회계 정산, 세금계산서, 전자영수증 자동 발행의 상세 구현.
  - 클라이언트 피드백 수집 이후의 SR 처리.

[SUCCESS CRITERIA (DoD)]
- 결제 시작부터 성공/실패/취소/복귀/재시도까지 사용자 화면 흐름이 문서로 설명된다.
- 현재 페이지 고정형 Toss 결제 UX를 유지할지, 팝업/전용 화면으로 분리할지에 대한 권장안과 근거가 정리된다.
- 결제 실패와 빌링 실패를 사용자-facing 상태와 운영-facing 상태로 나누어 정의한다.
- 운영자가 최소한 어떤 결제/구독 상태를 확인해야 하는지 API/UI 후보가 정리된다.
- Toss webhook, 환불, 영수증, 정산, 다중 PG 확장은 이번 범위에서 제외하거나 별도 후속 항목으로 명확히 분리된다.
- 승인 후 바로 WI로 나눌 수 있을 만큼 산출물과 검증 기준이 정리된다.

[CONSTRAINTS / POLICIES]
- Work tracking unit: WI
- REQ 승인 전에는 구현 파일을 수정하지 않는다.
- 결제 secret, billing key, customerKey, authKey는 민감 정보로 취급한다.
- 실제 결제가 발생하는 검증은 금지하며, 로컬/테스트 키/Mock 기준을 유지한다.
- 결제 UX 변경은 기존 구독 접근 정책(`ACTIVE`, `CANCELLED` grace period)과 충돌하면 안 된다.
- 문서 산출물은 영어 문서 체계를 따르되, REQ는 사용자 승인 문서이므로 한국어로 작성한다.

[RISKS / OPEN QUESTIONS]
- Risks:
  - 팝업/새 창 방식은 브라우저 차단, 모바일 인증 복귀, 라우팅 복구 문제가 생길 수 있다.
  - 페이지 고정형 방식은 디버깅과 복구에는 좋지만 실제 서비스 UX로는 결제 창이 페이지에 박혀 보일 수 있다.
  - 운영 화면을 과하게 넓히면 환불/정산/웹훅까지 범위가 커질 수 있다.
- Resolved Decisions:
  - 이번 REQ는 `사용자 결제 UX 분리`와 `운영자 결제/구독 상태 관리`를 같은 설계 범위로 묶어 진행한다.
  - `webhook`, `환불`, `영수증`, `정산`, `다중 PG 확장`은 이번 설계에서 후속 후보로 정리하되 구현 범위에는 포함하지 않는다.
