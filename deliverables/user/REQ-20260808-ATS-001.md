[GOAL / WHY]
- 인수 테스트에서 확인된 관리자 태그 관리 문제 두 건을 서로 독립적인 Screen Review(SR) 문서로 기록한다.
- 중복 태그 저장 실패를 정상적인 사용자 오류 피드백 흐름으로 개선할 요구를 명확히 한다.
- 태그 이름의 공백·특수문자 입력 규칙은 현재 구현과 외부 음악 서비스 사례를 근거로 정책 결정이 가능하도록 정리한다.

[SCOPE]
- In:
  - `SR-94`: 태그 이름 중복 생성·수정 시 관리자 화면이 `Failed to save tag` 오류 화면으로 대체되는 흐름 개선 요구
  - `SR-95`: 태그 이름의 앞뒤 공백, 내부 공백, 연속 공백, 특수문자 허용 규칙 조사 및 권고안
  - `docs/SR/index.md`, `docs/index.md`의 번호·상태·문서 개수 동기화
  - 현재 프론트엔드·백엔드·예외 정책과 Splice 등 공식 음악 서비스 분류 사례를 근거로 사용
- Out:
  - React/Spring Boot 코드 수정
  - DB 스키마 또는 기존 태그 데이터 변경
  - 태그 입력 정책의 최종 확정 및 구현
  - SR 이외의 활성 설계·정책 문서 변경

[SUCCESS CRITERIA (DoD)]
- `docs/SR/SR-94.md`와 `docs/SR/SR-95.md`가 각각 하나의 독립된 목적을 가진다.
- SR-94는 백엔드의 `409 TAG_NAME_DUPLICATED` 계약 유지, 프론트 사전 안내, 서버 응답 처리, 관리 화면 유지 요구를 구분한다.
- SR-95는 현재 확정된 규칙과 미확정 영역을 분리하고, 앞뒤 trim·내부 공백·허용 특수문자에 대한 권고와 결정 필요 항목을 담는다.
- 두 SR은 `OPEN`으로 인덱싱되고 전체 문서 개수가 실제 파일 수와 일치한다.
- 문서 링크, Markdown, Git diff 기계 검증이 통과한다.

[CONSTRAINTS / POLICIES]
- Work tracking unit: WI
- SR은 인수 테스트 시점의 발견 사항과 요청을 보존하는 Historical Record로 작성한다.
- 확인된 현재 동작, 사용자 요구, 제안, 미확정 정책을 섞지 않는다.
- 백엔드 검증은 동시성·직접 API 호출을 고려한 최종 방어선으로 유지한다.
- 외부 사례는 공식 서비스 페이지 또는 공식 도움말만 근거로 사용한다.
- 기존 사용자 변경과 추적되지 않은 파일은 수정하지 않는다.
