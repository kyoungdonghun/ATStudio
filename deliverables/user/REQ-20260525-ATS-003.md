[GOAL / WHY]
- Toss 정기결제 구독은 결제, 플랜 변경, 갱신, reconciliation incident 운영까지 구현되었다.
- 환불/영수증/정산/세금계산서 운영 정책 문서(REQ-20260525-ATS-002)는 다음 구현 순서로 결제 운영 감사 원장과 영수증 근거 저장을 먼저 권고했다.
- 목표는 실제 환불 mutation이나 세무 자동화에 들어가기 전에, 성공 결제의 receipt evidence와 관리자의 결제 운영 변경 이력을 로컬 DB에 남기는 기반을 만드는 것이다.

[SCOPE]
- In:
  - `payment_receipts` 저장 모델 추가.
  - `payment_operation_audit_logs` 저장 모델 추가.
  - Toss 정기결제 성공 응답의 안전한 영수증/현금영수증 근거 필드만 저장.
  - 최초 구독 결제, 업그레이드 차액 결제, 갱신 결제 성공 시 영수증 근거 저장.
  - reconciliation incident status 변경 시 관리자 감사 로그 저장.
  - 관리자 read-only API로 영수증 근거와 결제 운영 감사 로그 조회 제공.
  - DB 스키마, API 문서, 결제 운영 정책/런북/SR-93 현행화.
  - 단위 테스트 및 문서 검증.
- Out:
  - Toss refund/cancel API 실행.
  - 현금영수증 발급/취소 API 실행.
  - 정산 조회/import 구현.
  - 세금계산서 요청/발급 workflow 구현.
  - 관리자 결제 mutation UI 구현.
  - 사용자 영수증 화면 구현.

[SUCCESS CRITERIA (DoD)]
- 성공 결제에서 provider receipt URL 또는 cash receipt 근거가 있으면 중복 없이 저장된다.
- 저장 필드는 영수증 URL, receipt key, payment key, 발급 시각 등 운영 근거에 필요한 최소 정보로 제한된다.
- billing key, authKey, customerKey, 카드 원문, raw provider payload는 저장하지 않는다.
- reconciliation incident 상태 변경은 actor, before/after status, note, 대상 incident/order 정보를 감사 로그로 남긴다.
- 관리자 API로 payment receipts와 operation audit logs를 page 기반으로 조회할 수 있다.
- DB/API/운영 문서가 현행 구현과 맞는다.
- backend focused tests, compile/test gate, docs validation, diff check가 통과한다.
