[GOAL / WHY]
- ATStudio의 설계문서, 현행 코드, 현행 문서를 동일한 기준선에서 대조하여 취약점, 누락, 오기입, 구현-문서 불일치, 운영 위험, 테스트 공백, 개선 가능성을 전수조사한다.
- 결제, 화이트리스트, 기업 인증을 포함해 누적된 기능이 설계 의도와 실제 동작에 맞는지 증거로 확인하고, 수정 우선순위와 후속 작업 범위를 확정한다.
- 모델의 추론 능력에만 의존하지 않고 파일, 코드 경로, 테스트 결과, 재현 절차를 근거로 모든 판단을 추적 가능하게 남긴다.

[SCOPE]
- In:
  - 현재 브랜치와 미커밋 변경을 포함한 감사 기준선 및 자산 목록 확정
  - Tier 0 표준, 설계, UI, 정책, 결제, 클라이언트, 레지스트리, REQ/WI/SR 문서의 상호 참조와 현행성 조사
  - Spring Boot 백엔드의 API, 인증/인가, 서비스 상태 전이, 트랜잭션, 외부 결제 연동, 스케줄러, 예외 처리, 데이터 보호 조사
  - React 프론트엔드의 라우팅, 권한별 화면, API 계약, 상태 처리, 오류/빈 상태, UX 문구, 민감정보 노출 조사
  - JPA 엔티티, `schema.sql`, 수동 DB 패치, 인덱스, 제약조건, 운영 환경변수 및 배포 전제 조사
  - 결제, 화이트리스트, 기업 인증, 회원/권한, 구독, 음원/검색, 관리자 기능을 포함한 기능별 3-way 정합성 매트릭스 작성
  - 백엔드 테스트, 프론트 테스트, typecheck, ESLint, build, 문서 검증 결과와 테스트 공백 조사
  - 각 발견사항을 심각도, 근거, 영향, 재현 방법, 권장 조치, 정책 결정 필요 여부로 분류
  - 현재 작업 중인 `docs/client/` 개편 문서와 생성된 클라이언트 PDF를 감사 기준선에 포함
- Out:
  - 운영 DB 또는 운영 결제 Provider에 대한 쓰기 작업
  - 데이터 삭제, 스키마 적용, 환불, 결제, 이메일 전송 등 외부 상태 변경
  - 발견사항의 일괄 코드 수정 및 배포
  - 외부 침투 테스트, 부하 테스트, 법률/세무 적합성의 최종 인증

[SUCCESS CRITERIA (DoD)]
- 조사 대상 문서, 코드, API, 화면, 테이블, 설정, 테스트의 범위와 제외 사유가 기록된다.
- 핵심 기능마다 설계 의도, 코드 구현, 현행 문서가 한 행에서 비교되는 3-way 정합성 매트릭스가 작성된다.
- 모든 발견사항은 확인된 근거 경로 또는 실행 결과를 가지며, 추정은 추정으로 명시된다.
- 보안/개인정보, 결제 정합성, 권한, DB 마이그레이션, 운영 복구 관점이 독립적으로 검토된다.
- P0/P1/P2/P3 우선순위와 함께 즉시 수정, 정책 결정 후 수정, 후순위 개선, 유지의 네 가지 처분안이 제시된다.
- 문서 및 코드 카운트, API 계약, 상태 전이, 사용자 문구의 불일치가 식별된다.
- 관련 품질 명령의 성공/실패/미실행 사유가 그대로 기록된다.
- 최종 감사 보고서와 후속 수정 작업 후보가 사용자 승인 가능한 형태로 제공된다.

[CONSTRAINTS / POLICIES]
- Work tracking unit: WI
- 승인 전에는 감사 기준선을 변경하지 않는다.
- 미커밋 변경은 사용자 자산으로 간주하며 되돌리거나 덮어쓰지 않는다.
- 보안 비밀값은 값 자체를 출력하거나 문서에 저장하지 않고 존재 여부와 설정 방식만 확인한다.
- 운영/로컬 DB 변경, 데이터 삭제, 외부 Provider 호출 등 상태 변경은 별도 사전 승인을 받는다.
- 문서와 설계보다 현행 코드를 무조건 우선하지 않으며, 불일치는 정책 미확정과 구현 결함으로 구분한다.
- 모델 버전이나 과거 기억은 참고 자료일 뿐이며, 현재 저장소에서 재검증된 사실만 확정으로 보고한다.

[RISKS / OPEN QUESTIONS]
- Risks:
  - 현재 워킹트리에 클라이언트 문서 개편과 PDF가 미커밋 상태이므로, 감사 중 기준선이 바뀌면 결과가 흔들릴 수 있다.
  - 저장소 규모와 누적 문서가 커서 단순 파일 카운트만으로는 의미 있는 전수조사가 되지 않을 수 있다.
  - 외부 Toss 상태, 운영 DB, 운영 환경변수는 읽기 권한이 없으면 코드와 문서 기준의 정적 검토로 제한된다.
  - 테스트 성공만으로 정책·UX·운영 복구의 적합성을 보장할 수 없으므로 별도 수동 판단이 필요하다.
- Questions (minimal):
  - 현재 미커밋 `docs/client/` 개편과 `output/pdf/atstudio-client-testing-guide.pdf`를 그대로 포함한 워킹트리를 공식 감사 기준선으로 승인할지 확인이 필요하다.
