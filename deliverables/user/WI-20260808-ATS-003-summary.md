# WI-20260808-ATS-003 Work Summary

## 결론

- 현재 구현에서는 **관리자가 자기 자신을 포함한 어떤 관리자도 `USER`로 강등할 수 있다.**
- 프론트엔드는 모든 사용자 행에 `USER`/`ADMIN` 선택지를 노출하고, 백엔드는 요청자와 대상자의 관계 또는 남은 관리자 수를 확인하지 않은 채 역할을 저장한다.
- 마지막 관리자도 강등할 수 있으므로 관리자 계정이 0명이 되는 운영 잠금 상태가 가능하다. 이 판단은 코드 경로를 정적으로 확인한 결과이며, DB를 변경하는 실동작 재현은 수행하지 않았다.
- 단순히 프론트에서 선택지를 비활성화하거나 백엔드에서 관리자 수만 세는 방식은 충분하지 않다. 서버의 트랜잭션 안에서 공통 잠금 지점을 잡고 요청자 권한과 마지막 관리자 불변조건을 다시 확인해야 한다.

## 현재 사실

| 영역 | 확인 결과 |
| --- | --- |
| 관리자 UI | 현재 로그인 사용자를 구분하지 않고 모든 행에 역할 선택기를 표시함 |
| API 권한 | `PUT /api/users/{userId}`는 요청 시작 시 `ADMIN` 여부만 검사함 |
| 서비스 | 대상 사용자를 일반 조회한 뒤 요청된 역할을 그대로 반영함 |
| 마지막 관리자 보호 | 없음 |
| 자기 강등 보호 | 없음 |
| 동시 변경 보호 | 역할 변경 경로에서는 잠금과 직렬화가 없음 |
| 감사 | 역할 변경 전용 감사 기록이 없음 |
| 운영 복구 | 운영용 관리자 복구 절차를 찾지 못함. QA 부트스트랩은 비운영 환경 전용임 |

## 인증 세션 판정

- 액세스 토큰에는 발급 당시 역할이 들어가지만, 서버 필터는 유효한 요청마다 토큰의 사용자 ID로 DB 사용자를 다시 조회하고 **현재 DB 역할**로 권한을 구성한다.
- 따라서 강등 전 발급된 액세스 토큰이 다음 요청에서도 관리자 권한을 유지하는 구조는 아니다. 강등 직후 다음 관리자 API 요청은 서버에서 거절된다.
- 반면 React는 로컬 저장소에 저장된 사용자 역할로 관리자 라우트를 판단하며, 토큰 갱신 시 사용자/역할 상태를 다시 읽지 않는다. 그 결과 강등된 사용자가 관리자 화면에 남아 있다가 API `403`을 만나는 화면·서버 불일치가 생길 수 있다.
- Refresh Token도 역할 변경 시 폐기되지 않지만, 갱신 시 DB의 현재 역할로 새 토큰이 만들어진다. 권한 지속 문제와 별개로 역할 강등 시 세션 종료·재인증 정책은 명시할 필요가 있다.

## 권고 정책

### 서버 불변조건

1. `ADMIN -> USER`는 **요청자와 대상자가 서로 다를 때만** 허용한다. 자기 강등은 서버에서 거절한다.
2. 강등 후에도 삭제되지 않은 유효 관리자 계정이 최소 1개 이상 남아야 한다.
3. 운영 안정성을 위해 정상 상태에서는 소유자 관리자와 복구 관리자 등 최소 2개를 유지하도록 별도 운영 기준을 둔다.
4. 역할 변경은 현재 요청자를 서비스에 전달하고, 트랜잭션 내부에서 요청자가 여전히 유효한 `ADMIN`인지 다시 확인한 뒤 적용한다.

### 동시성

- 서로 다른 두 관리자가 동시에 상대를 강등할 수 있으므로 `countBy...` 결과만 확인하거나 대상 사용자 행만 잠그는 방식은 안전하지 않다.
- 모든 관리자 역할 변경이 공유하는 직렬화 지점이 필요하다. 예시는 전용 단일 guard 행을 `PESSIMISTIC_WRITE`로 잠그는 방식 또는 활성 관리자 집합을 고정된 순서로 잠그는 방식이다.
- 공통 잠금 획득 후 요청자·대상자·현재 관리자 수를 다시 확인하고, 그 뒤 강등과 성공 감사를 한 트랜잭션으로 저장해야 한다.

### UI와 오류 처리

- 자기 행의 `ADMIN -> USER` 선택지는 비활성화하고 이유를 바로 표시한다.
- 마지막 관리자 강등은 서버의 명시적 충돌 오류 코드로 거절하며, 프론트는 목록 전체를 오류 페이지로 바꾸지 말고 해당 모달/행에 이유를 표시한다.
- 다른 관리자를 강등할 때는 대상 ID 또는 닉네임, 변경 전·후 역할, 영향, 재인증 여부를 확인창에 표시한다.
- 본인 역할이 서버에서 바뀐 사실을 감지하면 최신 `/users/me` 정보를 다시 읽고 라우트를 재평가한다. 자기 강등을 금지하더라도 다른 관리자가 현재 세션 사용자를 강등할 수 있으므로 필요하다.

### 세션·감사·복구

- 관리자 강등 성공 시 대상 계정의 Refresh Token을 폐기하고 재인증을 요구하는 정책을 우선 권고한다. 현재 액세스 토큰도 서버에서는 즉시 USER 권한으로 평가되지만, 세션 종료는 화면 상태와 운영 기대를 일치시킨다.
- 역할 변경 감사에는 요청자 ID, 대상자 ID, 변경 전·후 역할, 결과, 거절 사유, 시각을 남긴다. 이메일, 토큰, 비밀번호, 전체 사용자 프로필은 기록하지 않는다.
- 성공 감사는 역할 변경과 같은 트랜잭션에 저장하고, 거절 시도는 롤백되지 않는 보안 이벤트 채널에 최소 정보로 남긴다.
- 운영 복구는 공개 API나 비운영 QA 부트스트랩을 재사용하지 않는다. 승인된 장애 티켓, 2인 확인, 백업/스냅샷, 실행 전후 관리자 수 확인, 감사 기록을 포함하는 제한된 콘솔 또는 DB 복구 절차를 별도로 정의한다.

## 필수 테스트

- 관리자 1명일 때 자기 강등과 타인에 의한 마지막 관리자 강등이 모두 거절되는지 확인
- 관리자 2명 이상일 때 다른 관리자 강등은 허용되고 관리자 수가 최소 1명으로 유지되는지 확인
- 두 관리자가 동시에 서로를 강등해도 최종 유효 관리자 수가 1명 이상인지 실제 MySQL 동시성 테스트로 확인
- 잠금 대기 중 요청자 자신이 먼저 강등된 경우, 해당 요청이 서비스 계층 재검증에서 거절되는지 확인
- 삭제된 관리자, 이미 USER인 대상, 역할 변경 없는 요청, 승격 요청의 경계 조건 확인
- 강등 직후 기존 액세스 토큰으로 관리자 API가 `403`이고, 일반 사용자 권한만 남는지 확인
- Refresh Token 폐기 또는 현재 역할 재발급 정책, React 역할 재동기화와 관리자 라우트 이탈 확인
- 성공·거절 감사의 요청자/대상/전후 역할/사유 기록과 민감정보 미기록 확인
