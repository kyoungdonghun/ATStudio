[GOAL / WHY]
- ATStudio 정기결제, 환불, 영수증 근거, 운영 감사 로그, 환불 후 권한 보정 기반은 구현되어 있다.
- 아직 Toss 또는 운영자가 제공하는 정산 자료를 내부 결제/환불 원장과 대조하는 기능은 없다.
- 목표는 ATStudio 자체 구독 매출의 PG-to-merchant 정산 자료를 안전하게 import하고, 내부 `subscription_payments`/`payment_refunds`와 대조하여 운영자가 회계 불일치를 확인할 수 있게 하는 것이다.
- Toss 정산 조회 기능/API는 provider-side 원천 자료로 인정하되, 첫 구현은 운영 규모와 검증 용이성을 고려해 CSV 기반 수동 import adapter를 우선한다. Excel 원본은 CSV로 export한 뒤 import한다.
- settlement source는 adapter 구조로 열어둔다. 1차 source는 CSV 수동 import, 2차 source 후보는 Toss Settlement API 자동 조회다.

[SCOPE]
- In:
  - settlement import/reconciliation 상세 설계를 확정한다.
  - `payment_settlements` 또는 동등한 settlement ledger를 추가한다.
  - 관리자 CSV import API를 제공한다.
  - settlement source abstraction을 둬서 추후 Toss Settlement API adapter를 추가할 수 있게 한다.
  - import row별 원본 파일/행 번호/중복키/정산 기준일/지급 예정일/금액/수수료/환불액/순정산액을 저장한다.
  - 내부 결제/환불 원장과 정산 row를 대조해 `MATCHED`, `MISMATCHED`, `LOCAL_PAYMENT_NOT_FOUND`, `PROVIDER_SETTLEMENT_NOT_FOUND`, `IGNORED` 등 운영 상태를 관리한다.
  - `/admin/payments` 또는 별도 관리자 결제 운영 화면에 정산 조회/필터/불일치 확인 UI를 추가한다.
  - 정산 import와 reconciliation 결과를 `payment_operation_audit_logs` 또는 별도 audit 경로에 남긴다.
  - 설계 문서, API spec, DB schema, SR-93, UI 문서, 인수테스트 체크리스트를 현행화한다.
- Out:
  - Toss 정산 API 자동 연동 구현. 단, 추후 adapter 추가가 가능한 구조와 문서 경계는 포함한다.
  - 실제 입금 확인 자동화 또는 은행 거래내역 연동.
  - 세금계산서 request/admin workflow.
  - cash receipt 발급/취소 자동화.
  - 창작자 royalty settlement 또는 seller payout.
  - 사용자 구독 권한 변경.
  - 환불 실행 또는 결제 취소 mutation 변경.
  - multi-PG 정산 포맷 통합.

[SUCCESS CRITERIA (DoD)]
- 운영자가 정해진 settlement CSV 템플릿을 업로드할 수 있다.
- 업로드된 정산 row는 중복 import 없이 settlement ledger에 저장된다.
- 내부 결제/환불 원장과 대조하여 금액, 환불액, 수수료, 순정산액, 지급 예정일 불일치를 식별한다.
- 정산 row는 사용자 구독 권한이나 결제 상태를 자동 변경하지 않는다.
- 관리자 화면에서 정산 import 결과와 mismatch row를 조회할 수 있다.
- 민감정보 원칙을 지켜 raw card data, Toss secret, billing key, authKey, customerKey, raw provider payload를 저장/노출하지 않는다.
- backend tests, frontend typecheck/lint/build, docs validation, `git diff --check`가 통과한다.

[CONSTRAINTS / POLICIES]
- Work tracking unit: WI.
- REQ 승인 이후 구현한다.
- 정산은 ATStudio 자체 구독 매출의 PG-to-merchant 정산만 다룬다.
- Toss settlement API는 후속 adapter 후보로 남기며, 첫 구현이 provider API 확장을 막지 않아야 한다.
- creator payout, seller payout, royalty settlement는 별도 도메인으로 분리한다.
- settlement row는 회계/운영 근거이며, 구독 권한의 source of truth가 아니다.
- import는 append-first 정책을 따른다. 잘못 올린 row는 삭제보다 `IGNORED`/재import/상태 변경으로 추적한다.
- CSV 파일 원본의 민감정보는 최소화하고, 저장 payload는 support-safe 필드만 허용한다.
- 운영자가 확인 가능한 mismatch를 만들되, 자동 환불/자동 권한보정은 수행하지 않는다.

[RISKS / OPEN QUESTIONS]
- Risks:
  - Toss 정산 CSV 컬럼은 운영자가 내려받는 실제 파일 포맷과 다를 수 있으므로, 첫 구현은 명시 템플릿과 validation error를 선명하게 제공해야 한다.
  - 수수료/VAT/환불 반영 시점은 PG 정산 정책에 따라 달라질 수 있어, 내부 결제 성공일만으로 정산 완료를 판단하면 안 된다.
  - 정산 mismatch를 결제 장애나 구독 권한 장애로 오해하면 안 된다. 정산 대사는 회계/입금 검증용이다.
- Questions:
  - 없음. CSV 수동 import 우선, Toss Settlement API는 후속 adapter 후보로 승인한다.

[APPROVAL POINTS]
- 승인됨:
  - Settlement import/reconciliation을 별도 기능으로 진행한다.
  - 첫 구현은 Toss API 자동 연동이 아니라 CSV 수동 import 우선으로 진행하되, Toss Settlement API adapter를 추가할 수 있는 구조로 둔다.
  - 정산 기능은 사용자 구독 권한, 결제 상태, 환불 실행을 자동 변경하지 않는다.
  - Tax invoice, cash receipt mutation, creator payout, multi-PG 정산은 이번 범위에서 제외한다.
