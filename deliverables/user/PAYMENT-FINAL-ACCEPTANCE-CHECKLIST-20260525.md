# Payment Final Acceptance Checklist

작성일: 2026-05-25  
대상: ATStudio Toss 정기결제, 구독 변경, 운영 대사/incident 기능  
목적: 최종 인수테스트 시 사용자가 직접 확인할 항목을 한 문서에서 추적한다.

## 0. 테스트 준비

| 체크 | 항목 | 기대 결과 | 메모 |
|------|------|-----------|------|
| [ ] | 테스트 서버가 최신 `dev/kyoung` 기준으로 실행된다. | 결제 관련 최신 UI/API가 반영되어 있다. | |
| [ ] | Toss 테스트 키 환경이 적용되어 있다. | 결제수단 등록 화면이 Toss 테스트 환경으로 열린다. | |
| [ ] | 테스트 계정의 기존 구독 상태를 정리한다. | 신규 가입, 변경, 취소 흐름을 독립적으로 볼 수 있다. | |
| [ ] | 관리자 계정으로 `/admin/payments` 접근이 가능하다. | `결제 운영` 화면과 `대사 Incident` 탭을 볼 수 있다. | |

## 1. 신규 정기 구독 가입

| 체크 | 항목 | 기대 결과 | 메모 |
|------|------|-----------|------|
| [ ] | 구독 페이지에서 플랜과 월간/연간 주기를 선택한다. | 결제수단 등록 흐름으로 이동한다. | |
| [ ] | 카드 등록을 완료한다. | 빌링키가 등록되고 최초 1회 결제가 진행된다. | |
| [ ] | 구독 관리 화면으로 돌아온다. | 현재 플랜, 결제 주기, 시작일, 만료일, 다음 결제일이 표시된다. | |
| [ ] | 결제 정보 영역을 확인한다. | 상태가 `자동 갱신 중`이고 결제수단이 마스킹되어 표시된다. | |
| [ ] | 구독 권한이 필요한 기능에 접근한다. | 구독 플랜 기준으로 접근/사용이 가능하다. | |

## 2. 결제수단 등록 중 이탈/재등록

| 체크 | 항목 | 기대 결과 | 메모 |
|------|------|-----------|------|
| [ ] | 결제수단 등록 화면으로 진입한 뒤 중간에 다른 화면으로 이동한다. | 구독 관리 화면에서 다시 등록을 이어갈 수 있는 버튼/흐름이 보인다. | |
| [ ] | 등록 진행 중 상태를 확인한다. | `등록 진행 중`과 `등록됨`처럼 서로 충돌하는 문구가 표시되지 않는다. | |
| [ ] | 결제수단을 다시 등록한다. | 정상적으로 자동결제 수단이 활성화된다. | |
| [ ] | 삭제된 Toss billing key 상황을 재현하거나 기존 문제가 있는 계정으로 업그레이드를 시도한다. | 사용자가 결제수단을 다시 등록하도록 안내되고, 낡은 billing key로 결제를 계속 시도하지 않는다. | |

## 3. 업그레이드

| 체크 | 항목 | 기대 결과 | 메모 |
|------|------|-----------|------|
| [ ] | 낮은 플랜에서 높은 플랜으로 변경 미리보기를 연다. | 변경 유형이 `오늘 변경` 또는 업그레이드로 명확히 보인다. | |
| [ ] | 즉시 결제 차액을 확인한다. | 남은 기간 기준 차액이 표시된다. | |
| [ ] | 월간에서 월간 상위 플랜으로 업그레이드한다. | 차액 결제 후 플랜이 즉시 상위 플랜으로 바뀐다. | |
| [ ] | 연간에서 연간 상위 플랜으로 업그레이드한다. | 남은 연간 기간 기준 차액 결제 후 플랜이 즉시 바뀐다. | |
| [ ] | 연간 구독에서 월간 상위 플랜으로 업그레이드한다. | 즉시 플랜 변경, 현재 결제일 유지, 다음 결제일부터 월간 주기 적용이 일관되게 안내된다. | |
| [ ] | 업그레이드 후 구독 카드와 플랜 변경 영역을 확인한다. | 현재 플랜과 예약 상태가 서로 모순되지 않는다. | |

## 4. 다운그레이드와 예약 변경

| 체크 | 항목 | 기대 결과 | 메모 |
|------|------|-----------|------|
| [ ] | 높은 플랜에서 낮은 플랜을 선택한다. | 즉시 결제 없이 다음 결제일부터 적용되는 예약 변경으로 안내된다. | |
| [ ] | 다운그레이드를 확정한다. | 현재 만료일까지 기존 플랜 권한이 유지된다. | |
| [ ] | 예약된 플랜을 다른 플랜으로 다시 변경한다. | 기존 예약이 새 예약으로 교체된다. | |
| [ ] | 예약 취소를 누른다. | 예약이 해제되고 현재 플랜/주기가 유지된다. | |
| [ ] | 현재 플랜을 선택했을 때의 버튼/문구를 확인한다. | 예약이 없으면 불필요한 `예약 해제` 액션이 노출되지 않는다. 예약이 있을 때만 예약 취소가 의미 있게 보인다. | |

## 5. 구독 취소와 취소 철회

| 체크 | 항목 | 기대 결과 | 메모 |
|------|------|-----------|------|
| [ ] | 구독 취소를 진행한다. | 즉시 권한 박탈이 아니라 현재 결제기간 종료 시점까지 사용 가능하다고 안내된다. | |
| [ ] | 취소 후 구독 관리 화면을 확인한다. | 만료일까지 사용 가능하며, 취소 상태가 명확히 표시된다. | |
| [ ] | 취소 후 취소 철회를 진행한다. | 자동 갱신 상태로 복구된다. | |
| [ ] | 취소 상태에서도 플랜 변경 가능 여부를 확인한다. | 정책상 허용된 변경/복구 흐름이 막히지 않는다. | |

## 6. 갱신, 실패, 만료

| 체크 | 항목 | 기대 결과 | 메모 |
|------|------|-----------|------|
| [ ] | 갱신 스케줄러 또는 테스트용 날짜 조정으로 다음 결제를 재현한다. | 등록된 billing key로 정기 결제가 시도된다. | |
| [ ] | 갱신 성공 후 결제내역을 확인한다. | 결제 주문, 구독 결제 row, 다음 결제일이 일관되게 갱신된다. | |
| [ ] | 결제 실패를 재현한다. | 실패 횟수, 유예 기간, 재시도 상태가 정책대로 반영된다. | |
| [ ] | 유예 기간 종료 또는 구독 만료 상태를 확인한다. | 구독 권한이 필요한 기능이 차단된다. | |
| [ ] | 만료 후 새 정기결제로 다시 가입한다. | 신규 billing key 등록과 최초 결제가 정상 진행된다. | |

## 7. 관리자 결제 운영 화면

| 체크 | 항목 | 기대 결과 | 메모 |
|------|------|-----------|------|
| [ ] | 관리자 계정으로 `/admin/payments`에 접속한다. | `주문`, `자동결제`, `결제내역`, `대사 Incident` 탭이 보인다. | |
| [ ] | 일반 사용자 계정으로 `/admin/payments` 접근을 시도한다. | 접근이 차단된다. | |
| [ ] | 주문 탭을 확인한다. | 결제 주문의 주문번호, 사용자, 목적, PG, 상태, 금액, 실패 코드가 보인다. | |
| [ ] | 자동결제 탭을 확인한다. | billing key 원문 없이 마스킹된 결제수단과 상태만 보인다. | |
| [ ] | 결제내역 탭을 확인한다. | 확정된 구독 결제 이력이 보인다. | |
| [ ] | `GET /api/admin/payments/receipts`를 호출한다. | 성공 결제에 영수증 근거가 있으면 receipt URL/key가 보이고 raw provider payload나 카드 원문은 보이지 않는다. | |
| [ ] | `GET /api/admin/payments/operation-audit-logs`를 호출한다. | receipt evidence 생성 또는 incident 상태 변경 감사 로그가 보인다. | |
| [ ] | `GET /api/admin/payments/refund-preview/{subscriptionPaymentId}`를 호출한다. | 환불 가능 결제에서는 원 결제액, 예약/성공 환불액, 남은 환불 가능액이 support-safe 형태로 보인다. | API-only |
| [ ] | `POST /api/admin/payments/refunds`로 환불 요청을 만든다. | provider 호출 없이 `REQUESTED` 환불 원장과 audit log가 생성된다. | API-only |
| [ ] | `POST /api/admin/payments/refunds/{refundId}/approve`를 호출한다. | `APPROVED`로 바뀌고 provider 호출 없이 audit log가 생성된다. | API-only |
| [ ] | 안전한 Toss 테스트 결제로 `POST /api/admin/payments/refunds/{refundId}/execute`를 호출한다. | Toss cancel이 저장된 idempotency key로 호출되고 결과가 `SUCCEEDED`, `FAILED`, 또는 `PENDING_PROVIDER_CONFIRMATION`으로 기록된다. 구독 권한은 자동 변경되지 않는다. | API-only |
| [ ] | 대사 Incident 탭에서 `OPEN` 필터를 확인한다. | 열린 incident만 표시된다. | |
| [ ] | 대사 Incident 탭에서 `전체`, `ACKNOWLEDGED`, `RESOLVED`, `IGNORED` 필터를 확인한다. | 상태별 조회가 정상 동작한다. | |
| [ ] | incident 상태와 처리 메모를 저장한다. | 상태와 메모가 저장되고 다시 조회해도 유지되며 operation audit log가 생성된다. | |
| [ ] | incident 화면의 민감정보 노출 여부를 확인한다. | billing key, authKey, customerKey, Toss secret, 카드 원문, provider raw payload가 보이지 않는다. | |

## 8. 대사와 운영 장애 대응

| 체크 | 항목 | 기대 결과 | 메모 |
|------|------|-----------|------|
| [ ] | `GET /api/admin/payments/reconciliation`을 호출한다. | 현재 로컬/Provider 불일치 상태가 support-safe 형태로 반환된다. | |
| [ ] | scheduled reconciliation이 실행되는지 확인한다. | 설정된 시간에 대사가 실행되고 이상 시 incident가 생성/갱신된다. | |
| [ ] | 같은 불일치가 반복될 때 확인한다. | 중복 row 대신 occurrence count와 lastDetectedAt이 갱신된다. | |
| [ ] | `RESOLVED` incident가 다시 발견되는 상황을 확인한다. | incident가 다시 `OPEN`으로 열린다. | |
| [ ] | `IGNORED` incident가 다시 발견되는 상황을 확인한다. | ignored 상태는 유지되고 occurrence metadata만 갱신된다. | |
| [ ] | 운영자 이메일 알림 설정을 켠 테스트를 수행한다. | 설정된 경우에만 operator email이 발송된다. | |

## 9. 보안과 데이터 경계

| 체크 | 항목 | 기대 결과 | 메모 |
|------|------|-----------|------|
| [ ] | 프론트 화면 전체에서 결제 민감정보를 확인한다. | raw billing key, authKey, customerKey, 카드 원문이 보이지 않는다. | |
| [ ] | 서버 로그를 확인한다. | Toss secret, billing key 원문, 카드 원문이 로그에 남지 않는다. | |
| [ ] | API 응답을 브라우저 네트워크 탭에서 확인한다. | 운영에 필요한 support-safe 필드만 내려온다. | |
| [ ] | 결제 실패/취소 시 에러 문구를 확인한다. | 사용자가 다음 행동을 이해할 수 있고 내부 예외 상세가 노출되지 않는다. | |

## 10. 최종 판단

| 체크 | 항목 | 기대 결과 | 메모 |
|------|------|-----------|------|
| [ ] | 신규 가입, 업그레이드, 다운그레이드, 취소, 취소 철회를 모두 통과했다. | 사용자 구독 핵심 흐름을 운영 후보로 볼 수 있다. | |
| [ ] | 정기 갱신 성공/실패/만료 흐름을 확인했다. | 스케줄러와 권한 정책이 결제 상태와 일치한다. | |
| [ ] | 관리자 결제 운영 화면과 incident workflow를 확인했다. | 운영자가 이상 상황을 발견하고 처리 상태를 남길 수 있다. | |
| [ ] | 민감정보 비노출을 확인했다. | 결제 운영 화면과 API가 보안 경계를 지킨다. | |
| [ ] | 남은 P2 범위를 확인했다. | 환불 backend는 구현됨. 남은 범위는 환불 entitlement correction, first-class admin refund UI, 정산, 세금계산서, webhook, multi-PG다. cash receipt issue/cancel은 카드-only 정기결제 범위에서는 보류한다. | |
