## [GOAL / WHY]

- 현재 결제 reconciliation은 매일 01:00 자동 실행되고 WARN 로그를 남기지만, 별도 incident 저장이나 운영자 알림이 없다.
- 운영자가 사용자 신고 없이도 결제 불일치 가능성을 발견하려면 reconciliation 결과를 DB에 영속 저장하고, 관리자 조회/상태 변경 및 선택적 운영자 알림이 필요하다.
- 목표는 자동 환불/자동 구독 보정이 아니라, 결제 불일치 후보를 놓치지 않고 추적 가능한 운영 흐름으로 만드는 것이다.

## [SCOPE]

### In

- `payment_reconciliation_incidents` 신규 테이블/엔티티/리포지토리를 추가한다.
- reconciliation mismatch를 중복 방지 키 기준으로 `OPEN`, `ACKNOWLEDGED`, `RESOLVED`, `IGNORED` 상태로 저장한다.
- 동일 issue가 반복 감지되면 발생 횟수와 마지막 감지 시각을 갱신한다.
- 해결된 issue가 다시 감지되면 재오픈할 수 있게 한다. 단, `IGNORED` 상태는 운영자가 의도적으로 무시한 항목으로 유지한다.
- 관리자 read-only 목록 API와 상태 변경 API를 추가한다.
- 운영자 이메일 알림은 환경변수로 명시 활성화된 경우에만 발송한다.
- SR-93, payment operations runbook, API spec, DB schema, index 문서를 현행화한다.
- 백엔드 테스트와 문서 검증을 수행한다.

### Out

- 자동 환불/자동 취소/자동 구독 보정.
- 관리자 환불/강제 취소 mutation.
- Slack, SMS, Kakao 알림.
- 프론트 관리자 화면 구현.
- 멀티서버 scheduler lock.
- Toss webhook 본 구현.
- 멀티 PG 구현.

## [SUCCESS CRITERIA / DoD]

- reconciliation scheduler가 mismatch를 감지하면 DB incident가 생성/갱신된다.
- 중복 issue는 새 row를 무한 생성하지 않고 기존 incident를 갱신한다.
- admin API로 incident 목록을 조회할 수 있다.
- admin API로 incident 상태를 `OPEN`, `ACKNOWLEDGED`, `RESOLVED`, `IGNORED` 중 하나로 변경할 수 있다.
- 운영자 알림은 기본 비활성화이며, 활성화 설정과 운영자 이메일이 있을 때만 발송된다.
- 민감정보(raw billing key, Toss secret key, raw card data, raw provider payload)는 incident, 알림, API 응답에 저장/노출하지 않는다.
- DB schema, API spec, SR-93, runbook 문서가 현재 구현을 반영한다.
- backend focused tests, full backend tests, docs validation이 통과한다.

## [CONSTRAINTS / POLICIES]

- DB 스키마 추가는 본 REQ 승인 범위에 포함한다.
- incident 저장은 결제/구독 상태를 바꾸지 않는다.
- 알림은 운영자용이며 사용자에게 결제 오류 알림을 자동 발송하지 않는다.
- 이메일 알림은 기본값 `false`로 둔다.
- 관리자 상태 변경은 incident workflow 상태만 변경하며, 결제 환불/구독 보정으로 확장하지 않는다.
- 모든 응답과 로그는 support-safe metadata만 포함한다.

## [RISKS / OPEN QUESTIONS]

- Risks:
  - GET endpoint에서 provider 조회/incident 저장을 동시에 수행하면 HTTP 의미가 흐려질 수 있으므로, incident 저장은 scheduler/명시적 run 흐름에 한정한다.
  - 이메일 알림을 기본 활성화하면 로컬 테스트/운영 준비 중 오발송 위험이 있으므로 기본 비활성화한다.
  - incident가 쌓이면 운영자가 처리하지 않는 backlog가 생길 수 있다.
- Questions:
  - 즉시 blocker 없음. 본 REQ는 이메일 알림만 포함하고 Slack/SMS는 후속 범위로 둔다.

## [APPROVAL POINTS]

- 신규 DB 테이블 `payment_reconciliation_incidents` 추가를 승인한다.
- 운영자 이메일 알림은 기본 비활성화로 승인한다.
- admin incident 상태 변경은 incident workflow만 변경하고 결제/구독/환불 mutation은 하지 않는 것으로 승인한다.
