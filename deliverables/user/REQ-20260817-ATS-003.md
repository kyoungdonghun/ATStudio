[GOAL / WHY]

- 컴파일 전용 준비성 WI는 정제 결과 `PASS`였다.
- 이전 DB 실행 시도는 MA의 상태 확인 중단이 러너 구성 전에 발생하여 실행되지 않았다. 이는 운영자 중단의 실행 전 종료이며, guard, DB, 비공개 번들, 컴파일러 실패가 아니다. DB 연결, DDL, 데이터 변경은 한 번도 발생하지 않았다.
- 기존 승인 패치에 대해 새 러너로 정확히 한 번만 최종 시도하고, 중간 상태 중단 없이 단일 터미널 결과까지 완료한다.

[SCOPE]

- In:
  - `scripts/database/patches/WI-20260809-ATS-068-user-consents.sql`을 소스 감사한 뒤, 기존 비공개 번들을 메모리에서만 검증하는 새 러너로 단 한 번 실행 시도
  - 연결 1회, `user_consents` 부재 확인 1회, 해당 패치 적용 1회, 사후 구조 집합 델타 확인 1회만 수행
  - 사후 델타는 기대된 `user_consents` 추가만 허용하며, 제거 및 예상 밖 추가는 각각 `0`이어야 함
  - 정제된 터미널 증거 작성, 임시 산출물 정리, `validate_docs.py` 및 대상 REQ의 `git diff --check` 실행
- Out:
  - 두 번째 시도, 재시도, 수리, 롤백, 보상, 삭제, `DROP`, 추가 SQL, 추가 연결, 대상 확대
  - 실행 중 운영자의 상태 확인 중단, 제품 코드ㆍ설정ㆍ정책ㆍ설계 변경, 번들 생성ㆍ수정ㆍ영속화, 그 밖의 모든 무관 작업
  - 비밀값, DB 식별자ㆍ연결 정보, 비공개 번들 정보, 원시 컴파일러ㆍDB 진단의 표시 또는 보존

[SUCCESS CRITERIA (DoD)]

- 기존 비공개 번들은 메모리 내 검증만 통과해야 하며, 패치 소스 감사 결과가 지정 파일과 일치해야 한다.
- 새 러너는 중단 없이 단일 터미널 결과까지 진행하며 JDBC 연결 수는 정확히 `1`이다.
- `user_consents`가 부재일 때만 패치를 정확히 `1`회 적용한다. 조건 불일치나 실제 실패는 즉시 터미널 실패로 종료한다.
- 성공은 `user_consents`만 추가, 제거 `0`, 예상 밖 추가 `0`의 정제된 사후 델타 증거로 인정한다.
- 임시 산출물 정리와 문서 검증 및 대상 REQ의 `git diff --check`가 통과한다.
