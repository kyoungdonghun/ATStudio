[GOAL / WHY]

- AT.M V1을 "모든 개선이 끝난 상태"가 아니라 "실제 운영이 가능하고 이후 발견 사항은 SR 기반 유지보수로 이관할 수 있는 상태"로 마감한다.
- 현재 확인된 품질 gate 실패, 43-table MySQL 기준선 미기록, 알려진 React Router 취약점, 현행 문서 오기를 닫고 재현 가능한 release candidate를 만든다.

[SCOPE]

- In:
  - 약관 동의, 인증 오류 분류, 중복 로그아웃 방지의 현재 계약에 맞게 백엔드/프론트 회귀 테스트를 보정하고 전체 quality gate를 통과시킨다.
  - `react-router` 및 `react-router-dom`을 현재 감사가 제시한 보안 수정 버전으로 통제된 메이저 업그레이드하고, 라우팅/인증 UI 회귀를 검증한다.
  - 현재 43-table 소스 상태, 의존성 감사 결과, production gate를 현재 문서에 정확히 반영한다.
  - 별도 승인된 disposable loopback MySQL에서만 현재 schema/seed의 manifest를 관측, 기록, 재검증하고 정확한 대상만 정리한다.
  - 운영 환경의 비밀값, HTTPS/CORS/callback, SMTP, Toss live rehearsal, backup/restore, logging/alerting, 단일 scheduler 확인을 release checklist로 고정한다.
  - 변경 사항을 검증 가능한 commit 단위로 고정하고 독립 최종 감사를 수행한다.
- Out:
  - 신규 상품 기능, 결제 정책 변경, 멀티 PG 추가, retained-data migration, multi-server scheduler lock.
  - 실제 결제/환불을 발생시키는 무승인 live provider 호출.
  - production DB, 외부 비밀값, 기존 고객 데이터의 열람/변경/삭제.

[SUCCESS CRITERIA (DoD)]

- 백엔드 Gradle 전체 test/check와 프론트 typecheck, lint, format, 전체 Vitest, production build가 모두 통과한다.
- 현재 43-table schema가 disposable MySQL에서 최초 설치, Hibernate `ddl-auto=validate` 기동, 구조 manifest 검증을 통과하고 대상 disposable DB만 정리된다.
- `npm audit --omit=dev`에서 현재 알려진 React Router production 취약점이 제거되거나, 제거 불가 시 명시적 보류 승인과 완화 근거가 기록된다.
- 현재 상태 문서는 code, schema, dependency 상태와 일치하며 historical evidence와 current evidence를 혼동하지 않는다.
- 실제 운영 환경에 필요한 외부 준비 항목과 책임자가 체크리스트로 남고, release candidate의 commit/검증 결과가 추적 가능하다.
- 이 범위 밖 후속 개선은 SR 유지보수로 이관한다.

[CONSTRAINTS / POLICIES]

- Work tracking unit: WI.
- 사용자 노출 브랜드는 `AT.M`; 내부 프로젝트/경로/API 식별자는 `ATStudio`를 유지한다.
- 비밀값, JDBC URL, 결제/메일 credential은 출력, 문서 기록, Git commit에 포함하지 않는다.
- disposable DB 생성/관측/삭제는 loopback과 guarded `ats_disposable_YYYYMMDD_xxxxxxxx` 이름으로만 수행하며, 실행 직전 대상과 정리 범위를 다시 확인한다.
- 운영 준비는 공개 acceptance tunnel의 성공과 동일시하지 않는다.
- 모든 코드/문서 수정은 WI handoff와 evidence pack으로 추적한다.

[RISKS / OPEN QUESTIONS]

- Risks:
  - React Router 메이저 업그레이드는 라우팅/테스트 동작을 바꿀 수 있어 전체 프론트 검증과 시각적 핵심 경로 점검이 필요하다.
  - DB manifest 실행은 disposable 대상이라도 생성/정리를 포함하므로 실제 실행 직전 승인 범위를 재확인한다.
  - 실제 SMTP/Toss live/production infra 검증은 외부 계정과 환경 구성이 있어야 하며, 이 저장소만으로 완료할 수 없다.
- Questions:
  - 없음. 외부 운영 환경 값 또는 live rehearsal 실행이 필요해지는 시점에만 비밀값을 공유하지 않는 방식으로 별도 확인한다.
