# REQ-20260517-ATS-001: Toss 단건 결제 연동

[GOAL / WHY]
- Mock-first 결제 계약 위에 Toss Payments 단건 결제 경로를 추가한다.
- 로컬/테스트 환경에서는 실제 과금 없이 결제 흐름을 검증하고, 운영 환경에서는 서버 승인 기반으로 구독 생성/업그레이드가 결제 성공 후에만 적용되도록 한다.

[SCOPE]
- In:
  - 결제 provider 설정을 `MOCK` 또는 `TOSS`로 선택 가능하게 한다.
  - Toss 결제 준비 응답에 client-safe checkout metadata를 포함한다.
  - Toss success redirect에서 받은 `paymentKey`, `orderId`, `amount`를 서버 confirm API로 전달한다.
  - 서버는 저장된 `PaymentOrder`의 사용자, provider, 금액, 만료 상태를 검증하고 Toss confirm API를 호출한다.
  - Toss test/live key는 환경변수로만 주입한다.
  - 구독 결제 화면과 업그레이드 흐름이 Mock/Toss provider를 모두 처리한다.
  - API/DB/UI 문서를 Phase B 상태로 현행화한다.
- Out:
  - Toss 자동결제/빌링키 저장 및 정기 결제 실행.
  - 환불/취소 자동화, webhook, 거래 대사.
  - 운영용 실키 발급/계약 처리.
  - KakaoPay 구현.

[SUCCESS CRITERIA (DoD)]
- `app.payment.provider=MOCK` 기본값에서 기존 Mock success/fail/cancel 테스트가 유지된다.
- `app.payment.provider=TOSS`일 때 prepare 응답이 Toss V2 checkout에 필요한 client key, order name, success/fail URL, customer key를 반환한다.
- Toss confirm은 secret key를 브라우저에 노출하지 않고 서버에서만 호출한다.
- Confirm 시 클라이언트 금액을 신뢰하지 않고 저장된 주문 금액을 기준으로 승인 요청한다.
- Toss 승인 실패 시 `payment_orders`가 FAILED로 남고 구독 생성/업그레이드는 적용되지 않는다.
- 관련 백엔드/프론트엔드 테스트, 타입체크, 문서 검증이 통과한다.

[CONSTRAINTS / POLICIES]
- Work tracking unit: WI
- 결제 secret, billing key, API key는 코드/문서에 하드코딩하지 않는다.
- 실제 결제가 발생할 수 있는 live key 사용은 로컬 기본값이 아니어야 한다.
- Toss 공식 문서 기준으로 V2 SDK와 서버 승인 모델을 따른다.
- Recurring billing은 이번 단계에서 설계/문서 연결까지만 유지한다.
- 파괴적 DB 작업, 데이터 삭제, 실운영 과금 테스트는 수행하지 않는다.
