# REQ-20260517-ATS-002: Toss 빌링키 기반 정기결제

[REQ]
REQ ID: REQ-20260517-ATS-002
Project: ATS
Owner: MA
Status: approved

[GOAL / WHY]
- ATStudio 구독 결제에 Toss Payments 빌링키 기반 정기결제를 추가한다.
- 현재 구현된 `MOCK` 결제와 Toss 단건 결제 흐름은 유지하면서, 정기결제 등록, 갱신 결제, 실패 처리, 자동 갱신 취소를 별도 레이어로 설계하고 구현한다.
- 구독 활성화, 업그레이드, 갱신은 결제 성공 이후에만 적용되도록 유지하고, 모든 결제 시도와 갱신 결과는 추적 가능해야 한다.

[SCOPE]
- In:
  - `billing_agreements` 도메인, 저장소, 상태 모델을 추가한다.
  - Toss 빌링키 등록 준비/확인/취소 API를 추가한다.
  - `RecurringPaymentProvider` 계열 인터페이스를 추가하고 Toss 빌링키 승인 어댑터를 구현한다.
  - 빌링키는 서버에만 저장하고, 평문 저장 없이 암호화 저장 및 비가역 fingerprint를 사용한다.
  - 정기 갱신 job을 추가해 갱신 대상 구독에 대해 `RENEWAL` payment order를 생성하고 결제 성공 시 구독 기간을 연장한다.
  - 정기결제 실패 시 `payment_orders` 실패 기록, billing agreement 실패 횟수 증가, 구독 유예/만료 정책을 적용한다.
  - 사용자가 자동 갱신을 취소하면 이후 결제를 중지하되, 이미 결제된 구독 접근권은 `expiresAt`까지 유지한다.
  - 프론트엔드 구독 결제/관리 화면에 정기결제 선택, 결제수단 등록 상태, 자동 갱신 취소 흐름을 추가한다.
  - API/DB/UI 문서와 테스트를 Phase C 상태로 현행화한다.
- Out:
  - KakaoPay, Naver Pay 등 Toss 외 PG 구현.
  - Toss webhook, 자동 환불, 정산, 세금계산서, 회계 처리 자동화.
  - 운영용 관리자 결제 감사 화면의 전체 구현.
  - SR-92의 Toss 결제위젯 모달/전용 checkout 분리 작업. 단, 정기결제 UI가 이 SR과 충돌하지 않게 설계한다.
  - 실제 live key를 사용한 과금 테스트.

[SUCCESS CRITERIA (DoD)]
- `app.payment.provider=MOCK`와 기존 Toss 단건 결제 흐름이 회귀 없이 동작한다.
- 사용자는 정기결제 모드에서 Toss 빌링키 등록을 시작하고, 성공 콜백 후 `BillingAgreement`가 `ACTIVE` 상태로 저장된다.
- 빌링키와 Toss secret key는 프론트엔드 응답, 로그, 문서, 테스트 픽스처에 평문으로 노출되지 않는다.
- 초기 정기 구독은 결제수단 등록만으로 활성화되지 않고, 승인된 초기 결제까지 성공해야 구독이 `ACTIVE`가 된다.
- 갱신 job은 결제일이 도래한 활성 정기결제 구독만 대상으로 하며, 같은 구독 기간에 대해 중복 갱신 결제를 만들지 않는다.
- Toss 자동결제 승인 성공 시 `subscription_payments`가 생성되고 `user_subscriptions.expiresAt`이 다음 기간으로 연장된다.
- Toss 자동결제 승인 실패 시 구독 상태, billing agreement 상태, 실패 횟수, 다음 재시도 여부가 정책대로 반영된다.
- 자동 갱신 취소 후에는 다음 결제일부터 Toss 승인 API를 호출하지 않는다.
- 백엔드 테스트, 프론트엔드 타입체크/핵심 테스트, 문서 검증이 통과한다.

[CONSTRAINTS / POLICIES]
- Work tracking unit: WI
- REQ 승인 전에는 구현 파일을 수정하지 않는다.
- 결제 secret, billing key, customerKey 매핑 정보는 보안 민감정보로 취급한다.
- 빌링키 암호화 키는 환경변수 또는 gitignored local 설정으로만 주입한다.
- 로컬 테스트 기본값은 실제 과금이 발생하지 않는 `MOCK` 또는 Toss test key만 허용한다.
- Toss 공식 문서 기준으로 빌링키는 서버가 `customerKey`와 매핑해 저장하고, 갱신 결제 스케줄링은 ATStudio가 직접 구현한다.
- 정기결제는 카드/계좌 자동결제 중심으로 설계하며, Toss Pay, KakaoPay, Naver Pay 같은 국내 간편결제 자동결제 지원을 전제로 하지 않는다.
- DB 스키마 변경은 승인된 REQ와 WI 안에서만 수행한다.

[RISKS / OPEN QUESTIONS]
- Risks:
  - Toss 자동결제는 별도 계약/리스크 검토가 필요할 수 있어, test key 구현과 운영 활성화 조건을 분리해야 한다.
  - 빌링키는 노출되면 재결제 위험이 있으므로, 암호화 키 관리 실패가 가장 큰 보안 리스크다.
  - 갱신 job은 중복 실행, 서버 재시작, 부분 실패 상황에서 idempotency가 깨지기 쉽다.
  - 결제 성공 후 로컬 구독 연장 실패가 발생하면 보상 취소/환불 경로가 필요하지만, 자동 환불은 이번 범위 밖이다.
  - 정기결제 실패 유예 정책이 불명확하면 사용자는 결제 실패 직후 접근권 상실 또는 과도한 유예를 경험할 수 있다.
- Resolved Decisions:
  - 초기 정기 구독은 "빌링키 등록 후 즉시 1회 결제 성공 시 활성화"를 기본 정책으로 한다.
  - 결제 실패 시 기본 유예 기간은 `3일`, 재시도 횟수는 `3회`로 한다.
  - 빌링키 암호화 키 이름은 `PAYMENT_BILLING_KEY_ENCRYPTION_SECRET`로 고정한다.

[ALTERNATIVE SUGGESTION]
- 추천안:
  - 정기결제 등록과 초기 결제를 한 흐름에서 처리하되, 내부적으로는 `BILLING_AGREEMENT`와 `SUBSCRIBE` payment order를 분리한다.
  - 실패 정책은 우선 `3일 유예 + 최대 3회 재시도 + 이후 SUSPENDED/EXPIRED 전환`으로 설계하고, 실제 운영 데이터가 쌓인 뒤 조정한다.
  - SR-92의 결제창 UX 분리는 이번 REQ에서 구현하지 않고, Phase C 안정화 후 독립 UX REQ/SR로 처리한다.
- 대안:
  - 정기결제 등록만 먼저 만들고 초기 결제는 기존 Toss 단건 결제로 유지할 수 있다. 구현 위험은 낮지만 사용자 흐름이 두 단계로 늘어난다.
