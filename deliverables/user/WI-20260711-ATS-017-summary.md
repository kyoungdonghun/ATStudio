# WI-20260711-ATS-017 Backend/DB/API Independent Review Summary

## 결론

- 기준점: `dev/kyoung`, HEAD `27d22446e5d21324dadcfcb322dbe51704dfe914`.
- 독립 재판정 결과는 **확정 P0 3건, 확정 P1 11건, 조건부 P1 1개 결함군**이다.
- 선행 리뷰의 P1 주장 중 화이트리스트 제거 완료 상태와 ADMIN 결제 진입은 P2로 축소했고, 소셜 로그인 콜백은 백엔드 결함이 아니라 프론트엔드 연동 결함으로 이관했다.
- 신규 MySQL DB도 안전하지 않다. `schema.sql`의 결제 정산 감사 ENUM 누락은 신규 설치에서 그대로 재현 가능한 DDL/Java 불일치다.
- 기존 DB는 별도 위험이다. 저장소에 완전한 순서형 마이그레이션 체인이 없고 회사 인증 문서의 레거시 메타데이터 백필도 없어, 실제 DB 기준선을 확인하기 전에는 업그레이드 가능성을 확정할 수 없다.

## 권장 개선 순서

1. P0 세 건을 먼저 차단한다: 원본 파일을 공개 정적 루트에서 분리하고, 탈퇴 시 갱신을 중단하며, 이메일 실패 로그에서 토큰/PII를 제거한다.
2. 신규 MySQL DDL의 정산 감사 ENUM을 고치고, 실제 기존 DB 기준선을 확인해 순서형 마이그레이션과 회사 문서 백필 계획을 확정한다.
3. 결제 명령에 행 claim/lock 또는 optimistic version, 청구 기간 키, 주문당 최종 결제 유일성을 도입한다.
4. 갱신 주문을 청구 기간으로 식별하고 due 작업을 페이지/claim 단위의 독립 트랜잭션으로 분리한다.
5. 최초 결제 실패 결과를 별도 커밋 경계로 보존하고, 환불 예약 시 원 결제를 잠근다.
6. 공통 transaction-aware 파일 mutation coordinator와 실패 삭제 재시도/정합성 점검을 도입한다.
7. 회사 문서 검역/서명 검증, 플레이리스트 이미지 decode/re-encode, 화이트리스트 CSV 수식 중화를 적용한다.
8. 서버 로그아웃과 비밀번호 변경/재설정 시 refresh 세션 폐기를 구현한다.
9. 수정 후 MySQL/Testcontainers, 실제 Spring 트랜잭션, 두 worker 동시성, resource-handler 보안 테스트를 추가한 뒤 전체 회귀를 다시 실행한다.
