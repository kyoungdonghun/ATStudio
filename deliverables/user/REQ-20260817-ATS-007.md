[GOAL / WHY]

- 임시 저장소 밖 인벤토리 시도 두 건이 검증 가능한 결과를 남기지 못했다. 기존 일회용 MySQL bootstrap 도구에 최소 범위의 재사용 가능한 읽기 전용 `Inventory` 액션을 추가하고, 이후 한 번만 실제 인벤토리를 실행한다.
- 이 작업은 가능한 고아 일회용 스키마의 존재 여부만 집계한다. 어떤 정리나 데이터 변경 권한도 부여하지 않는다.

[SCOPE]

- In:
  - 지원되는 진입점인 `scripts/database/bootstrap-disposable-mysql.ps1`와 `scripts/database/DisposableMysqlBootstrap.java`에만 새 `Inventory` 액션을 추가한다.
  - `scripts/database/test-bootstrap-guards.ps1`에 `Inventory`의 사전 연결 guard와 읽기 전용 단일 집계 계약을 검증하는 집중 guard test를 추가한다.
  - 실제 소스 동작이나 지원 인터페이스가 바뀌어 설명 정정이 필요한 경우에만 `scripts/database/README.md`를 최소 범위로 갱신한다.
  - `Inventory` 성공 결과는 정수 집계 하나와 `NO_POSSIBLE_ORPHAN` 또는 `POSSIBLE_ORPHAN_EXISTS` 하나만 보존하고 출력한다. 이 결과에는 스키마명, 데이터베이스명, 호스트/포트, URL, 자격 증명, 불투명 번들 데이터나 경로, 원시 SQL/행, 진단 정보를 포함하지 않는다.
  - `Inventory`의 사전 연결 단계는 액션 allowlist, loopback 호스트, 필수 동반 일회용 이름 형식, 현재 소스의 `CREATE TABLE` 수 43을 모두 확인한다. 동반 이름은 형식 guard 전용이며 조회 대상이 아니다. preflight가 끝나기 전에는 Connector/J 탐색ㆍ로딩, 자격 증명 읽기, 연결을 수행하지 않는다.
  - DB 단계는 관리자/root endpoint 하나에만 연결하고, `^ats_disposable_[0-9]{8}_[a-z0-9]{8}$`와 정확히 일치하는 일회용 스키마명 정규식 predicate로 제한된 `COUNT` 쿼리 정확히 하나만 수행한다. 동반 이름은 그 쿼리의 대상이 아니며, 이름을 선택하지 않고 선택된 `atstudio` DB에 접근하지 않는다.
  - 구현 및 guard test가 완료된 뒤, 저장소 밖의 불투명 외부 번들을 사용하여 지원 도구를 통한 실제 `Inventory`를 정확히 한 번 실행한다.
- Out:
  - `CREATE`, `ALTER`, `DROP`, DML, 스키마 적용, 시드, 패치, manifest expectation 기록 또는 변경.
  - 이름 목록화, 원시 행 또는 원시 SQL 조회ㆍ출력, 선택된 `atstudio` DB 접근, 일반 DB/원격 DB 탐색.
  - 기존 액션의 동작 변경. 허용 액션 목록에는 `Inventory`만 추가한다.
  - 가능한 고아의 정리, 삭제, 재시도, 추가 조사, 애플리케이션 변경, 제품 DB 접근.

[SUCCESS CRITERIA (DoD)]

- `Inventory`는 기존 지원 PowerShell 진입점을 통해서만 호출되며, 기존 액션은 동작을 유지한 채 allowlist에 `Inventory`만 추가된다.
- 유효한 `Inventory`는 loopback, 형식 guard 전용 동반 이름, 현 소스 43-table count를 모두 통과하기 전 Connector/Jㆍ자격 증명ㆍDB 연결을 시작하지 않는다. 불일치 또는 거부는 연결 전에 실패 폐쇄한다.
- DB 단계는 관리자/root endpoint 하나만 사용하며, `^ats_disposable_[0-9]{8}_[a-z0-9]{8}$` 정규식 predicate가 있는 `COUNT` 한 번뿐이다. 이름 선택, 선택된 DB 연결, `atstudio` 접근, DDL/DML, 스키마ㆍ시드ㆍ패치, manifest expectation 처리는 없다.
- 성공 산출물은 정수 count와 가능한 고아 상태 하나로 제한된다. count가 0이면 `NO_POSSIBLE_ORPHAN`, 0보다 크면 `POSSIBLE_ORPHAN_EXISTS`를 표시한다. 금지된 연결ㆍ대상ㆍ번들ㆍ원시ㆍ진단 정보는 표준 출력, 표준 오류, WI 산출물에 남기지 않는다.
- 집중 guard test는 action allowlist, loopback, 형식 guard, 43-table preflight, Connector/J/자격 증명 선행 금지, 단일 `COUNT` 정규식 범위, 이름 비선택, selected DB 비접근, 변경 SQL 부재, manifest expectation 비변경, 기존 액션 보존을 확인한다.
- 실제 실행은 구현 WI가 통과한 뒤 정확히 한 번만 수행한다. 결과 count가 0보다 크면 즉시 중지하고 별도 파괴적 정리 승인을 요청한다. count가 0인 경우에도 정리는 이 REQ 범위 밖이다.

[CONSTRAINTS / POLICIES]

- Work tracking unit: WI. 본 REQ는 사용자의 지속적인 비설계 작업 진행 지시와 읽기 전용 일회용 DB 인벤토리의 명시 승인을 근거로 승인 상태다.
- 최소 변경 원칙을 적용한다. 구현 가능 파일은 PowerShell entrypoint, Java entrypoint, 집중 guard test, 그리고 소스 동작상 필요한 경우의 README뿐이다.
- 불투명 외부 번들은 두 번째 WI의 연결 수단일 뿐이다. 그 내용, 식별자, 파일명, 경로, 자격 증명, URL, 호스트/포트는 열람ㆍ출력ㆍ기록하지 않는다.
- `Inventory`는 일회용 이름 형식과 일치하는 스키마의 존재 가능성만 집계한다. 이는 어떤 대상의 삭제 권한이나 전체 환경의 무결성 결론이 아니다.
- 실제 DB 실행 전에 반드시 구현 WI의 Evidence Pack과 집중 guard test 통과를 확인한다. 실제 실행은 한 번뿐이며, 결과가 불명확하거나 안전 gate가 실패하면 재시도하지 않는다.
- 이 REQ는 destructive cleanup을 승인하지 않는다. count가 양수인 경우에만 후속 정리의 별도 명시 승인을 요청하고, 그 전까지 어떤 정리도 수행하지 않는다.
