# REQ-20260521-ATS-001: Toss 정기결제 운영 안정화 및 단건 구독 결제 제거

[REQ]
REQ ID: REQ-20260521-ATS-001
Project: ATS
Owner: MA
Status: approved

[GOAL / WHY]
- ATStudio 구독 결제는 로컬 인수테스트 기준 기능 구현을 완료한 상태로 보고, 운영 투입 전 안정화 작업을 별도 REQ로 분리한다.
- 구독 사용자 흐름은 Toss billing-key 기반 정기결제로 단순화하고, QR/앱 기반 Toss one-time 단건 구독 결제 경로는 제거한다.
- 운영 전에는 결제 실패, redirect 누락, 원장 불일치, 구독 만료/차단, 운영자 조회, 이메일 알림을 보강해 실제 서비스 장애 가능성을 낮춘다.

[SCOPE]
- In:
  - `SR-93`을 운영 안정화 백로그의 기준 문서로 삼아 구현 가능한 항목을 REQ/WI로 분해한다.
  - 백엔드에서 구독 `UPGRADE` one-time 결제 경로를 차단한다.
  - 구독 `SUBSCRIBE` one-time 결제 코드와 UI/API 진입점을 제거하거나 비구독 legacy/test 범위로 격리한다.
  - 신규 구독은 전용 checkout/callback 단계에서 Toss billing auth -> billing key 발급 -> 첫 결제 -> 구독 활성화로 진행한다.
  - 기존 구독자가 billing agreement 없이 업그레이드를 시도하면 결제수단 등록 흐름으로 유도한다.
  - 테스트 DB 기준 모든 계정의 구독/권한 상태를 재검증한다. 기본 방향은 DB hard delete가 아니라 만료/취소/무구독 상태를 통해 접근 차단을 검증하는 것이다.
  - 갱신 실패 정책은 `3일 / 3회 재시도`를 유지한다.
  - grace 종료 후 구독은 `EXPIRED`, billing agreement는 `SUSPENDED`로 정리한다.
  - 자동 갱신 해지는 현재 이용 기간 유지 후 만료로 처리한다.
  - 운영 전에는 reconciliation job을 우선 추가하고, 이후 webhook까지 확장할 수 있게 설계한다.
  - 결제 성공 후 로컬 저장 실패에 대비해 실패 원장과 운영자 runbook을 먼저 마련하고, 자동 취소/환불은 후속 자동화 대상으로 둔다.
  - 운영자 결제 화면은 read-only 조회부터 구현한다.
  - 만료된 payment order 정리 스케줄러를 추가한다.
  - 결제 실패 사용자 이메일 알림을 기존 메일 인프라를 활용해 추가한다.
  - Toss 단일 PG 기준으로 마감하되 provider 추상화는 훼손하지 않는다.
  - Toss 테스트 내역 확인 절차와 실패 케이스 인수테스트를 추가한다.
- Out:
  - KakaoPay, Naver Pay 등 다중 PG 실제 구현.
  - 운영 live key를 사용한 실제 과금 테스트.
  - 환불/취소/정산 조작 기능이 포함된 관리자 화면.
  - 자동 환불/자동 보상 취소의 완전 자동화.
  - 2대 이상 서버를 전제로 한 scheduler distributed lock 도입.
  - 운영 secret 값을 저장소 파일에 기록하는 작업.
  - 사용자 데이터 대량 hard delete 실행. 필요 시 별도 승인 후 수행한다.

[SUCCESS CRITERIA (DoD)]
- 구독 사용자-facing 경로에서 Toss one-time widget 또는 QR/앱 단건 구독 결제 흐름이 제거된다.
- 백엔드는 one-time `UPGRADE` 구독 결제 요청을 수락하지 않는다.
- 신규 구독은 정기결제 등록과 첫 결제 성공 후에만 활성화된다.
- 기존 구독자가 billing agreement 없이 업그레이드하면 안전한 안내와 결제수단 등록 경로를 제공한다.
- 무구독/만료/취소 상태 계정은 구독 권한이 필요한 기능에서 정상 차단된다.
- 갱신 실패는 3일 grace와 최대 3회 재시도 정책을 따른다.
- grace 종료 후 구독과 billing agreement 상태가 각각 `EXPIRED`, `SUSPENDED`로 수렴한다.
- 자동 갱신 해지는 현재 이용 기간을 유지하고 다음 결제를 실행하지 않는다.
- payment order 만료 정리 스케줄러가 READY/IN_PROGRESS 등 오래된 주문을 안전하게 닫는다.
- reconciliation job은 Toss/로컬 원장 불일치를 탐지하고 운영자가 확인 가능한 기록을 남긴다.
- 운영자 read-only 결제 조회에서 payment order, billing agreement, subscription payment를 민감정보 없이 확인할 수 있다.
- 결제 실패 또는 갱신 실패 상태에서 사용자 이메일 알림이 발송된다.
- Toss test-key 환경에서 성공/실패/취소/redirect 누락/갱신 실패 케이스 인수테스트가 문서화된다.
- `gradlew.bat test`, payment focused tests, `npm test`, `npm run typecheck`, `npm run lint`, `npm run build`, 문서 검증이 통과한다.

[CONSTRAINTS / POLICIES]
- Work tracking unit: WI
- REQ 승인 전 구현 파일 수정은 하지 않는다.
- 결제 secret, billing key, authKey, customerKey 원문은 응답, 화면, 로그, 문서, 테스트 fixture에 노출하지 않는다.
- 운영 secret은 환경변수 또는 배포 플랫폼 secret/secret manager로만 주입한다.
- 운영 서버의 기본 결제 provider는 `TOSS_BILLING` 기준으로 잡되, 로컬/테스트 환경은 실제 과금이 발생하지 않게 분리한다.
- scheduler는 현재 단일 서버 운영을 전제로 구현한다. 다중 서버 lock은 후속 확장으로 둔다.
- 대량 DB 삭제, 운영 데이터 삭제, live key 과금 테스트, 환불 조작은 별도 승인 없이는 수행하지 않는다.

[RISKS / OPEN QUESTIONS]
- Risks:
  - 기존 one-time 구독 결제 코드를 제거하면 과거 테스트나 legacy mock 경로가 깨질 수 있다.
  - 결제 성공 후 로컬 저장 실패는 자동 보상 전까지 운영자 runbook에 의존한다.
  - reconciliation job은 provider 조회 API/권한/응답 형태에 따라 구현 난도가 달라질 수 있다.
  - 모든 계정 구독 상태를 테스트에서 정리할 때 hard delete와 만료 상태 전환의 의미가 다르다.
  - 이메일 알림은 과발송, 중복 발송, 민감정보 포함 위험이 있다.
- Questions:
  - 없음. 단, 테스트 DB의 기존 구독 정리는 hard delete가 아니라 만료/취소/무구독 상태 검증으로 우선 설계한다.
