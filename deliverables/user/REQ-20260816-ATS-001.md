[SUCCESS CRITERIA (DoD)]

- 패치 대상은 사전 검증을 통과한 명시 승인 로컬 인수/개발 DB 하나로 한정되며, `atstudio`, 운영, 스테이지, 원격 호스트가 아님이 정제된 증거로 확인된다.
- `user_consents`가 없을 때에만 지정 패치를 정확히 한 번 적용하고, 성공 뒤 `user_consents` 존재와 패치 범위만 검증한다. 이미 존재하거나 대상ㆍ사전조건이 불명확하면 SQL을 실행하지 않고 실패 종료한다.
- 패치 실행은 `user_consents`만 생성하며, 기존 데이터 삭제 또는 다른 스키마 변경이 없음을 확인한다.
- 일회용 DB는 loopback MySQL에서 정확히 하나의 새 식별자로 생성되며, 현행 `schema.sql`과 `seed.sql` 기준의 43-테이블 스키마/시드 검증을 통과한다.
- 남기는 증거는 정제된 매니페스트뿐이다. 증거에는 실행 상태, 43-테이블 검증 결과, 입력 식별자, 검증 판정, 정확한 일회용 DB 삭제 판정만 포함하며 연결 문자열, 자격증명, 환경값, 원시 행 데이터, 개인정보는 포함하지 않는다.
- 일회용 DB는 같은 loopback 연결과 생성 시 기록한 정확한 식별자가 모두 일치할 때에만 삭제되고, 삭제 결과가 확인된다. 불일치 또는 검증 실패 시 삭제를 포함한 위험 작업을 수행하지 않고 실패 종료한다.
- 인수 런타임 준비 핸드오프는 두 작업의 결과ㆍ잔여 위험ㆍ후속 브라우저 인수검사 범위를 분리해 기록한다.

[CONSTRAINTS / POLICIES]

- Work tracking unit: WI
- 본 REQ는 사용자가 2026-08-16에 명시 승인한 DB 실행 범위만 허용한다. 범위 확대, 제품 변경, 대상 DB 변경은 별도 승인이 필요하다.
- 실행자는 저장소 밖에서 제공되는 환경 번들을 불투명한 연결 수단으로만 사용한다. 그 파일이나 값을 열람ㆍ출력ㆍ기록하지 않으며, 무시 설정ㆍ로컬 환경 번들ㆍ비밀값에는 접근하지 않는다.
- 모든 사전 점검은 위험 작업보다 먼저 수행한다. 승인 대상 식별, loopback 여부, 단일 대상 여부, 실행 모드, 예상 DB 식별자가 하나라도 불일치하거나 확인 불가하면 연결, SQL 실행, DB 생성, DB 삭제를 하지 않고 실패 종료한다.
- 기존 DB 패치는 `scripts/database/patches/WI-20260809-ATS-068-user-consents.sql` 하나만 사용한다. 재실행 가능성, 이미 존재하는 `user_consents`, 추가 DDL/DML, 데이터 삭제 징후는 모두 차단 조건이다.
- 일회용 증명은 기존 DB와 완전히 분리된 새 DB에서만 수행한다. 현재 최신 43-테이블 스키마/시드 이외의 입력, 외부 서비스, 이메일, Provider, 결제, 환불, OAuth는 사용하지 않는다.
- 정제 로그만 허용한다. 호스트 세부정보, 포트, 사용자명, 비밀번호, 토큰, 연결 문자열, 환경값, SQL 결과 행, 개인정보를 출력하거나 산출물에 남기지 않는다.
- 정리는 일회용 DB 하나에만 한정한다. 생성 시점의 정확한 식별자와 loopback 대상이 모두 재확인되지 않으면 `DROP DATABASE`를 실행하지 않고 차단 상태로 보고한다.
- 한 번에 하나의 Subagent와 하나의 WI만 순차 실행한다. 각 WI 완료 직후 다음 의존 WI의 핸드오프 패킷을 생성해 위임한다.
